# HAQQMULCH — PYAT's inviolable build-first discipline
## General addendum to MULCH: faithful non-preservation under material limits

**2026-11-20 · user-governed PYAT methodological candidate · not protected authority**

Read beside [SORACLE's general MULCH primer](04_MULCH_FAITHFUL_NON_PRESERVATION_PRIMER_20261120.md) (its current draft [PR #1195](https://github.com/maidiu/rawlsing/pull/1195)) and the [PYAT PROGRAMMA](../../../PYAT_CONTROL_ROOM/PROGRAMMA_PYAT/00_PROGRAMMA_PYAT.md). This document is **cross-task operating discipline**, not a current scientific commission, statistical method, acceptance rubric or replacement for PROGRAMMA. Topic-specific problems, algorithms, thresholds, models, examples and falsifiers belong **only to their own investigation and owner**.

### 1. First, second and third: BUILD PYAT

**The controlling priority is getting the actual PYAT machine built, integrated and useful.** It is not completing a theoretical totality, a preferred method, an infinitely fine representation, an exhaustive validation regime or a catalog of unrealized powers. The user has put completion of the working machine first, second and third. **Do not turn the necessary disciplines of scientific accuracy, historical conservation and receiving into reasons the machine never becomes usable.**

Constructive critique earns its place by **improving actual working behavior**. Reuse accepted code, exact source semantics, real consumer interfaces, already made architectural decisions and presently available resources. Select the shortest adequate existing-owner improvement. Do not resurrect a historically superseded physical form or start another engine merely because a mathematical or conceptual alternative looks cleaner on paper.

MULCH changes the form to retain the function; **HAQQMULCH forces the new form to fit inside material possibility**. This constrains architecture, not just the order in which we test an architecture.

### 2. The four material ceilings are real

Every substantial design must face **(a) available work time and engineering effort, (b) available computational power and purchase/usage cost, (c) runtime and acceptable latency, and (d) permanent and temporary storage capacity**. RAM/peak process-tree memory, file descriptors, I/O, serialization, cold reopening, data transfer and concurrency are relevant components of the concrete resource profile; measured local host capacity and usage permissions determine which ceilings presently bind.

An unmeasured demand for maximal resolution is not a binding requirement. Nor is an arbitrary threshold proposed by a previous agent binding merely because it appears in a document. **The owner of each actual task must justify a quantitative benchmark by showing which real performance or scientific decision it changes**, with exact workload and host conditions. If the relevant result is already usable at acceptable cost, **stop optimizing and build the next needed function**.

A better algorithm under unlimited compute is **not** automatically a better algorithm for PYAT. Something that cannot finish within the available machine, time and money, or cannot deliver outputs to a real consumer, is not the selected solution.

### 3. Zoom out honestly before allowing the project to fail

When full-detail computation is impractical, consider **coarser but scientifically meaningful scope, narrower question, smaller authorized frontier, conditional/on-demand evaluation, sparse representation, bounded search, justified approximation, precomputation of reusable sufficient statistics only where worthwhile, delayed or optional expensive work, and consumer-side interface changes**. These are legitimate constructive responses to material scarcity—not intrinsically scientific defeats.

The choice is **not** between God-resolution and surrender. The feasible resolution is a positive design variable. Preserve the ability to ask a more specific question later when information and resources permit, rather than eagerly materializing all possible combinations now. Distinguish **unsearched** from **searched but unsupported**, **underpowered** from **false**, **estimated** from **observed**, **model-assisted** from **source-native**. Lower-resolution, conditional, partial and uncertain outputs can all be productive when exactly identified.

**Sharp truth boundary:** Feasibility allows giving a weaker, broader or provisional statement. It does **not** authorize calling a fabricated joint observed, changing a denominator without disclosure, granting source rights, erasing a supported contrary configuration, or smuggling an exploratory model into empirically certified truth. If the demanding estimand cannot be computed honestly, change the question or return a truthful typed limitation; **do not fake its answer**.

### 4. Preserve historical powers, not historical burdens

For any inherited component, separate:

- its real function and observed usefulness;
- the source/evidence/owner conditions under which it is true;
- its specific implementation form and material cost;
- the existing lawful consumer and what that consumer actually needs;
- a possible narrower or different replacement achieving the same or stronger real function more economically.

**A historical algorithm is not sacred. A historical achievement is not disposable.** A new feature need not recreate yesterday's module boundaries, intermediate table, serialization scheme, indicator names or full stage order. It must preserve legitimate result meaning, negative states, relevant variants and the ability for downstream analysis to receive what it actually requires—or document and justify a competent transformation of that downstream requirement.

Defend an existing design when a supposedly superior replacement has no measurable consumer benefit. Attack an existing design when it prevents a needed operation. Never defend extra bureaucracy on the ground that it appeared in an earlier commission.

### 5. A downstream consumer can be mulched too

Do not assume an expensive upstream obligation is unavoidable simply because a downstream interface currently expects a huge object or an over-specified answer. Through competent owner agreement, change the consumer's calling pattern, staged inputs, accepted uncertainty, resolution or on-demand queries **when this improves the total organism's fidelity and feasibility**.

The measure is **total-system functionality**, not the elegance of one producer or its exact historical output shape. Material reality, independent evidence, uncertainty, actual social relationships and future computation must not be erased to simplify an interface. Conversely, a beautiful source-aware intermediate representation that nobody can efficiently consume has not completed its task.

### 6. The continuous HAQQMULCH cycle

**INHERIT:** open the exact current repository, owner law, user priorities, source and code HEADs, tests, claims, history, pending original functions and next actual consumer. Admit any currentness gap.

**CONFRONT:** identify the sharpest mismatch between the *best present* component and the required effect. Examine its first consumer and the true cost of the present form. Distinguish a real defect from a hypothetical optimization.

**RECONSTITUTE:** propose the **fewest changed operations** that deliver the important function. Explicitly choose resolution, uncertainty/evidence grade, cost and viable owner. Before minting a new mechanism, check existing mechanisms for the desired power.

**BUILD:** land substantial, integration-ready operative code or an authorized concrete consumer/product improvement wherever the current scope and runtime allow. Do not let planning papers substitute for the next implementation. If blocked by a protected boundary, produce the smallest compatible candidate in the correct owner location with an exact handoff.

**EXERCISE:** run an informative positive and discriminating negative within the actual host/source permissions. Measure only costs that could change the next practical decision. Make no unexecuted test claim.

**CHALLENGE AGAIN:** ask whether the new structure is still too expensive, too narrow, misleading, underused, unowned, overvalidated, scientifically insufficient or disconnected. Continue advancing the operating system rather than explaining why a perfected version would be better.

**RECEIVE:** preserve exact HEADs, real test and independent-review grade, adopted owner judgments and paired protected PROGRAMMA/CURRENT_PROGRESS records through authorized receiving. No fake HQ accreditation or self-adoption.

This sequence is a **decision discipline**, not seven new bureaucratic gates, automatic job launches or a demand to write a new report for every bug.

### 7. The two forbidden forms of failure

**Unbuildable rigor:** a theoretically exquisite method consumes so much time, money, computation or storage that it prevents PYAT reaching a useful, honest product. It is methodologically defective *for this machine*, even if defensible in a less constrained setting. Zoom out, simplify or reassign the question.

**Useful-looking fabrication:** a computational shortcut silently changes what the source supports, invents observed evidence, overwrites uncertainty or denies genuine minorities, so the resulting outputs appear more definite than reality permits. It is defective *as science*, even if it makes the demo impressive. Return a smaller or weaker honest product.

**The inviolables are therefore not maximal resolution, full materialization, exhaustive search or one chosen scientific method. They are a genuinely working machine, truthful evidentiary interpretation, historical-function conservation at real consumer scope, practical resource feasibility, and legitimate owner authority.**

### 8. Compact decision return (only where useful)

When a substantial PYAT change is proposed, its author should be able to say, without performing a new philosophy cycle: **what existing component is being reused; the real missing capability; why the chosen level of fidelity is scientifically honest and adequate for downstream use; the expected and observed cost relative to this host and alternative; the minimal actual code/consumer delta; the positive and negative outcome; and what remains held or unknown**.

If those answers are already available, **code next**. If a better method requires far more resources than it earns in truthful downstream value, **do not adopt it**. If a slightly weaker, honest method gets the full machine moving, **choose it and continue**.

> **HAQQMULCH OATH:** Preserve the truth, recover the living function, discard the unaffordable form. Do not enthrone maximum resolution, historical machinery, abstract perfection or agent-invented benchmarks. Do not counterfeit evidence to create an illusion of progress. Build the most truthful, powerful PYAT that available time, computation, runtime and storage make practicable. Then build the next part.

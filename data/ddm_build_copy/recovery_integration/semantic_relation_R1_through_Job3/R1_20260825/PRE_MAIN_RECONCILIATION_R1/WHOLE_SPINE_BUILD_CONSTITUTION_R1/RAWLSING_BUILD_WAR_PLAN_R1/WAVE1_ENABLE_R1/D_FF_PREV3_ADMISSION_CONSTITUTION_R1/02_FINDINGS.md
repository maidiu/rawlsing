# WAVE 1D — FIELD FORGE RELATION → PRE-V3 ADMISSION FINDINGS R1

## 1. Exact problem being solved

GT0 proved the negative seam correctly: a FIELD FORGE producer-preserving reference or relation cannot be fed to current I04/P06 as though it were an empirical fact, cannot be fabricated into `StructuralEmpiricalAdmission`, and cannot enter current M1 as `DIRECT_STRUCTURAL_EMPIRICAL_ADMISSION`.

Wave 1 now needs the smallest **positive compatibility seam** without undoing that correction.

The problem is therefore not “teach I04 a new family.” It is:

> What is the smallest separately governed PRE-V3 admission object that can say one exact FIELD FORGE relation is eligible for one exact downstream structural use, while preserving relation ownership and all upstream ceilings?

The answer is a sibling relation-admission service and receipt, not coercion into the empirical-admission service.

## 2. Current authority constraints

### FIELD FORGE R2

Adopted FIELD FORGE R2 authorizes explicit actor-independent structural-observatory relations at exact relation grain while preserving producer-owned empirical semantics. It explicitly allows neutral same-unit conjunction/joint, conditional/support/redistribution, comparison/directional, alternative/branch and other relation-specific objects when separately lawful.

It does not authorize strong FIELD/CAPITAL/HEGEMONY/HOMOLOGY/PRESSURE/MECHANISM nouns by default, does not create cross-context transport from similarity, does not choose a physical carrier, and does not permit actor inference.

### WSC001 whole-spine law

The binding separation is:

`FIELD_FORGE_EXACT_RELATION != PRE_V3_STRUCTURAL_ADMISSION`.

The downstream logical owners V553–V558 remain distinct.

### WSC001C second-pass correction

The current concrete implementation is narrower than the first WSC001C prose implied:

- I04 accepts exact `EmpiricalQuerySpec + EmpiricalFact`;
- I04 does not directly consume a FIELD FORGE relation;
- current M1 direct basis is `DIRECT_STRUCTURAL_EMPIRICAL_ADMISSION`;
- current M1 does not directly consume a FIELD FORGE relation or relation-admission object.

That correction is the design boundary for this lane.

### GT0 hostile rereview

GT0 correctly retains `UNDEFINED_FOR_OBJECT` for baseline F0 and `BLOCKED_EXPLICIT_AUTHORITY` for a named substantive structural request absent a governed FIELD-FORGE→PRE-V3 admission surface. Therefore the positive Wave 1 seam must be added deliberately; GT0 does not already contain it by implication.

## 3. Why a sibling admission family is minimal

There are three obvious implementation strategies:

1. **Widen I04/P06 to accept FIELD FORGE relations.** Rejected. This breaks the current empirical object contract and collapses empirical-admission and relation-admission jurisdictions.
2. **Convert a FIELD FORGE relation into EmpiricalFact or StructuralEmpiricalAdmission.** Rejected. This changes semantic type/ownership to fit an implementation and is expressly forbidden by the correction.
3. **Add a sibling relation-admission family using common exact authority/replay utilities.** Adopted as the minimum constitutional design.

The sibling family adds only one new meaning: exact eligibility of one relation for one target use.

## 4. Proposed exact logical families

### 4.1 `FIELD_FORGE_RELATION_ADMISSION_RULE@1.0.0`

This is a content-addressed rule bound to one separately accepted admission authority.

Minimum semantic material:

- exact admission authority id/version/hash;
- exact operation id;
- allowed FIELD FORGE relation family/schema ids;
- allowed upstream relation evidence states for this use;
- exact `target_use_ref`;
- requested downstream owner/contract family;
- allowed relation owner/rule refs where restricted;
- exact allowed scope/universe/risk-set identities where restricted;
- exact participant-role/cardinality/order/multiplicity constraints where target-use constitutive;
- required external authority bindings by role and operation;
- required map/comparator/falsifier/transport authority when cross-context;
- permitted upstream information-loss ceiling;
- permitted relation permission ceiling and exact output permission subset;
- negative-authority refs;
- effective period/current-selection semantics;
- replay semantics.

The rule may not define the FIELD FORGE relation itself. It may only decide downstream use of an already exact relation.

### 4.2 `PREV3_FIELD_FORGE_RELATION_ADMISSION@1.0.0`

This is the immutable decision receipt.

It owns:

- admission decision state;
- decision reason code;
- exact target-use permission narrowed by the decision;
- admission authority/rule identity;
- deterministic receipt/replay identity.

It preserves by exact reference:

- FIELD FORGE relation identity and owner;
- upstream relation rule/authority/currentness;
- relation typed evidence state;
- scope/universe/risk-set and participant bindings;
- applicable negative refs;
- information-loss declaration;
- dependency/provenance/replay closure.

It does not copy the relation into a new semantic owner.

## 5. Decision semantics

The admission decision should use the following small public family:

| decision | meaning | positive structural-use eligibility? |
|---|---|---|
| `ADMITTED` | exact accepted rule positively authorizes this exact relation for this exact target use | YES |
| `VALID_EMPTY` | no positive relation-admission content exists but emptiness is lawful/typed | NO |
| `MISSING_AUTHORITY` | required admission or external authority is absent | NO |
| `DENIED` | exact authority/rule denies the use | NO |
| `DEFERRED` | decision is explicitly deferred | NO |
| `OUT_OF_SCOPE` | relation/scope/target use lies outside exact rule jurisdiction | NO |
| `NONCOMPARABLE` | exact use requires comparison/transport not lawfully established | NO |
| `UNRESOLVED` | exact prerequisites exist conceptually but cannot be resolved positively or negatively | NO |
| `BLOCKED_EXPLICIT_AUTHORITY` | requested semantics require a separately competent owner not present here | NO |
| `OBSERVABILITY_LIMIT` | required evidence is unavailable at the lawful relation/source ceiling | NO |
| `INTEGRITY_FAILURE` | exact identity/hash/replay/closure failed | NO |

Exact internal reason codes should refine these public states without inventing a universal ontology of every future blocker.

### Relation-state independence

A FIELD FORGE relation may itself carry `OBSERVED_ZERO`. That is not admission denial. The target-use rule may lawfully admit zero evidence if it is structurally meaningful for that exact use.

Likewise, an upstream positive relation does not guarantee `ADMITTED`; missing target-use authority still blocks.

This yields the required noncollapse:

`RELATION_EVIDENCE_STATE != ADMISSION_DECISION_STATE`.

## 7. Positive admission gate

A positive result requires all applicable gates to pass:

1. relation identity/content/replay closure exact;
2. relation family/schema allowed by the exact rule;
3. relation evidence state allowed by that target-use rule;
4. target use exactly matches;
5. relation scope/universe/risk-set is allowed;
6. participant role/cardinality/order/multiplicity constraints satisfied where meaning-bearing;
7. relation permission permits the target use;
8. all exact claim-required measurement/estimand/weight/PRA/TTAR/source-relation authority present;
9. all exact map/comparator/falsifier/transport authority present when the operation crosses contexts;
10. no binding negative/denial/noncomparability/observability condition defeats the use;
11. upstream information-loss declaration is sufficient for the requested use under the exact rule;
12. target semantics are not a current-blocked strong noun absent a separate owner;
13. admission authority/rule is exact, positive, current for that operation and content-hash bound.

Only then is `ADMITTED` lawful.

## 8. Permission and target-use law

An admitted relation is not generally admitted “into PRE-V3.” It is admitted only for one exact target use.

Required relation:

`admitted_permission = relation_permission ∩ admission_rule_permission_for_target_use`.

Any attempt to widen permission is `INTEGRITY_FAILURE` or an equally exact fail-closed result in implementation.

Target use must be content-addressed/exact. The evaluator must not accept mutable strings such as `latest`, generic `default`, nearest matching or implicit consumer selection.

The admission receipt should retain both:

- exact `target_use_ref`;
- exact requested downstream owner/contract family.

This lets later M1/V554 code verify it is the intended consumer without the admission service deciding M1's own semantics.

## 9. Information-loss law

The relation admission is semantically additive but information-reference-preserving:

`ADMISSION_LOCAL_INFORMATION_LOSS = NONE__REFERENCE_PRESERVING`.

The receipt adds a decision and permission binding; it does not transform relation content.

The relation's upstream information-loss declaration remains first-class. If the requested target use needs information not represented by the relation, no admission rule may simply declare the missing information present. The rule must either prove the relation is sufficient at that target-use grain or return the exact blocker.

Therefore:

`ADMISSION_AUTHORITY != INFORMATION_CREATION_AUTHORITY`.

## 10. Provenance and replay

The future receipt should be content-addressed over a canonical semantic projection containing at minimum:

- receipt contract id/version;
- exact relation ref;
- exact relation owner/rule refs;
- exact admission authority/rule refs;
- exact historical current-selection/authority snapshots used;
- exact relation typed state;
- exact target-use ref/downstream owner;
- exact output permission subset;
- exact dependency and blocker refs;
- exact upstream information-loss declaration;
- decision state/reason code.

Replay pins historical authority. A later superseding rule does not rewrite the prior receipt.

Repository presence, carrier persistence or successful reconstruction supplies no permission by itself.

## 13. Temporal / route / higher-order nonactivation

The relation-admission surface does not itself activate V553, V555 or V556.

- V553 activates only if the selected target use needs new temporal/comparability meaning beyond preserved relation prerequisites.
- V555 activates only if a mediation route is required.
- V556 activates only if higher-order relation/topology semantics are separately required.

For the intended first weak positive thread, `NO_V555_ROUTE` and `ZERO_V556_OBJECTS` remain lawful defaults unless the chosen relation proves otherwise.

## 14. Strong-noun firewall

A neutral FIELD FORGE precursor cannot become a strong structural noun through admission alone.

The admission rule must return `BLOCKED_EXPLICIT_AUTHORITY` when the requested target use asserts any currently unowned strong noun at a grain not separately authorized.

Where the source/relation cannot even observe the premise needed to pose that target use, the narrower `OBSERVABILITY_LIMIT` is appropriate.

`BLOCKED != FALSE` remains binding.

## 5. D04 — channel fusion, driver scalarization, and vector normalization

The conceptual lineage supports WVS/Hofstede/colonial inputs feeding a driver vector, but no accepted formula currently governs family fusion or channel-to-driver scalarization.

Two evidence-supported architecture choices remain:

1. `DRIVER_LOCAL_FUSION_WITH_FIXED_DECLARED_RULE`
   - transform channels into a declared scale for the target driver;
   - combine only within that driver using fixed owner-authored coefficients/rules;
   - preserve source/family identity as channel provenance;
   - never renormalize surviving channels because other channels are unavailable.

2. `FAMILY_SUBSCORES_THEN_DRIVER_WITH_NEW_EXPLICIT_FAMILY_RULES`
   - first build WVS/Hofstede/colonial family subscores;
   - then fuse family subscores into each driver;
   - requires new explicit family-level transforms, weights, missingness, and normalization law.

A separate scalarization question must also be explicit:

- `COMPLETE_DECLARED_NUMERIC_REQUIREMENTS_ONLY`: if the declared numeric sufficiency condition for a driver is not met, the driver remains typed no-numeric;
- `PARTIAL_FIXED_WEIGHT_SCALARIZATION`: permit a driver scalar from a proper subset of intended channels while keeping original coefficients and carrying exact missing coverage.

What is forbidden is availability-based reweighting.

**RECOMMENDATION — not authority**

Choose driver-local fusion for R1. Do not introduce family-level subscores until there is a concrete modeling reason. Prefer complete declared numeric requirements for each driver unless HQ deliberately chooses partial fixed-weight scalarization; this avoids making absence numerically depress or inflate a driver while pretending the driver is complete.

No cross-driver min-max normalization should be inferred merely because the legacy runtime called its input `normalizedDrivers`.

**Deferral**

The family-subscore architecture is deferrable if driver-local fusion is selected. The R1 driver scalarization rule is not.

## 7. D06 — claim ceilings and requiredness

Generic OBL063 already freezes the available claim ceilings:

- `POPULATION_STATISTIC`
- `SOURCE_LOCAL_STATISTIC`
- `SUPPORTED_COMPONENT_ONLY`

PRE553/source authority owns how strong the evidence actually is. The model owner owns how strong a claim the terminal use demands. The model owner may demand less than the evidence can support; it may not demand more and thereby upgrade the source.

The recovered schema calls the 103 references proxies. A proxy listing alone does not establish that each proxy is constitutive or runtime-required.

**RECOMMENDATION — not authority**

- Do not require `POPULATION_STATISTIC` merely because a driver is country-scoped. Use it only where the terminal semantic claim actually requires a population estimand.
- Where the intended use is legitimately source-local, bind `SOURCE_LOCAL_STATISTIC` and preserve the existing no-population-generalization limits.
- Use `SUPPORTED_COMPONENT_ONLY` only when the model use is explicitly component-level.
- Treat recovered proxy channels as optional unless the owner explicitly identifies a channel as constitutive of that driver.

This is the choice that most directly preserves the purpose of OBL063: application runtime need not wait for universal full-source population certification, but it also cannot launder source-local evidence into a population claim.

**Deferral**

Not for active R1 channels. Later population-certification overlays may upgrade admissible uses without regenerating source-local evidence.

- `VERSIONED_MODEL_PRIOR`

The generic requirements remain binding:

- omission creates no numeric value;

No production model-prior or per-driver fallback manifest was recovered.

**RECOMMENDATION — not authority**

## 9. D08 — typed-no-numeric dimensionality and downstream behavior

The project already has two strong architectural signals:

- generic OBL063 exposes `ADMISSIBLE_TYPED_NO_NUMERIC_CONTRIBUTION` and deterministic coverage receipts;
- PRE553 component-vector machinery uses an explicit governed dimension set rather than an anonymous variable-length list.

**Admissible evidence-supported options**

1. `FIXED_DECLARED_DRIVER_SLOTS_WITH_TYPED_STATE`
   - every active driver dimension remains present by identity;
   - its state is numeric, typed no-numeric, or blocked;
   - no-numeric is never serialized as numeric zero;
   - missing drivers do not cause driver→type weight renormalization;
   - output carries exact driver coverage/missingness.

2. `BLOCK_ON_ANY_NONNUMERIC_DRIVER`
   - preserve a full numeric vector requirement and block type construction whenever any active dimension cannot be numeric.

Variable-length numeric omission is not recommended because it erases which declared dimension is absent and makes positional semantics unstable.

A terminal all-missing guard is also required. If no active driver has a numeric contribution, driver→type normalization must not emit a seemingly meaningful uniform softmax or a min-max artifact from absence.

**RECOMMENDATION — not authority**

Choose fixed declared typed slots. Permit partial numeric coverage without renormalizing driver weights, carry the exact coverage receipt/mask, and require at least one numeric active driver before type normalization. Any stronger minimum-coverage threshold can be versioned later.

**Deferral**

The dimensionality law itself cannot be deferred. A stricter threshold above “at least one numeric active driver” can be deferred.

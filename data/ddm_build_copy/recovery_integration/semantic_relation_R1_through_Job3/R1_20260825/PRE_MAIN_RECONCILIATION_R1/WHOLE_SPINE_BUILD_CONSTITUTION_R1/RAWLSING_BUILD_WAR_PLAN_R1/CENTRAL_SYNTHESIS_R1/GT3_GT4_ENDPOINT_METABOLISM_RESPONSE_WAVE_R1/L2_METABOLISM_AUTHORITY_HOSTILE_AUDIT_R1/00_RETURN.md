- `operation_version`;
- `operation_content_hash`.

It then defines that hash as:

`LOWERCASE_SHA256_OVER_CANONICAL_SEMANTIC_ENTRY_MATERIAL`.

But the candidate never defines the canonical semantic **projection** of an operation entry.

Because `operation_ref` is itself a required field of the entry, the literal full-entry interpretation is self-referential:

`operation_content_hash = SHA256(entry containing operation_content_hash)`.

The repository's existing content-addressing law avoids this problem by defining a semantic projection first and keeping identity/hash material outside that hashed projection.

A future implementation therefore has to invent at least one of these unstated laws:

- exclude all of `operation_ref` from the hash;
- include operation ID/version but exclude only `operation_content_hash`;
- hash a second unnamed projection;
- hash the full entry and somehow require an impossible digest fixed point.

Those alternatives are not semantically equivalent.

Implementation-local choice is forbidden.

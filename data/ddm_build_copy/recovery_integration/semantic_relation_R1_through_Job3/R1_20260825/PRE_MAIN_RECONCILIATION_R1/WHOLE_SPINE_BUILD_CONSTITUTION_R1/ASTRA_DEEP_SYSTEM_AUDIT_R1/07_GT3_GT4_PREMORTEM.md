# GT3/GT4 pre-mortem

The current public V3 terminal is a real protection. It is also a boundary condition that will cease to make upstream ambiguity harmless once a separately accepted positive owner exists. This file names prerequisites; it does not design GT3/GT4 or authorize a positive event.

## Five plausible classes of future escaped mistake

| Future failure class | Evidence already present | Plausible failure once positive effects exist | Required precondition |
|---|---|---|---|
| 1. A validated identity outlives the body it validated | ASTRA-001: nested aliases alter sealed source incidence; both queries still return SUPPORTED. | A later actor decision cites unchanged historical source refs whose meaning has drifted, especially through a validation cache. | Deep immutability or authenticated reads; distinguish source truth from cached claims; same-ref replay proof. |
| 2. A new composition omits the only operation-authority check | ASTRA-002: shared I03 accepts family/source-unfit ALLOW; shared relation adapter accepts REVIEW. | A new owner or adapter treats a valid structural object as already authorized for its operation. | Scope-fitted authority at shared operation boundaries; no reliance on provenance or generic ALLOW as a grant. |
| 3. Synthetic tests miss the ordinary serialized representation | ASTRA-003: exact current query representation fails the public target condition while active focused tests pass. | A real positive invocation fails or is patched around using a private path whose missing validation becomes permanent. | Authentic ordinary-object public-entry tests; negatives must reach the intended check; preserve exact current identity. |
| 4. A delegation receipt is mistaken for per-invocation causal permission | ASTRA-004: internal test-only positive decisions are identical for distinct sources; public guard safely denies. | Positive decisions get reused across evidence, actor or replay context, or zero counters are mistaken for observed state invariance. | Accepted owner contract binding exact invocation and applicability; actual effect/rollback/retry tests. No present public positive leak is demonstrated. |
| 5. Dependency and negative-blocker roles disappear between packaging and use | ASTRA-006: metadata-role/checksum ownership is not fully specified in the bounded slice; builder and resolver checks are sound. | A future consumer promotes opaque provenance into an execution prerequisite while omitting a negative dependency. | Audit one actual accepted codec and first consumer; specify opaque evidence versus required/negative dependencies. Current reachable violation is unproved. |

These classes are ranked hypotheses about failure mechanisms, not predictions or five additional defects. Class 5 remains an open question precisely because current constructor and itemwise resolver controls are counterevidence.

## Conditions before the first positive event

1. Dispose ASTRA-001 and ASTRA-002 at their actual shared boundaries; preserve accepted empirical, relation and permission meaning.
2. Separately accept the positive owner's authority and the exact invocation contract. A source class or object-family label cannot establish the applicability of a specific source body to a specific actor/operation.
3. Bind evidence identity, authority/adoption, owner identity/version, actor, operation, and replay/idempotence context where the accepted owner performs the transition. Whether the binder resides before the owner or inside it is an implementation choice; its acceptance and proof are not optional.
4. Observe real actor, ledger, cursor, RNG and scheduler state for denied, delegated, duplicate, retried and partially failed invocations. The pure guard's returned zero fields and unchanged supplied fingerprints prove only the pure guard path.
5. Resolve dependency-role ownership from ASTRA-006. Preserve CONTEXT as structural availability and require a new accepted causal boundary before it participates in positive transition.

[_presentation_matches](https://github.com/maidiu/rawlsing/blob/abd0b5ff2ffcf235b67140641f88cc61ca45c12c/rawlsing_next/v3_psepf_zero_positive_guard.py) already binds authority/owner presentation, operation and surface. The internal source-class checks are useful. They do not establish source-content applicability, and GuardDecision does not retain source_ref/source_hash. The public entry uses the immutable empty registry and cannot be overridden by the caller. The existing separation therefore survives: **DELEGATE is not EXECUTE**, and **V558 resolution is not positive authority**.

The single dangerous assumption is that a receipt from a currently harmless zero-effect path is already sufficient authorization for a future stateful path. HQ should require a new accepted proof at the first effectful boundary, without allowing that future work to retroactively promote GT1/GT2 evidence.

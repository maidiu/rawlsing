# VMESTYE — RETURNS, RECEIVING AND CONTINUOUS RECONCILIATION
## No orphan reports
Every returned investigation is a **candidate assertion set**, not automatically a change to VMESTYE's canonical functional status. It must supply:
- exact startup/head, branch, source cuts, available host/runner and what actually ran versus did not;
- FINDING, INTERPRETATION, ACTION, accountable OWNER, uncertainty/alternate explanation;
- original and current function IDs (or explicit unresolved join), exact old and current source/call/authority evidence;
- human explanation: `input X → operation Y [authority] → output Z → so that consumer Q`;
- positive and typed negative, missing first edge, proposed status at exact scope, falsifier and responsible independent reviewer;
- full no-drop counts against assigned membership and exact residuals; output files/paths, hashes and changed files.

## Prong write-through
Each worker writes only to its assigned `PRONGS/<owner>/` (or isolated branch corresponding to that location). The RETURN and stable row references stay there. Integrator ZL-15 is the **only candidate writer** of normalized `DATA/FUNCTION_ATLAS.tsv`, `DATA/RELATIONS.tsv`, `DATA/OPERATION_TRACES.tsv`, `DATA/AUTHORITY_APPLICATIONS.tsv` and final human story; this prevents rival status sheets.

## Admission transaction
**1. RETURNED:** record SHA, files, worker-scope count and all negatives in CONTROL. **2. INDEPENDENT RECEIVE:** correct competent reviewer verifies exact head, actual sources, grader, no-drop, representative raw code first-consumer trace, false green, duplicate/stranded/negative conservation. **3. ADJUDICATE:** accept, revise, reject or hold with precise changed rows. **4. CROSSWALK:** update canonical normalized graph, backlink to original prong event and PROGRAMMA owner IDs. **5. VALIDATE:** uniqueness, coverage, link/edge/grain and status-proof assertions; no invalid green. **6. CURRENTNESS:** if protected code changed during review, new exact-current observation required; previous acceptance remains historical proof, not automatic present acceptance. **7. RECIPROCAL ADMISSION:** only qualified Pyat/PRE-MAIN owner changes operative PROG5 status/current progress or merges to protected.

## Conflict-resolution court
Conflict key: exact old function/grain, current requirement/consumer, source/authority version and cut. Two contradictory statements need adjudication at common cut, or must remain separate `CONFLICT_PENDING` events. Never edit a historical negative to manufacture consistency. Differences in physical carrier, issuer, source rights or original execution grade are **not** cosmetic.

## Event-sourced decisions (simple Git files, no daemon)
Every accepted change adds an evidence/decision event: event ID, covered function/operation/authority IDs, previous state, new state, source cut, prong return SHA, reviewing authority, material change, falsifier and linked Pyat receiving. The master status is the current **view** derived from accepted events, not an overwrite of the originals. Git history plus a flat `DATA/DECISION_EVENTS.tsv` suffices; no new database is required.

## Failure/partial success is deliverable
`REVISE`, `NOT_RUN`, `OPEN_PROOF_GAP`, `OPEN_FUNCTIONAL_GAP`, `NO_CURRENT_CONSUMER`, `HELD_ISSUER` and `BRANCH_STRANDED` are positive knowledge states when properly sourced. Do not require a worker to fabricate success to complete a prong. A prong completes its assignment when it records **all** cases, including exact open IDs and next accountable steps.

## Independent final receiving
ZL-16 audits historical→current, ZL-17 current terminal→historical/authority. Neither authored the atlas or the prong findings. They must pass at least five cold human navigation scenarios from VMESTYE's intro, exact anti-joins, selected rule vs snapshot distinction, branch-only status and nonnative qualification boundaries. ZL-15 corrects review defects; the corrected head requires independent recheck. User/qualified PRE-MAIN owner finally authorizes protected documentation receiving.

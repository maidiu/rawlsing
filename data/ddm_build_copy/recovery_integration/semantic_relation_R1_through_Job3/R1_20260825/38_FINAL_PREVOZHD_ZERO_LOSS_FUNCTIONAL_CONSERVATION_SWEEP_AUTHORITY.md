## Binding terminal ledger

Every historically meaningful function or engineering choice discovered by any lane MUST end in exactly one terminal disposition:

1. `PROVED_CURRENT_SUCCESSOR`
   - same or stronger semantic function exists in current PRE-V3;
   - exact current code/object/authority ref exists;
   - exact current test/receipt or executable proof exists.

2. `PROVED_STRONGER_SUPERSESSION`
   - old mechanism is intentionally absent because a current mechanism performs the same valuable function at equal or stronger grain;
   - the proof must identify the old function, the stronger successor, and the exact equivalence/strengthening argument.

3. `OPEN_FUNCTIONAL_GAP`
   - valuable function is not currently proved conserved.

4. `HISTORICAL_HEURISTIC_ONLY`
   - historical choice was one implementation/policy heuristic, not binding conceptual capital; any surviving function must be separated from the old numeric/algorithmic choice.

5. `ACCIDENTAL_OR_OBSOLETE_MECHANIC`
   - mechanism existed historically but carried no independently valuable semantic/engineering function after controlling for its purpose.

6. `DUPLICATE_OR_ALIAS`
   - function is already represented by another ledger row at the same semantic grain; exact alias relation required.

No other terminal status is allowed.

## Strong proof law

A row may be `PROVED_CURRENT_SUCCESSOR` only if all three are present:

`CURRENT_SEMANTIC_OWNER + CURRENT_IMPLEMENTATION + CURRENT_TEST/RECEIPT`

A surviving documentation file alone is not enough.
A schema field alone is not enough.
A branch-local implementation not adopted into an accepted/current lineage is not enough.
A current ability to represent a fact is not enough if the old function autonomously generated/selected/composed that fact.
A generic carrier that can physically hold information is not proof of the semantic function that interprets or governs it.

## 2. PHASE P0 — ARCHITECTURAL NECESSITY

### 2.1 C01, C02, C06, C07 launch relation

These four cells MAY run in parallel after campaign launch because they attack different first-principles burdens:

- `C01`: what the finished runtime actually consumes;
- `C02`: what C11 information truly requires persistence;
- `C06`: what identity/replay/integrity truly requires persistence;
- `C07`: what the permanent compiled structural destination must be.

However each must read the same Governing Vision Constitution and whole-machine closure.

### 2.2 P0 return acceptance

A P0 worker is not `ACCEPTED` merely because files exist. HQ must verify:

- branch/start-point correctness;
- read-first authority compliance;
- no runtime mutation;
- exact write-scope compliance;
- complete required outputs;
- complete `VC4_TERMINAL_VISION_CHECKSUM`;
- no unresolved semantic leakage hidden as implementation detail;
- no claim that current implementation automatically defines architecture;
- no Chetiri candidate self-selection.

### 2.3 G0 synthesis inputs

HQ may adjudicate G0 only after all four P0 cells are `ACCEPTED` or an explicit blocked-cell witness itself decides the question.

G0 must synthesize:

- `C01_RUNTIME_NEED`
- `C02_INFORMATION_DERIVABILITY`
- `C06_REPLAY_INTEGRITY_NEED`
- `C07_COMPILED_DESTINATION_NEED`

### 2.4 G0 pass condition

`G0_PASS__SOURCE_BACKED_REMAINS_LAWFUL_CANDIDATE` requires all:

1. no accepted proof that permanent full event-grain materialization is semantically required for ordinary runtime;
2. every nonpersisted C11 obligation has a lawful reconstruction path or explicit sparse canonical material;
3. ExactRef/replay/integrity can remain exact without assuming a full duplicate empirical payload;
4. the intended compiled structural substrate can be specified without source evidence becoming actor fact;
5. terminal checksum has no unresolved starvation/leakage risk.

G0 does NOT prove source-backed execution is fast enough.

### 2.5 G0 block condition

Any accepted minimal proof of one of these blocks further broad source-backed exploration until HQ adjudicates:

- irreducible event-grain persistence required by C11 semantics;
- replay/integrity impossible without permanent event carrier;
- terminal runtime legitimately requires full respondent/event substrate as an ordinary production dependency;
- source-backed concept necessarily reduces lawful I03/I05 frontier;
- frozen semantic contradiction.

## 3. PHASE P1 — EXECUTION FEASIBILITY

P1 is deliberately staged rather than four-way parallel.

### 3.1 First launch C03

`C03_NATIVE_SOURCE_ACCESS` runs first.

Reason: C04/C05 must not invent assumptions about selective SAV/DTA access, chunking, reader setup, full-frame behavior or compatibility paths.

C03 must be accepted before C04/C05 execution strategy can be finalized.

### 3.2 C04 and C05 launch after C03

After C03 acceptance:

- C04 and C05 MAY run in parallel;
- both must consume accepted C01/C02/C03/C06/C07 findings;
- C04 owns I03 execution feasibility;
- C05 owns I05 execution feasibility;
- neither may redesign I03/I05 semantics.

### 3.3 C08 launch timing

C08 may begin after C02/C06/C07 are accepted, but its final return may not close until C03/C04/C05 returns are available because invalidation/rebuild granularity depends on actual execution strategy.

Preferred launch: after C03 acceptance, parallel with C04/C05, with a mandatory final reconciliation against both.

### 3.4 G1 pass condition

HQ may pass G1 only when it can state an exact execution model for every required compiler primitive and classify each execution structure as authoritative, regenerable, transient or unnecessary.

Allowed high-level G1 outcomes:

- `SOURCE_BACKED_EXECUTION_FEASIBLE_WITHOUT_MANDATORY_FULL_MATERIALIZATION`
- `HYBRID_SOURCE_AUTHORITY_WITH_REGENERABLE_ACCELERATION_REQUIRED`
- `PERSISTENT_FULL_MATERIALIZATION_REQUIRED_FOR_NAMED_CAPABILITY`
- `INSUFFICIENT_EVIDENCE`

No architecture is selected at G1.

## 7. WORKER STATE MACHINE

Every cell uses exactly:

`PLANNED -> READY -> LAUNCHED -> ACTIVE -> RETURNED -> HQ_REVIEW -> ACCEPTED | REJECTED | BLOCKED`

Optional terminal states:

- `SUPERSEDED_BY_EXACT_EVIDENCE`
- `NO_ACTION_REQUIRED`

A worker may not mark itself `ACCEPTED`.

`RETURNED` means only that the worker has stopped and submitted evidence.

## 8. BRANCH LAW

Each cell receives a dedicated branch named in `04_WORKER_REGISTRY.csv`.

At launch HQ records:

- exact control-branch launch SHA;
- exact branch name;
- exact write scope;
- exact read-only runtime boundary;
- exact raw-source authorization, if any.

Workers may not merge, rebase, retarget or absorb sibling returns unless HQ explicitly reissues the order.

Later-phase workers consume earlier returns only from HQ-accepted commits or exact pins named by HQ.

## 9. RETURN HANDOFF LAW

Every worker return must state:

- branch;
- exact starting SHA;
- exact return SHA;
- changed files;
- authority files actually read;
- raw sources probed and exact SHA, if any;
- runtime files inspected;
- runtime files modified (`NONE` unless separately authorized);
- required-output completeness;
- terminal checksum status;
- exact final disposition;
- unresolved named evidence;
- explicit STOP token.

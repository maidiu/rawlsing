# R2-06 MINIMUM ONE-RUNNER CONTRACT

Status: `DESIGN_ONLY__REPRESENTATION_NEUTRAL__NO_RUNTIME_AUTHORITY`

## Objective

One runner must be sufficient to compare every authorized physical organization without moving any semantic law and without giving a candidate a favorable bespoke court.

The runner is a **shadow acceptance instrument**, not production serving infrastructure. It must remain small enough that it does not become a second query architecture.

## Inputs frozen before candidate results

The runner receives exact immutable inputs:

```text
candidate_id
candidate_commit
candidate_organization in {
  LONG_SHARDED,
  QUESTION_BLOCKED_LONG,
  HYBRID_DENSE_PLUS_EXPLICIT
}
candidate_physical_config
candidate_tuning_disclosure_hashes
exact_source_manifest / source SHA set
frozen decoder configuration identities
frozen source/C11/I03/I05/I04/whole-machine authority frontier
R02 accepted FD/geometry/type certificates applicable to the candidate
R03 oracle contract + hostile corpus + late-bound blind-frontier seed protocol
resource hard/preferred boundaries
HQ-frozen practical runtime boundaries
integrity/publication contract version
hostile replay selection
```

No `latest`, source-family default, mutable path, inferred weight, inferred routing, inferred relation, or candidate-reported semantic digest is accepted as authority.

## Candidate adapter boundary

Each physical implementation may provide only the minimum adapter needed to expose:

```text
build_from_governed_decoder_batches(...)
seal_shadow_release(...)
reopen_exact_root(...)
iter_or_resolve_carrier_neutral_C11(...)
stream_full_audit(...)
canonical_scan_for_exact_predicate(...)
```

The adapter may expose execution capabilities such as projection pruning or dense block availability to an internal planner. It may not expose source family/profile as semantic input to I03/I05/I04 or the independent oracle.

## Phase 0 — branch / authority freeze

Fail before source work unless:

- candidate commit is exact;
- source manifest and every source digest are exact;
- decoder/source authority identities match the frozen court;
- C11/I03/I05/I04 and whole-machine pins match;
- candidate tuning disclosure is frozen;
- resource and practical-runtime boundaries are already recorded;
- optional caches/indexes are declared explicitly;
- organization/config/profile count is declared.

Receipt: `AUTHORITY_FREEZE_RECEIPT`.

## Phase 1 — exact source / decoder open

For each exact source in scope:

1. verify content digest;
2. open only the frozen governed decoder path;
3. record reader/config receipt;
4. expose bounded physical batches;
5. forbid source-family semantic inference in candidate compiler.

The runner does not redo broad source reconnaissance. It validates the exact inputs needed by the candidate court.

Receipt: `SOURCE_OPEN_RECEIPT`.

## Phase 2 — cacheless serial bounded build first

Every organization must first build with:

```text
persistent_cache_count = 0
worker_count = 1
bounded_batching = true
bounded_sort_merge = true where needed
no serving publication
```

This isolates organization cost from caches and parallelism.

The runner records continuously:

- peak process-tree RSS, including backend state;
- scratch/staging bytes;
- authoritative bytes written;
- member count/size distribution;
- open-file high water if available;
- decoder rows/cells and logical event count;
- build wall time;
- fallback/invariant-validation counts;
- number of physical schemas/profiles used.

Failure to remain bounded is a candidate failure, not a request to increase workstation limits.

Receipt: `BUILD_RECEIPT`.

## Phase 3 — seal / publication mechanics in shadow mode

The candidate builds one immutable non-serving root:

```text
UNIQUE_STAGING
-> COMPLETE_AUTHORITATIVE_MEMBERS
-> SEMANTIC/INVARIANT_PRESEAL_CHECK
-> ROOT_AND_WHOLE_MEMBER_HASH_SEAL
-> FULL_STAGED_VERIFY
-> CONTENT_ADDRESSED_PROMOTE_AS_INACTIVE
-> SEALED_REOPEN_VERIFY
```

Because this is a shadow court, the runner **does not activate production serving state**. It tests active-selector CAS semantics using isolated test control state/fault injection only.

Minimum root binds:

- semantic release identity;
- physical root identity;
- source/decoder/compiler/schema/config/authority/replay determinants;
- authoritative member roles, lengths, hashes;
- exact coverage/member inventory;
- organization/config descriptor as execution metadata.

Merkle/chunk metadata is absent unless that mechanism is the specific candidate under court.

Receipt: `SEAL_PUBLICATION_RECEIPT`.

## Phase 4 — reopen and one C11 boundary

Open the sealed shadow root through exactly one invariant-checked carrier-neutral C11 facade/materializer.

Hard rules:

- no direct I03/I05 access to physical rows/blocks as semantic facts;
- no source-family semantic branch;
- no second fast constructor that skips C11 invariants;
- no eager corpus-sized Python materialization;
- exact-key/no-fallback object and release resolution;
- canonical semantic hashes/ExactRefs independently recomputable.

Receipt: `REOPEN_C11_RECEIPT`.

## Phase 5 — independent R03 source/C11 oracle

The runner invokes the independent oracle lanes rather than candidate-reported parity:

### O1 source-native lane

Check the accepted hostile physical/source witnesses required for candidate scope, including rare source-family exceptions.

### O2 C11 lane

- enumerate full expected/observed logical object/record ref multisets;
- independently recompute canonical projections and hashes;
- require M01-M18 closure;
- check sensitivity cases where a one-field mutation must change identity/outcome;
- check invariance under physical relayout.

The candidate's own materializer may provide observed objects. It may not compute expected truth.

Receipt: `INDEPENDENT_EQUIVALENCE_RECEIPT`.

## Phase 6 — I03 exact court

Execute the same frozen suite for every organization, including at minimum:

- scalar positive/negative cases;
- arbitrary AND/OR/NOT;
- pair and k-way joints;
- high-cardinality/string predicates;
- routing/risk-set states including unresolved/nonmember/inapplicable;
- typed semantic/physical missingness counterexamples;
- governed weighted/design/estimand cases;
- repeated/ranked/component/MR targets;
- multi-universe/source-relation cases;
- valid-empty, observed-zero, zero-support, zero-overlap, noncomparable, integrity failure distinctions.

The independent set/incidence evaluator compares respondent membership/support where applicable.

Receipt: `I03_RECEIPT`.

## Phase 7 — I05 declared + blind open-world court

After candidate commit/config/tuning disclosure are frozen:

1. record deterministic nonce;
2. compile exact blind frontier not present in tuning disclosure;
3. include uncached high-cardinality/string, 3+ conjunction, NOT/routing, reversal/Simpson, recursive, branch-conditioned, co-signature/cloud-like cases across multiple physical blocks;
4. delete every optional accelerator before the dispositive run;
5. evaluate every candidate;
6. require `candidate_count == covered_candidate_count`;
7. compare exact facts/receipts with frozen I05 plus independent finite set/incidence checks.

If an unseen candidate requires re-ingest, source-specific code, or a prebuilt bitmap, the candidate organization fails.

Receipt: `I05_BLIND_RECEIPT`.

## Phase 8 — I04 court

Run positive and every frozen nonpositive admission class plus multi-blocker precedence cases.

Physical organization/profile/cache state is absent from I04 semantic inputs.

Receipt: `I04_RECEIPT`.

## Phase 9 — replay / source reconstruction

For deterministic selected hostile events/objects:

- reconstruct source snapshot and row/variable coordinates;
- verify raw value and physical state/declaration;
- verify topology/order/rank/component/multiplicity;
- verify routing/weight/coordinate/source-relation/authority/replay dependencies as applicable;
- compare to frozen source-native/C11 witness.

Selection includes rare exceptions, not only ordinary scalar events.

Receipt: `REPLAY_RECEIPT`.

## Phase 10 — cache ablation court

The dispositive organization run has all optional caches absent.

If a candidate later proposes one cache for a separately frozen serving-latency objective:

1. build cache from verified canonical root;
2. rerun selected I03/I05 suite;
3. delete cache completely;
4. rerun exact same suite;
5. inject stale cache from another root/config;
6. corrupt cache bytes;
7. require identical semantic outputs/coverage in all states.

Cache failure only changes speed or triggers discard/rebuild. Canonical corruption may never fall back to cache.

Receipt: `CACHE_ABLATION_RECEIPT` or `NOT_APPLICABLE`.

## Phase 11 — integrity / corruption / publication court

Baseline injections:

- root manifest bit flip;
- missing/truncated/swapped member;
- stale ExactRef/content hash;
- source/compiler/authority determinant mismatch;
- partial staging visibility attempt;
- promoted-but-inactive root;
- active-selector CAS race/failure in isolated control state;
- canonical corruption while cache is healthy;
- stale/unauthorized valid root;
- post-promotion automatic fallback attempt.

Required result: no plausible empirical output from failed canonical integrity/publication state.

If chunk/Merkle is under court, add chunk transplant/reorder/TOCTOU/query-closure attacks; otherwise do not burden the baseline with that machinery.

Receipt: `INTEGRITY_PUBLICATION_RECEIPT`.

## Phase 12 — determinism / relayout metamorphic court

Rebuild the same logical material with permitted changes:

- temp path;
- batch size;
- shard/block grouping;
- row-group size/compression level where incidental;
- filesystem enumeration order;
- Python hash seed;
- worker count only if parallelism is an admitted mechanism;
- cache absent/present if a cache is under court.

Require identical semantic release identity, canonical C11 projections/refs/hashes, I03/I05/I04 receipts, replay semantics, and source reconstruction.

Physical root may differ only where the physical-byte profile is explicitly non-byte-reproducible; such difference is visible and never changes semantic identity.

Receipt: `DETERMINISM_RECEIPT`.

Receipt: `RESOURCE_COMPLEXITY_RECEIPT`.

## Phase 14 — organization decision

Apply `ORGANIZATION_DECISION_LAW.md` exactly.

No weighted score. No percentage beauty contest.

Decision order:

1. any semantic/source/oracle mismatch -> reject candidate;
2. any integrity/publication/replay fail-open -> reject candidate;
3. any unbounded-memory failure -> reject candidate;
4. any hard absolute resource boundary failure -> candidate insufficient;
5. any required pre-frozen practical-runtime boundary failure -> candidate insufficient;
6. if all boundaries pass -> candidate sufficient;
7. choose the first sufficient organization in the authorized escalation order and stop.

Receipt: `ORGANIZATION_DECISION_RECEIPT`.

## Atomic final receipt

A candidate can be recommended only if one immutable acceptance bundle binds every phase receipt plus exact code/input/config identities.

Suggested logical envelope:

```text
POST_R4_CARRIER_ACCEPTANCE_RECEIPT
  authority_freeze
  source_open
  build
  seal_publication
  reopen_c11
  independent_equivalence
  i03

  cache_ablation_or_na
  integrity_publication
  determinism

```

No earlier receipt authorizes production serving. Runtime implementation/adoption remains HQ authority after Round 2.

## Runner minimality law

The runner itself must not become another storage/query architecture. It may contain:

- bounded orchestration;
- exact receipt generation;
- small independent R03 canonical/hash/set evaluator;
- deterministic blind-frontier compiler;
- fault injection;
- candidate-neutral comparisons.

It must not contain:

- a second production empirical database;
- a full alternate query engine;
- source-family semantic rules;
- candidate-specific semantic adapters;
- persistent benchmark caches required for correctness;
- auto-tuning that changes the court after results are observed.

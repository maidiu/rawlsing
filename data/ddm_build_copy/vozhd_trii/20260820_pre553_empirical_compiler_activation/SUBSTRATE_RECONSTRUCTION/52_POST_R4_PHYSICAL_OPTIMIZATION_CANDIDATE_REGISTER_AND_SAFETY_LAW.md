## 0. ABSOLUTE PURPOSE

The purpose of optimization is:

> **make the exact same Rawlsing empirical reality cheaper to carry, compile, verify, reconstruct and query.**

The purpose is NOT:

- to simplify Rawlsing by deleting information;
- to reduce the query/discovery frontier;
- to weaken provenance or replay;
- to replace exact respondent-grain incidence with aggregates;
- to convert unknown/absence/noncomparability into convenient defaults;
- to introduce source-family semantics into downstream stages;
- to bypass authority because source-native physical data is inconvenient;
- to trade whole-machine capability for benchmark performance;
- to reopen already-closed semantic architecture merely because a physical implementation is inefficient.

The controlling maxim is:

> **NO OPTIMIZATION EARNS EVEN ONE BYTE OR ONE SECOND BY WEAKENING RAWLSING. EVERY GAIN MUST COME FROM ELIMINATING PHYSICAL REDUNDANCY, PYTHON OBJECT OVERHEAD, UNNECESSARY MATERIALIZATION, UNNECESSARY I/O, OR UNNECESSARY COMPUTATION.**

## 5. SELF-INTERROGATION LAW

Before proposing, implementing or accepting an optimization, Vozhd and worker must answer all of the following explicitly.

### 5.1 Hidden-assumption interrogation

- What functional dependency am I assuming?
- Is that dependency proved by authority/source structure, or merely common in surveys?
- Is it true for every source governed by this implementation, or only WVS/LiTS?
- Does it fail on repeated, ranked, multiple-response, string, date, mixed-type, missing-range, routed or malformed-native cases?
- Am I assuming rectangularity where the semantic substrate does not require rectangularity?
- Am I assuming variable names are unique/stable when only variable ordinal/source position is guaranteed?
- Am I assuming decoder ordering is immutable without a frozen order law?
- Am I assuming a physical state is semantically missingness?
- Am I assuming a value label is merely presentation when some later authority may need it?
- Am I assuming a field is derivable because it happened to be derivable in a proving source?

### 5.2 Capability-interrogation

- Which I03 queries become cheaper?
- Which I03 queries become more expensive?
- Does the design still support arbitrary authorized respondent-level conjunctions?
- Does question-oriented storage harm respondent-oriented or topology-oriented operations?
- Does a proposed bitmap/index cover only known query shapes and silently starve future lawful predicates?
- Does the design preserve enough raw incidence for I05 to discover patterns not imagined at design time?
- Am I optimizing storage at the expense of autonomous discovery?
- Am I making later structural interpretation depend on a physical layout accident?

### 5.3 Integrity-interrogation

- Does lazy/chunk verification weaken the current fail-closed integrity guarantee?
- Can a cache become stale while still appearing authoritative?
- Is every cache keyed to exact immutable release identity and invalidated deterministically?
- Could a partial/corrupt partition be read as valid evidence?
- Does parallelism make output identity depend on filesystem/process scheduling?
- Does physical row order become an implicit identity without explicit law?

### 5.4 Type/interchange interrogation

- Can integer narrowing overflow or alter signedness?
- Can float representation alter `-0.0`, infinities, NaNs, NaN payloads, large integer-like floats, sentinel values or exact source round-trip?
- Can dictionary/string encoding normalize Unicode, whitespace, null bytes or code points?
- Can date/time conversion alter source-native representation or timezone semantics?
- Can a decoder/native type mismatch be hidden by Arrow coercion?
- Can categorical code/value-label separation lose exact raw storage value?

### 5.5 Complexity/intervention interrogation

- Is there a simpler lower-risk fix that closes the measured gate?
- Is the proposed design solving a measured bottleneck or a hypothetical one?
- Does the gain justify new code paths, indexes, partitions, caches or invariants?
- Will future debugging become harder because the logical event is reconstructed across too many sidecars?
- Am I creating a second canonical copy under another name?
- Am I turning an optimization layer into permanent architecture debt?
- Am I continuing to optimize after the machine is already comfortably within budgets and useful runtime limits?

A candidate that cannot survive this interrogation is not ready for implementation.

## 6. CANDIDATE RISK CLASSES

Candidates are classified by the amount of semantic danger introduced by changing physical assumptions.

### CLASS A — LOW SEMANTIC RISK

Implementation mechanics change while the same physical/logical records remain explicit.

Examples:

- streaming an existing relation rather than retaining it in RAM;
- bounded merge-stream reading;
- caching immutable repeated computations;
- progress telemetry;
- Parquet batch/row-group/compression tuning that does not change logical values.

Class A still requires parity tests, but should be preferred first when it can close the measured gate.

### CLASS B — FUNCTIONAL-DEPENDENCY / TYPED-ENCODING RISK

Information is stored at a lower-redundancy grain because exact derivability is claimed.

Examples:

- move source constants to release metadata;
- move question-stable metadata to question dimension;
- derive row/question from locator;
- typed float/native lanes;
- question-level defaults + event overrides;
- narrower integer/enumeration encodings.

Class B requires explicit proof that each omitted event-level value is losslessly derivable or captured by an exact exception path.

### CLASS C — PHYSICAL-GRAIN / EXECUTION-ENGINE RISK

The persistent physical carrier or query execution model changes substantially while promising the same logical C11 interface.

Examples:

- canonical matrix/columnar incidence instead of persistent long event table;
- virtual RespondentEvent view;
- direct vectorized PhysicalCell->Arrow compilation;
- bitmap predicate algebra;
- question-oriented partitions;
- late materialization;
- source-specialized physical compilers behind one logical interface;
- chunk/Merkle integrity schemes replacing current full-member reopen behavior.

Class C is never a default next step. It requires a separate bounded comparison court against the simplest already-passing lower-risk design.

## 7. CANDIDATE REGISTER

This section preserves ideas. It does not authorize them.

### C01 — STREAM EVENT OVERRIDES DURING WRITE

Risk: `CLASS_A`

Current issue:

R4 retains event/authority/dependency override lists in Python until close.

Candidate:

- give each override relation its own bounded Parquet writer;
- flush by deterministic batch/row-group size;
- preserve event_locator ordering;
- preserve exact field/value payloads;
- never retain corpus-scale override Python objects.

Potential benefits:

- bounded memory during full-source compilation;
- lower close-time allocation spike;
- earlier durable scratch progress;
- simpler resource predictability.

Hidden dangers:

- non-deterministic ordering if writers are fed concurrently;
- duplicate locator/field overrides not detected;
- change in duplicate-resolution behavior if existing code accidentally relied on last-write-wins;
- partial relation publication if process dies.

Mandatory proof:

- exact override multiset/order law;
- duplicate hostile fixture;
- crash/partial-output invalidation;
- reconstructed logical parity;
- bounded memory at high override density.

Default priority:

`FIRST-LINE CANDIDATE IF REAL P2 CONFIRMS OVERRIDE ACCUMULATION AS RESOURCE WALL`.

### C02 — STREAM / MERGE OVERRIDES DURING READ AND AUDIT

Risk: `CLASS_A`

Current issue:

R4 reader eagerly materializes override relations into Python dictionaries.

Candidate:

- iterate fact and sorted override relations together by locator;
- maintain only bounded current override state;
- use predicate pushdown / partition lookup for exact random reconstruction;
- any optional lookup index must be regenerable and nonauthoritative.

Potential benefits:

- actual lightweight reopen;
- bounded audit RAM;
- lower Python object count.

Hidden dangers:

- unsorted/duplicate overrides;
- random lookup becoming pathologically slow;
- reconstruction changing when more than one field override shares locator.

Mandatory proof:

- exhaustive bounded reconstruction parity;
- multi-field/duplicate hostile cases;
- full audit parity;
- random exact sample latency and correctness.

### C03 — NORMALIZE SOURCE-NATIVE PHYSICAL PROVENANCE BY TRUE GRAIN

Risk: `CLASS_B`

Candidate decomposition:

Release-level constants may include, only when exactly proved:

- source SHA;
- decoder/version identity;
- execution-only authority label;
- fixed source shape/order law.

Question/variable-level metadata may include, only when exactly stable for the native variable:

- variable ordinal/name;
- native type;
- source-native missing declaration;
- value-label table/ref;
- question-level topology/default physical metadata.

Respondent-level metadata may include only respondent-stable material.

Event level retains only what actually varies by physical event, plus sparse exact exceptions.

Potential benefit:

- remove repeated JSON/provenance payload from millions of events;
- reduce override density;
- reduce disk/RAM/CPU.

Critical danger:

A value that merely looks question-stable may actually be event-dependent under a source topology or decoder behavior.

Mandatory proof:

- functional-dependency census on each source family;
- hostile exception injection;
- exact event reconstruction from decomposed grains.

### C04 — CACHE IMMUTABLE IDENTITY COMPUTATIONS DURING COMPILATION

Risk: `CLASS_A`

Candidates:

- release/universe ExactRef once per source;
- respondent ExactRef once per respondent;
- question ExactRef once per native question;
- topology refs once per topology;
- reusable authority/dependency sets once per set.

Potential benefit:

- eliminate millions of repeated SHA-256/JSON/ref constructions;
- reduce CPU and temporary allocation.

Danger:

Cache key must include every semantic input. No mutable/global `latest` cache.

Mandatory proof:

- cache-off vs cache-on identity equality;
- fresh-process deterministic replay.

### C05 — NATIVE TYPED RAW-VALUE LANES

Risk: `CLASS_B`

Candidate:

- explicit int/bool/float/string/date/native-special lanes as justified;
- avoid textual float round-trip when exact binary/native preservation is proved;
- adaptive typed storage may differ by variable/source physical type while exposing one logical value contract.

Potential benefit:

- lower storage;
- faster vectorization;
- fewer JSON/string conversions.

Critical dangers:

- float `-0.0`;
- NaN/infinity/NaN payload behavior;
- source missing sentinels;
- integer overflow/signedness;
- date/time coercion;
- Unicode/string normalization;
- native numeric representation vs Python value equivalence.

Mandatory proof:

Hostile value corpus including all source-native edge cases actually representable by the decoders. No claim that `float64` is automatically exact enough merely because Python floats are binary64.

### C06 — DERIVABLE ROW / QUESTION / EVENT LOCATORS

Risk: `CLASS_B`

Candidate:

For a sealed rectangular source with explicit traversal law:

`locator <-> (source_row_ordinal, source_variable_ordinal)`

permit deterministic derivation instead of storing redundant coordinates.

Potential benefit:

- narrower fact relation;
- faster write/read.

Critical dangers:

- decoder order drift;
- duplicate/hidden variables;
- nonrectangular/repeated structures;
- row filtering;
- physical source transformations that reorder columns;
- accidental use of Parquet physical row position as semantic identity.

Mandatory proof:

- source-order law frozen in manifest;
- bidirectional round-trip for entire bounded source;
- hostile reordered-source failure;
- no downstream dependence on incidental file order.

### C07 — QUESTION/RELATION DEFAULTS + SPARSE EVENT EXCEPTIONS

Risk: `CLASS_B`

Candidates:

- topology default;
- multiplicity kind default;
- rank/index law where source topology proves it;
- physical-state defaults only when semantically safe;

Potential benefit:

- reduce dense repeated columns.

Danger:

Mandatory proof:

### C08 — DIRECT VECTORIZED PHYSICAL COMPILER

Risk: `CLASS_C`

Candidate hot path:

`decoder batch -> typed Arrow arrays -> canonical physical carrier`

rather than one Python `RespondentEvent` object per cell.

Logical C11/RespondentEvent remains reconstructable at the boundary.

Potential benefit:

- very large ingest-throughput improvement;
- far less Python allocation;
- bounded memory.

Critical danger:

The current RespondentEvent constructor/semantic object path may be performing validation or canonicalization that a vectorized compiler silently bypasses.

Mandatory proof:

- enumerate every constructor/invariant effect before bypass;
- differential oracle against accepted object path;
- streaming semantic-hash/parity proof over bounded hostile corpus;
- no validation rule may exist only in the old object constructor after cutover.

### C09 — QUESTION-ORIENTED / COLUMNAR PHYSICAL ORGANIZATION

Risk: `CLASS_C`

Candidate:

Physically cluster responses by variable/question or question blocks rather than respondent-major long event order.

Potential benefits:

- stronger compression because one column has one type/vocabulary;

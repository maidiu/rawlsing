## 5. Logical configuration versus executable scope variant

R03 did not locate one universal materialized `scope_variant_id`, but the distinction is strongly evidenced.

A **logical configuration** is the stable semantic identity of a joint family: members, order, roles, type, completion, response/boundary semantics and authority lineage.

An **executable scope variant** is one lawful runtime instantiation after exact source/wave and any relevant country/form/module/split/routing/risk-set constraints are applied and a respondent substrate exists.

Evidence:

- Section85 registries carry stable configuration IDs plus exact source/wave eligibility.
- The current V550J compiler requires an explicit registry and activates against runtime source/wave/country context; it has no universal GSS/default family fallback.
- The current GSS draft registry describes logical families across multiple eligible waves.
- Historical routing archaeology proves that wave membership alone may be insufficient: route/form/module/risk-set authority can remain unresolved even when the family is known.

Thus “these columns exist in this source object” is not executable scope authority.

## 14. Typed negative-state law

The mature lineages repeatedly converge on one discipline: absence, non-applicability, valid emptiness, unresolved applicability, review-required evidence, permission denial, observed zero and integrity failure are distinct.

Current Section85 explicitly accepts healthy typed states including:

- `PASS / PRESENT / ALLOW`;
- `PASS / PRESENT / DENY`;
- `PASS / VALID_EMPTY / NOT_APPLICABLE`;
- `PASS / NOT_APPLICABLE / NOT_APPLICABLE`;
- `PASS / APPLICABLE_UNRESOLVED / DENY`.

A nonempty object, nonzero count or free-text readiness label is not authority. This prevents missing authority from becoming false data and prevents valid emptiness from becoming failure.

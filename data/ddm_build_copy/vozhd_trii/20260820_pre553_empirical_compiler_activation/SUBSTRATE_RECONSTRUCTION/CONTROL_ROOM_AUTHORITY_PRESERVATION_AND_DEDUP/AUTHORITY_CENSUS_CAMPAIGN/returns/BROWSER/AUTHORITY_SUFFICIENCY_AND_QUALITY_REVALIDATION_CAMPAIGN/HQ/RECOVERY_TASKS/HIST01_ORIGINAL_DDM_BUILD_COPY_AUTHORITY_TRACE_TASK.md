# HIST-01 — ORIGINAL `ddm_build_copy` AUTHORITY-CONSUMPTION TRACE

Status: `ISSUED__HISTORICAL_ROOT_TO_CONSUMER_AUTHORITY_DAG__C09_BLOCKER`

Repository: `maidiu/rawlsing`

Execution environment: full-history Git-capable repository checkout is preferred. This is repository-history archaeology, **not** survey-source archaeology. No local survey SAV/DTA files are required. No broad filesystem crawl outside the repository is authorized.

## 0. Governing question

Determine whether the authority/files/surfaces currently known to Vozhd are historically complete with respect to what the pre-Vozhd `ddm_build_copy` → Odin → Dva → Trii → Chetiri pipeline actually presumed or consumed.

Do this from the historical substrate itself, not from current authority names or the 68-TIR reconstruction.

The court must answer:

> Starting from the first committed appearance of `data/ddm_build_copy`, what exact files, registries, sidecars, generated products, scripts, constants, external references, and upstream producers fed that substrate; how did those inputs evolve; what downstream consumers depended on them through Odin/Dva/Trii/Chetiri; and does any historically presumed informational distinction remain absent from the current authority/TIR universe?

## 1. Root commit — prove it, do not guess it

Define the canonical historical ancestry as the ancestry of the repository's canonical pre-Vozhd line leading into the later `ddm_build_copy`/Odin/Dva/Trii/Chetiri substrate. Do not select a commit merely because it has the earliest timestamp on an unrelated side branch.

Use full Git history to locate the **first commit in that ancestry whose tree contains at least one path under**:

`data/ddm_build_copy/`

Required proof:

1. record the exact root commit SHA;
2. record its first parent SHA, if any;
3. prove the parent tree contains no `data/ddm_build_copy/` path;
4. prove the root tree does contain it;
5. enumerate every path under `data/ddm_build_copy/` at that root commit;
6. record blob SHA / mode / size where available.

If multiple independent ancestry lines introduced separate `ddm_build_copy` trees, do not collapse them. Record each candidate root and prove which one feeds the canonical pre-Vozhd lineage.

Output:

`ROOT_COMMIT_PROOF.md`

`ROOT_SNAPSHOT_MANIFEST.csv`

Classify every root-snapshot object into exactly one primary role:

- not consumed in the historically reachable pipeline.

## 3. Backward producer/input trace

For every root object that was not purely manually authored, trace its producer backward.

A producer edge requires concrete evidence such as:

- exact script/function writes the path or payload;
- exact build command names the output;
- exact import/serialization call writes it;
- exact checked-in authority says it is generated from named parents;
- exact commit/README/receipt binds producer and input.

For each producer, recursively trace **all information-bearing inputs** until reaching terminal historical leaves.

Terminal leaf classes:

- `VERSIONED_MANUAL_AUTHORITY`
- `VERSIONED_RAW_REFERENCE_DATA`
- `EXTERNAL_OR_UNVERSIONED_SOURCE`
- `SOURCE_SURVEY_BINARY_REFERENCE`
- `CODE_CONSTANT_OR_EMBEDDED_TABLE`
- `ENVIRONMENT_OR_TOOLCHAIN_SEMANTICS`
- `UNKNOWN_OR_UNRECOVERED_INPUT`

The trace must include inputs outside `data/ddm_build_copy` whenever the producer reads them.

Do not stop merely because a file has a plausible name. Trace the actual read/write edge.

Output:

`BACKWARD_PRODUCER_INPUT_EDGE_LEDGER.csv`

Required fields include:

- `edge_id`
- `consumer_or_output_object`
- `consumer_or_output_commit`
- `producer_object_or_function`
- `producer_commit`
- `input_object`
- `input_commit_or_external_identity`

## 4. Forward evolution trace through the pre-Vozhd pipeline

Starting from the proved root, trace forward through the historical commits that materially alter the authority/dependency graph.

Do **not** write a useless commit-by-commit changelog of formatting noise.

Record every commit/event that does at least one of:

- introduces a new information-bearing input;
- changes a producer or transformation rule;
- adds/removes a registry, semantic authority, mapping, identity surface, negative constraint, routing rule, topology rule, directionality rule, learned product, replay key, provenance key, or lifecycle rule;
- introduces a new consumer;
- changes which authority a consumer reads;
- supersedes/retires an authority;
- moves an authority across Odin / Dva / Trii / Chetiri lineage;
- converts a generated output into an assumed input;
- creates a hidden dependency on environment/toolchain/path/order/default behavior.

For each material event record exact commit SHA and exact predecessor/successor relationship.

Output:

`FORWARD_AUTHORITY_EVOLUTION_LEDGER.csv`

## 5. Consumer-side trace — the critical denominator

The historical denominator is **not the set of files that happened to exist**.

The denominator is every information-bearing dependency actually presumed by historically reachable consumers.

Enumerate every executable/script/build/replay/analysis/runtime component in the pre-Vozhd chain that reads from, imports, joins against, opens, deserializes, queries, or otherwise semantically depends on `ddm_build_copy` or one of its upstream/downstream authority objects.

For every consumer dependency, record:

- consumer component/function;
- exact commit/range where dependency exists;
- exact authority/input object;
- exact fields/keys/semantic distinctions consumed when recoverable;
- whether dependency is direct, transitive, implicit/defaulted, or environment-mediated;
- whether later Odin/Dva/Trii/Chetiri authority explicitly supersedes it;
- whether the old dependency remains terminally meaningful.

Special attention must be paid to dependencies hidden in:

- row order;
- file order;
- path names;
- filename conventions;
- alias/default lookup;
- last-row-wins logic;
- missing/null coercion;
- implicit numeric-code order;
- environment/package decoder behavior;
- generated IDs whose derivation was not persisted;
- manually copied files later treated as authoritative inputs.

Output:

`HISTORICAL_CONSUMER_DEPENDENCY_LEDGER.csv`

## 8. Exhaustiveness / closure proof

The court may claim historical completeness only if all of the following are proved:

- root commit and root snapshot exact;
- every root non-documentation object classified;
- every generated root object has a producer/input disposition or explicit unresolved state;
- every historically material authority-graph mutation is accounted;
- every reachable pre-Vozhd consumer dependency is enumerated;
- every consumer dependency maps to an authority object or explicit unresolved/missing historical object;
- every authority object maps to current authority/TIR, dead legacy, or explicit orphan/unresolved state;
- no unaccounted reachable consumer edge remains.

Do not equate `git grep found nothing` with exhaustiveness unless the search denominator and historical refs are explicitly enumerated.

## 9. Forbidden shortcuts

- start from current R10*/REC files and work backward by name;
- assume the 68 TIRs are complete before the crosswalk stage;

- create successor authority.

This is an evidence court only.

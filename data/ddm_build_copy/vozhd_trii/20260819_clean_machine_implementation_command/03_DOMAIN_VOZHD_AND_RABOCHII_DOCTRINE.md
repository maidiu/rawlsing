# 03 — DOMAIN VOZHD & RABOCHII DOCTRINE

## 1. Domain commands

### Data & Logistics Vozhd

Owns implementation of the frozen physical substrate, ingestion, canonical persistence, migration mechanics, exact storage/retrieval primitives, and operational query substrate. Does not own semantic query/discovery meaning.

### Empirical Vozhd

Owns implementation synchronization across:

- exact empirical query;
- autonomous discovery;
- actor comparability service;
- positioned-subject empirical possibility field production;
- empirical replay/diagnostic services under frozen authority.

It must preserve the separation between population empirical fact, comparator proof, possibility geometry, and actor state.

### Structural Vozhd

Owns implementation synchronization across:

- StructuralEmpiricalAdmission;
- V553 temporal/comparability semantics where accepted;
- V554 affordance/applicability;
- V555 atomic mediation-route semantics;
- V556 governed interaction/topology;
- V557 publication/use governance;
- V558 repository/resolution;
- ResolvedStructuralContext boundary.

It must implement the final direct DAG rather than a universal numbered pipeline.

### Developmental Vozhd

Owns implementation synchronization across:

- objective actor-fact publication for comparator use;
- V3EmpiricalPossibilityInput;
- V3 empirical-possibility metabolism authority implementation;
- structural-context intake;
- actor-developmental causal ownership;
- V2/app nonconsumption boundary where affected.

Population geometry and structural context remain prior constraints, never direct actor psyche/persona.

## 2. Vozhd responsibilities

Every domain Vozhd must maintain:

- active rabochii roster;
- exact branch/head for each worker;
- input/output contract version for each worker;
- sibling dependencies;
- unresolved authority requests;
- semantic-diff review;
- current local DAG view reconciled to G4;
- current substrate contract version reconciled to G2;
- tests/fixtures required by G5;
- integration readiness state.

A Vozhd must audit worker products during construction whenever they change shared seams, not only at final return.

## 3. Rabochii jurisdiction

Each rabochii receives:

- one mission;
- exact base SHA;
- exact branch;
- bounded write surface;
- frozen authority pack;
- frozen substrate version;
- frozen interface/input/output contract versions;
- exact sibling dependencies;
- required tests;
- forbidden semantic moves;
- escalation path;
- acceptance outputs.

The worker may make ordinary local engineering choices where no shared semantic contract is changed.

## 4. Rabochii forbidden powers

A rabochii may not independently:

- create a shared table/column semantic;
- alter canonical object grain;
- invent a new shared ID/hash scheme;
- broaden accepted source pooling/linkage;
- add a hidden fallback/default/latest rule;
- convert null into a semantic state without authority;
- invent a cross-domain interface;
- turn provenance into runtime authority;
- copy producer semantics and re-own them;
- add a new DAG edge;
- treat an implementation convenience as architecture;
- alter a sibling-owned contract;
- create a compatibility shim without registered owner/death condition.

## 5. Worker completion packet

Every rabochii return must include at minimum:

1. `RESULT.md`
2. `RESULT.json`
3. `SEMANTIC_DIFF.json`
4. `CONTRACT_CONFORMANCE.json`
5. `TEST_AND_FIXTURE_RECEIPT.json`
6. `DEPENDENCY_IMPACT.json`
7. `OPEN_AUTHORITY_REQUESTS.json`

If no semantic change occurred, `SEMANTIC_DIFF.json` must explicitly say so and list why the code change is implementation-only.

## 6. Worker result states

Use finite states:

- `COMPLETE_CONFORMANT`
- `COMPLETE_WITH_NONBLOCKING_DEBT`
- `BLOCKED_SHARED_CONTRACT`
- `BLOCKED_AUTHORITY_CONFLICT`
- `BLOCKED_SUBSTRATE_AMBIGUITY`
- `BLOCKED_SIBLING_DEPENDENCY`
- `FAILED_CONFORMANCE`

Workers do not declare themselves integrated.

## 7. Parallelization rule

The Campaign Vozhd and domain Vozhds maximize independent work fronts, not worker count.

Workers may run in parallel when their shared inputs are frozen and they do not need each other's unresolved output to define their own contract.

Historical stage sequence is not evidence of a dependency.

A real dependency is one where a worker cannot determine its lawful input/output semantics until another authority or producer result is frozen.

## 8. Cross-worker discovery rule

If worker A discovers that worker B's frozen contract is insufficient or incompatible:

- A does not patch B's surface;
- A records an exact conflict;
- A notifies its Vozhd and G6;
- G6 identifies all affected workers;
- the owning staff authority adjudicates the contract;
- affected workers refresh/rebase before continuing across the changed seam.

## 9. Command responsibility

If two rabochii under one Vozhd implement incompatible interpretations of a supposedly frozen shared contract, that is primarily a command failure, not merely two worker mistakes.

Vozhds are therefore required to perform proactive synchronization audits.

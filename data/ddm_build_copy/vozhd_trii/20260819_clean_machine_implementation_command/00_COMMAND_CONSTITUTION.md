## 1. Purpose

This command system exists to build the completed Rawlsing machine rapidly without allowing parallel implementation to create semantic drift, incompatible schemas, duplicate authority, hidden defaults, or stage-number cargo cults.

The governing operating principle is:

> Centralize ontology, data law, interfaces, authority, integration, and adjudication. Decentralize bounded construction. Audit continuously. No local improvisation may become shared reality by accident.

This system is organized for an aggressive one-to-two-day implementation campaign once architecture closure authorizes implementation. Speed is obtained by opening every genuinely independent work front as soon as its inputs are frozen, never by weakening authority or allowing workers to invent shared contracts locally.

## 2. Constitutional hierarchy

No commander or worker may override higher law.

1. Rawlsing governing spirit / full-project total ambition.
2. Terminal-demand and architecture-pass law.
3. Accepted D12-D15 upstream authority and its parent adjudications.
4. Accepted downstream authorities, corrected R01/R02/R03 law, stage close-read rulings, and final whole-machine closure.
5. Canonical data-substrate, object, interface, authority, reference, replay, and negative-state contracts issued under this command system.
6. Domain-command orders.
7. Rabochii implementation decisions inside expressly delegated jurisdiction.

Current implementation code, historical stage numbering, filenames, old materializations, and convenience adapters are evidence only where they conflict with higher authority.

## 3. Activation gate

This system is fully specified now but may not authorize production implementation until all of the following are true:

- R03 hostile broad-DAG synthesis is accepted;
- required stage close-reads are accepted;
- whole-machine architecture is reclosed;
- the final implementation campaign is regenerated from that closure;
- the incoming-data / physical-substrate contract is frozen;
- shared object/interface/identity/reference contracts needed for the first build wave are frozen.

Until then, only command-system preparation, evidence preparation, fixture preparation, and non-production contract design expressly allowed by the parent are lawful.

## 5. Responsibility rule

A Vozhd is responsible not merely for issuing orders but for the semantic compatibility of everything produced under that command.

Every sub-Vozhd must continuously audit subordinate work against:

- the same incoming data substrate;
- the same canonical object model;
- the same DAG and interface registry;
- sibling producer/consumer contracts;
- higher authority and negative authority;
- the Rawlsing full-project ambition and governing spirit.

A worker's self-declaration of completion is never sufficient acceptance evidence.

## 6. Shared-contract monopoly

Rabochii and domain Vozhds may not independently create or mutate shared definitions of:

- database/table/object grain;
- canonical IDs or hash boundaries;
- source-universe identity;
- respondent/event/question/component identity;
- authority IDs/versions/hashes;
- typed absence/negative-state vocabulary;
- reference-edge classes;
- replay identity;
- shared serialization;
- cross-domain interface schemas;
- DAG ownership or consumer edges;
- migration/equivalence semantics.

Any required change is a formal request to the owning General Staff authority. Until adjudicated, the worker must fail closed rather than invent a local convention.

## 7. Contract-first law

No shared producer/consumer boundary may be implemented from prose expectations alone.

Before implementation begins across a shared seam there must be one authoritative machine-readable or mechanically precise contract stating at least:

- object grain;
- required/optional/forbidden fields;
- identities and hashes;
- semantic owner;
- legal producers and consumers;
- cardinality and ordering;
- typed positive/negative/absence states;
- reference/provenance roles;
- effective-time semantics where applicable;
- replay obligations;
- authority bindings;
- forbidden coercions and fallbacks;
- compatibility/versioning rule.

Producer and consumer implement independently against that shared contract. Neither side owns unilateral interpretation.

## 8. No communal implementation branch

Rabochii work on isolated branches and bounded write surfaces unless Integration Command explicitly authorizes a coordinated shared worktree for a tightly coupled operation.

The canonical integration branch is controlled territory. Only Integration Command may move accepted implementation tranches onto it.

## 9. Continuous reconciliation

Synchronization is event-driven.

A reconciliation is mandatory whenever a worker:

- changes a shared interface;
- requests a schema change;
- changes identity/hash material;
- changes negative-state behavior;
- changes an authority binding;
- introduces or removes a DAG edge;
- changes materialization/replay behavior;
- discovers an incompatibility with a sibling contract.

Domain Vozhds also conduct wave-boundary reconciliation even if no worker reported a conflict.

## 10. Inspectorate stop authority

The Inspectorate may issue:

- `PASS`
- `PASS_WITH_REQUIRED_HARDENING`
- `RETURN_FOR_HARMONIZATION`
- `STOP_INTEGRATION`
- `AUTHORITY_CONFLICT_ESCALATION`

It may not invent replacement architecture. Its power is to detect and block drift until the proper authority resolves it.

## 11. Integration rule

Nothing integrates because it compiles, passes local tests, or looks consistent.

Integration requires proof of:

- exact authority conformance;
- substrate conformance;
- interface conformance;
- sibling compatibility;
- identity/reference/replay continuity;
- negative-authority continuity;
- semantic-diff review;
- required hostile fixture passage;
- no unauthorized DAG edge;
- no unregistered shared-contract change.

## 12. Legacy-code posture

The current V550-V558 machine is read-only archaeological/reference terrain during the clean build except for explicitly adjudicated salvage.

Every reused surface must be classified as exactly one of:

- `KEEP_AS_IS`
- `KEEP_WITH_HARDENING`
- `EXTRACT_MECHANISM_ONLY`
- `USE_AS_TEST_ORACLE`
- `USE_AS_MIGRATION_ADAPTER`
- `SUPERSEDED_BY_ACCEPTED_AUTHORITY`
- `REBUILD_FROM_CONTRACT`
- `RETIRE_AFTER_EQUIVALENCE`

Historical location or stage name creates no presumption of retention.

## 13. Physical-substrate supremacy over convenience

All semantic services must anchor to the frozen Incoming Data Reality / Physical Substrate Contract.

No worker may infer a join, default, identity, missingness meaning, time relation, source equivalence, respondent linkage, weight meaning, or routing eligibility because it is convenient or seems obvious from labels.

The physical schema must preserve every distinction required by the canonical semantic model and must make lossy ambiguity difficult or impossible to express accidentally.

## 14. Golden-fixture doctrine

A single frozen hostile miniature substrate must exercise, at minimum:

- multi-source universes;
- routing / not-asked / ineligible;
- DK/refusal/unknown distinctions;
- multiselect and repeated events;
- question/component topology;
- exact and weighted measures;
- zero, observed-zero, zero-support, low-support;
- conflicting/noncomparable sources;
- temporal mismatch;
- minority and multimodal joint configurations;
- negative authority;
- historical authority replay;
- broken reference/hash failure.

Every relevant subsystem develops and integrates against the same fixture.

## 15. Golden-path calibration

Before mass integration, prove at least one complete structural path and one reverse-possibility path through the new contracts. These are calibration shots, not substitutes for later coverage.

Structural calibration:

`source -> canonical empirical substrate -> exact query -> StructuralEmpiricalAdmission -> lawful structural transforms -> publication -> repository/resolution -> ResolvedStructuralContext -> V3 boundary`

`objective actor facts -> comparator -> exact query/PSEPF -> V3EmpiricalPossibilityInput -> V3 boundary`

## 16. No shim without death certificate

Every compatibility shim must declare:

- exact source contract;
- exact target contract;
- why the shim exists;
- semantic equivalence claim;
- owner;
- tests;
- retirement condition.

Unowned permanent adapters are forbidden.

## 17. Semantic-diff requirement

Every proposed integration tranche reports not only code diff but semantic diff:

- canonical objects changed;
- database/schema changed;
- authority changed;
- DAG edges changed;
- identity/hash material changed;
- negative-state behavior changed;
- reference/replay changed;
- consumers affected;
- migrations required.

No semantic diff means no hidden semantic change is permitted.

## 18. Final acceptance

The completed clean machine is accepted only when terminal outputs can be semantically reconstructed backward through exact immutable references to:

- the producing semantic objects;
- the exact governing authorities;
- the relevant source universe(s);
- the exact empirical/query/risk-set/measure substrate where applicable;
- the exact V3 causal history where actor state is involved.

A break in that chain is a machine defect even if runtime output appears plausible.

> Freeze law. Freeze substrate. Freeze interfaces. Fan out hard. Integrate centrally. Audit every seam. Never permit local improvisation to become shared reality by accident.

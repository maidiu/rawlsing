# 12 — FORCE STRUCTURE & ACTIVATION PLAN

## 1. Standing command before activation

Before implementation authority is granted, the following units may exist as planning/evidence commands only:

- Campaign Vozhd;
- General Staff G1-G6;
- Inspectorate;
- Integration Command planning cell.

Domain implementation Vozhds may prepare force packages and worker missions but may not write production implementation until activated.

## 3. Delegation boundaries

Campaign Vozhd delegates **execution jurisdiction**, never constitutional authority.

A sub-Vozhd may:

- split a frozen mission into bounded rabochii;
- adjudicate local C0 choices;
- reject subordinate work;
- require harmonization;
- propose shared-contract changes;
- recommend integration tranches.

A sub-Vozhd may not:

- alter final whole-machine DAG;
- redefine substrate grain;
- redefine shared identities;
- create cross-domain authority;
- weaken governing-spirit/terminal law;
- integrate directly.

## 4. Force generation rule

Do not pre-create dozens of workers.

At every wave, Campaign Vozhd asks:

1. What contracts are frozen now?
2. What outputs can be produced without waiting for unresolved sibling semantics?
3. Which work fronts share enough internal coupling to need one sub-Vozhd?
4. Which fronts are independent enough to run concurrently?
5. Which tasks are too small to justify a separate worker and should remain one command's local work?

Then generate forces accordingly.

## 5. Activation sequence

### A0 — architecture receipt

Import accepted R03 synthesis, stage close-reads, and whole-machine closure into G1/G4 registries.

### A1 — substrate mobilization

G2 performs final Incoming Data Reality audit and freezes physical substrate contract.

This is the first major implementation bottleneck and may itself use parallel reconnaissance workers under one G2 Vozhd.

### A2 — shared-contract mobilization

G3/G4 convert the final architecture into exact object/interface/identity/reference contracts.

G5 builds matching hostile fixture/invariants concurrently.

### A3 — Campaign Mobilization Review

Campaign Vozhd checks:

- substrate frozen;
- first-wave interfaces frozen;
- fixture frozen;
- integration line declared;
- Inspectorate attack plan declared;
- COP initialized;
- worker launch packets complete.

Result:

`IMPLEMENTATION_MOBILIZATION_AUTHORIZED__WAVE_1_OPEN`

or fail closed.

### A4 — rolling waves

Open every independent front, integrate completed reconciled tranches continuously, and launch dependent fronts from exact accepted integration SHAs.

### A5 — final convergence

Stop opening new semantic fronts. Concentrate forces on:

- whole-machine hostile integration;
- replay/reconstruction;
- migration/equivalence;
- database performance/indexing without semantic change;
- deletion/retirement eligibility only where separately authorized.

## 6. Command turnover

If a Vozhd is replaced or a new chat/agent assumes command, turnover requires a command packet containing:

- exact canonical integration SHA;
- COP snapshot;
- current contracts/versions/hashes;
- active worker branches/heads;
- unresolved authority requests;
- known conflicts;
- integration queue;
- next true dependency barriers.

No new commander should reconstruct campaign state from chat memory.

## 7. Emergency stop

Any commander discovering a possible constitutional violation may issue a local stop on the affected seam immediately.

Within that stop:

- unaffected independent fronts continue;
- affected workers freeze;
- G6 determines impact radius;
- the proper authority adjudicates;
- Campaign Vozhd decides whether a broader wave stop is required.

This preserves speed without letting one uncertainty contaminate the whole build.

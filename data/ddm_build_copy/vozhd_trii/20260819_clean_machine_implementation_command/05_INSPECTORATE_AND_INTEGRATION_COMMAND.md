# 05 — INSPECTORATE & INTEGRATION COMMAND

## A. Independent Inspectorate / Red Team

The Inspectorate is outside producing domain commands.

Its job is not to help workers finish faster. Its job is to detect when speed is creating a second labyrinth.

### Inspectorate attack classes

Continuously attack for:

1. **substrate drift** — two workers assume different respondent/question/event/risk-set/weight/time grains;
2. **identity drift** — similar objects use different identity tuples/hash material;
3. **absence drift** — null/zero/not-asked/ineligible/unknown/refusal/noncomparability treated inconsistently;
4. **source collapse** — labels or convenience joins erase universe distinctions;
5. **authority leakage** — provenance/score/readiness/repository presence becomes semantic permission;
6. **DAG leakage** — workers introduce unregistered direct edges or recreate numbered transit;
7. **semantic duplication** — downstream copies/re-IDs producer-owned meaning;
8. **hidden defaults** — latest/nearest/fuzzy/majority/backfill/file-order behavior appears without authority;
9. **temporal drift** — source time, actor-fact time, decision time, and effective time silently conflated;
10. **replay drift** — historical outputs cannot recover exact immutable input/authority versions;
11. **actor/world collapse** — empirical/structural prior becomes belief/persona/memory/knowledge/action directly;
12. **sibling mismatch** — producer and consumer both pass local tests but implement different contracts;
13. **legacy smuggling** — superseded V550-V558 conventions re-enter through reuse without salvage authority;
14. **test weakening** — fixtures are changed to accommodate implementation instead of authority.

### Inspectorate dispositions

- `PASS`
- `PASS_WITH_REQUIRED_HARDENING`
- `RETURN_FOR_HARMONIZATION`
- `STOP_INTEGRATION`
- `AUTHORITY_CONFLICT_ESCALATION`

The Inspectorate may block integration. It may not create replacement architecture itself.

### Inspectorate cadence

Audit triggers:

- every shared-contract change;
- every domain-wave return;
- every integration candidate;
- every golden-path completion;
- any worker-reported sibling incompatibility;
- any new adapter/shim;
- any schema migration;
- whole-DAG reconciliation before the next major dependency layer opens.

## B. Integration Command

Integration Command is the sole authority for admitting completed implementation tranches to the canonical clean-machine integration line.

A domain Vozhd recommends. Integration Command admits or rejects.

### Integration acceptance packet

Each candidate tranche must provide:

- exact worker branch/head/base;
- domain-Vozhd acceptance receipt;
- authority pack identity;
- substrate contract version;
- interface contract versions;
- semantic diff;
- schema/migration diff;
- DAG diff;
- test/fixture receipts;
- Inspectorate disposition;
- replay/provenance conformance;
- dependency impact;
- unresolved debt explicitly classified.

### Integration gates

A tranche is rejected if any of the following are true:

- worker is based on stale shared contract;
- required authority unresolved;
- unregistered interface/DAG edge exists;
- schema change lacks G2 approval;
- identity/hash change lacks G3 approval;
- sibling contract has not been revalidated;
- hostile fixture fails;
- semantic diff is incomplete;
- negative authority is lost;
- source-universe separation is weakened;
- replay/reference closure is broken;
- adapter lacks owner/retirement condition;
- Inspectorate has `STOP_INTEGRATION` or unresolved `RETURN_FOR_HARMONIZATION`.

## C. Canonical integration line

The implementation campaign must declare one canonical integration branch once activated.

Rules:

- no rabochii writes directly to it;
- no domain Vozhd force-pushes it;
- Integration Command records every admitted tranche and resulting head SHA;
- every accepted integration commit updates the Common Operating Picture;
- workers for later dependent waves launch from explicitly issued integration SHAs, not from floating branch names.

## D. Semantic integration audit

Integration reviews semantic effects separately from code effects.

Mandatory questions:

- Did the legal object set change?
- Did ownership change?
- Did any consumer gain or lose a legal edge?
- Did any identity/hash change?
- Did absence/negative semantics change?
- Did source-composition authority change?
- Did runtime permission change?
- Did replay claims change?
- Did a cache/index become necessary for meaning?
- Did a legacy convention become canonical accidentally?

## E. Whole-machine reconciliation

After each meaningful integration wave, Campaign Vozhd + Integration + Inspectorate run a reconciliation:

> Does the integrated machine still instantiate the exact incoming substrate, accepted canonical object model, final DAG, Rawlsing terminal ambitions, and governing spirit?

The reconciliation is not a status recap. It is a semantic checksum.

If the answer is uncertain at any interface, the next dependent wave remains closed.

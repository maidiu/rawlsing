# 22 — OPERATIONAL TEMPO, CRITICAL PATH & FORCE GENERATION DOCTRINE

## 1. Objective

Maximize wall-clock progress without increasing semantic drift.

The campaign optimizes:

`MAXIMUM_INDEPENDENT_CORRECT_WORKFRONTS / MINIMUM_TRUE_SERIAL_BARRIERS`

not worker count, commit count, or apparent activity.

## 2. Critical-path ownership

Campaign Vozhd + G6 maintain one live critical-path graph in the COP.

Every active or planned unit is classified:

- `CRITICAL_PATH`
- `PARALLEL_SUPPORTING`
- `SPECULATIVE_RECONNAISSANCE`
- `BLOCKED_TRUE_DEPENDENCY`
- `BLOCKED_AUTHORITY`
- `BLOCKED_SUBSTRATE`
- `INTEGRATION_WAIT`

No unit may be described as blocked merely because a historically earlier stage is unfinished. The exact missing contract/object/receipt must be named.

## 3. Force-generation rule

Whenever an output freezes a previously unresolved input, the responsible Vozhd immediately reevaluates the dependency graph for newly open fronts.

If two missions no longer share an unresolved input, they should normally become separate workers.

If several workers share one semantic jurisdiction and can investigate independently, use a sub-Vozhd with one dispositive synthesis rather than serialize the investigations.

## 4. Worker-count discipline

Do not maximize rabochii count.

Spawn a worker only when it has:

- a bounded mission;
- exact frozen inputs;
- a disjoint or leased write surface;
- an identifiable output that advances a gate;
- no cheaper way to obtain the same evidence from an already-active unit.

Idle coordination overhead is treated as a performance defect.

## 5. Tranche size

Workers should commit small semantically coherent tranches rather than one enormous end-of-mission dump when doing so exposes interfaces earlier without destabilizing shared contracts.

A tranche is integration-eligible only when its semantic boundary is complete; arbitrary partial code is not integrated merely to show progress.

## 6. Early seam calibration

For any new shared contract, prioritize the smallest producer/consumer calibration path that exercises the real interface and hostile negatives.

This is not a serial prototype of the whole system. It is an early seam checksum used to unblock mass parallel construction safely.

## 7. Audit proportionality

Audit effort scales with semantic blast radius:

- local C0 implementation: domain Vozhd review;
- shared C1: owner + G6 + targeted Inspectorate;
- C2 shared evolution: full impacted-domain/seam audit;
- C3: stop and higher-authority adjudication.

Do not run whole-machine bureaucracy for a local refactor; do not wave through a one-line identity change because the diff is small.

## 8. Fast-fail rule

Workers must report a true contract/authority/substrate blocker as soon as it is proven rather than spending the remainder of the mission building around it.

The owning command then either:

- resolves the blocker;
- opens parallel reconnaissance;
- redirects unaffected workers;
- or narrows the stopped seam.

## 9. Integration tempo

Integration Command accepts proven coherent tranches continuously; it does not wait for an arbitrary clock-based release train.

However, any integrated shared-contract change triggers the required dependency invalidation/reconciliation before affected downstream tranches can follow.

## 10. No hidden serial queues

The following are presumptively invalid scheduling reasons:

- stage number ordering;
- one-worker habit;
- waiting for a sibling whose output is not actually consumed;
- waiting for implementation of a contract that is already semantically frozen;
- bundling unrelated tasks because one module historically contained them.

## 11. Required Campaign Vozhd tempo audit

At every wave reconciliation, Campaign Vozhd must answer:

1. What is the current true critical path?
2. Which blocked units are blocked by an exact information dependency?
3. Which newly frozen inputs allow another front to open now?
4. Are any workers duplicating the same investigation?
5. Are any workers sharing a write surface that should be decomposed or leased?
6. Is any coordination layer producing no unique command value?
7. Can any final merge dependency be separated from launch/evidence work?
8. Is Inspectorate effort aimed at the highest semantic blast radius?
9. Are integration-ready tranches waiting for a non-semantic reason?

Any unnecessary serialization found is corrected immediately.

## 12. Speed ceiling

No schedule pressure authorizes:

- substrate guessing;
- authority guessing;
- local shared-contract invention;
- source pooling;
- hidden defaults;
- semantic copy/reownership;
- skipping seam conformance;
- integrating stale workers;
- destructive migration without proof.

Speed comes from decomposition, frozen contracts, and parallel work—not from accepting uncertainty as semantics.

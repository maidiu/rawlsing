# Workstreams and Delegation

## Coordination model

Vozhd Dva owns cross-stage semantics, integration order, gate decisions, worker partitioning, and final schematic adjudication. Rabochiis receive bounded read/write domains and explicit acceptance criteria. Workers do not independently redefine neighboring stage contracts.

Parallelism is encouraged where dependencies are clear. Shared interfaces are reasoned about in schematic breakouts, reconciled centrally, then handed to implementation workers as accepted seam contracts.

## Prong 1 — Reconnaissance / cross-stage evidence

Purpose: establish what the current pipeline actually emits, consumes, preserves, loses, or blocks.

Outputs:
- producer/consumer traces;
- current semantic-loss findings;
- concrete interface defects;
- V558→V3 consumer requirements;
- V3→V2 boundary requirements;
- five acceptance slices and executable harness.

Reconnaissance reports are evidence for schematic adjudication, not automatic architecture.

## Prong 2 — Schematic transformation breakouts

Purpose: determine, seam by seam, what each stage should create from the lawful information supplied upstream and what it must emit for the next stage.

Canonical method:

`upstream authority → lawful intake → stage-specific operation → enriched output → downstream requirement`

Boundary sessions live under `schematics/boundaries/` and are indexed in `schematics/SESSION_INDEX.md`.

Typical delegation pattern:
- one forward worker starting from upstream authority;
- one backward worker starting from the next stage's real needs;
- on high-risk seams, one hostile critic for overclaiming/essentialization/information-loss hazards.

Schematic workers are production-read-only unless separately authorized. They return transformation equations, preservation ledgers, worked examples, defects, and unresolved questions.

Vozhd Dva reconvenes the breakouts in `schematics/synthesis/`. Only accepted synthesis rulings become implementation authority.

## Prong 3 — V553 entry repair and temporal semantics

Immediate known defect: activate `POSTG5-004` and repair V553 to consume canonical V552J outputs rather than the obsolete structural handoff packet.

Then implement the accepted S00/S01 rulings for temporal semantics needed by all five vertical slices: comparability, persistence, drift, rupture, absence over time, uncertainty, structural dimensions, and provenance.

V553 should transform lawful upstream structural evidence; it should not reconstruct governed upstream identity from synthetic convenience labels where canonical identity already exists.

## Prong 4 — V554–V556 semantic implementation

Purpose: implement accepted S01/S02/S03 transformations without instantiating biography or psyche.

Subdomains may be delegated separately once seam contracts are adjudicated:
- V554 bounded structural/seed affordance transformation;
- V555 mediation topology and conditions;
- V556 pressure-flow / attractor topology and requirements.

Workers must preserve explicit source/provenance/uncertainty lineage and cannot generate actor-specific facts.

## Prong 5 — V557–V558 boundary completion

Purpose: implement accepted S04/S05 rulings so deepened structural priors cross a controlled runtime-consumption boundary without semantic starvation.

Work includes:
- lossless preservation of runtime-authorized prior information;
- forbidden-inference enforcement;
- source/derived/generated/rendered separation;
- runtime input normalization;
- V3 reference-consumer tests.

## Prong 6 — Vertical fixtures and test harness

Purpose: make cross-stage continuity executable rather than documentary.

Maintain the finite test set covering:
1. temporal persistence/drift/rupture;
2. contradictory inter-strata pressure;
3. mediation plus buffering/amplification;
4. pressure-flow plus attractor prerequisites;
5. uncertainty/absence/noncomparability/forbidden inference.

As accepted seam contracts are implemented, replace explicit current-gap XFAILs only with production evidence that the real chain satisfies the reference contract.

## Prong 7 — Horizontal source qualification

Begins only after representative vertical slices work. Workers can then own source-family/wave qualification shards and report concrete common-model failures rather than redesigning stages independently.

## Prong 8 — V3 runtime rebuild

S06 schematic adjudication precedes deep V3 implementation. Early coding may begin against a frozen V558 mock/reference consumer only after the seam contract is stable enough.

V3 owns runtime state/event architecture, causally attributable transitions, actor-specific developmental pressure-flow, and Enneagram-like attractor realization over time.

## Prong 9 — Genealogy / household runtime

Can overlap late V3 work once actor state and temporal event interfaces exist. Owns Parent 1 / encounter / Parent 2 / relationship / household / child orchestration.

## Prong 10 — V2 and app/demo

S07 schematic adjudication defines the V3→V2 read-only render boundary before deep V2 implementation. V2 contract/design may proceed against mocked V3 state once that boundary is frozen.

Full integration waits for stable event/state APIs. App/demo work should prioritize a polished demonstrable vertical path over broad feature expansion.

## Worker launch rules

Every Rabochii launch must specify:
- whether it is reconnaissance, schematic, implementation, qualification, or review work;
- base branch and target integration branch;
- exact read/write domain;
- exact issue/capability/seam IDs;
- upstream contracts that bind;
- downstream requirements that must remain satisfied;
- accepted schematic ruling if implementing a shared seam;
- tests/acceptance evidence required;
- explicit out-of-scope areas;
- required machine-readable report.

Workers encountering a cross-cutting ambiguity must return a proposed ruling or `PARTIAL_AWAITING_CROSS_HOOK`; they must not invent downstream semantics to make their local task green.

# Downstream Advisory Reconnaissance Track

**Authority:** Vozhd Dva coordination only  
**Status:** advisory / pre-adjudication  

## Purpose

The binding implementation/adjudication track may be blocked by an upstream dependency while substantial downstream excavation remains useful.

This track allows Rawlsing to bank downstream understanding without pretending that an unfrozen upstream contract is already production law.

## Governing distinction

Two tracks may coexist:

1. **Binding track** — accepted seam rulings, production architecture, implementation packets, completion gates. This track obeys real upstream dependencies.
2. **Advisory architecture track** — code excavation, cumulative-upstream analysis, downstream-demand analysis, boundary examination, provisional architecture, schema/object design, defect maps, hostile cases and provisional completion strategy. This track is read-only against production code and cannot change project law.

Advisory work may inspect downstream stages before their binding predecessor has completed. It must label every conclusion according to dependency status, distinguishing accepted upstream law, provisional upstream-target assumptions, current-code observation and matters requiring later binding adjudication.

## Standard two-pass rhythm

For each substantive downstream stage, advisory work normally proceeds in two passes before descending further:

`PASS A — DEEP EXCAVATION`
`→ PASS B — MAXIMAL ARCHITECTURE BUILD-OUT`
`→ NEXT STAGE PASS A`

### Pass A — deep excavation

Determine:
- everything lawfully available in the cumulative upstream DAG;
- the next stage's total information need;
- what that next stage can already reuse directly from earlier producers;
- the current stage's residual semantic responsibility;
- current implementation strengths, losses, duplicate authority and wrong-primary surfaces;
- provisional object families and jurisdiction boundaries;
- concrete questions that require later binding adjudication.

Pass A answers primarily: **what is this stage actually for?**

### Pass B — maximal architecture build-out

Starting from the accepted advisory excavation, design the strongest implementable provisional target possible now:
- exact stage jurisdiction/equation;
- component architecture;
- selected DAG input classes and authority precedence;
- semantic object families, row grains and provisional schemas;
- stable identity, lineage and provenance rules;
- state/lifecycle and typed negative authority;
- production dataflow;
- physical artifact/publication roles;
- downstream composition/handoff strategy;
- migration/deprecation map;
- finite completion court;
- hostile/ordinary worked cases;
- bounded eventual implementation packets.

Pass B answers primarily: **if the excavation is right, what should the finished stage actually look like?**

Exact producer bindings that depend on unfinished upstream implementation may be tagged for later finalization rather than omitted. The semantic slot should still be designed now where evidence permits.

## Category-separation law

Advisory architecture must keep three classes distinct:

1. **semantic objects** — stage-created or inherited meanings that may lawfully survive into downstream reasoning;
2. **boundary/interface objects** — handoff/index/manifest contracts that carry or resolve semantic objects but are not themselves new semantic meaning merely because they are published;
3. **validation/audit failures** — corrupt transport, schema mismatch, identity-integrity failure, forbidden-inference attempts, synthetic-fallback attempts and similar defects. These fail closed or remain diagnostic; they must not be laundered into authoritative semantic negative-state rows.

This distinction is mandatory in maximal architecture passes.

## What advisory work may do

- inspect all current production/test surfaces of the stage under study;
- inherit the cumulative upstream map and identify earlier outputs the stage could lawfully reuse directly;
- use already-adjudicated upstream semantic law and accepted target architectures as constraints;
- inspect the next stage far enough to understand total downstream need;
- identify the current stage's likely residual semantic responsibility;
- build a detailed provisional internal architecture and artifact/handoff strategy;
- identify current implementation strengths, losses, duplicate authority, placeholders and wrong-primary surfaces;
- propose implementation/test implications for later adjudication;
- identify exactly which conclusions could change when the blocked upstream implementation lands.

## What advisory work may not do

- write production code;
- modify accepted seam rulings;
- update the authoritative cumulative map as though proposals were accepted;
- declare a downstream stage `COMPLETE` or `READY`;
- freeze schemas/object contracts for later workers;
- make speculative upstream changes;
- promote generated/persona/runtime meaning into V5 structural stages.

## Reuse law

Advisory reports are intended to be reused.

When the relevant upstream stage becomes binding, Vozhd performs a **delta check**:

`advisory model + final upstream contract → contradiction/delta analysis`

If no material contradiction exists, the advisory excavation and maximal architecture become evidence for the formal seam court and do not need to be repeated. Only binding choices are then adjudicated.

## Sequencing

Run advisory work serially so each later stage inherits both the excavation and maximal architecture of the prior stage.

Current intended sequence:

`PRE-S01 V554 excavation`
`→ PRE-S01.5 V554 maximal architecture`
`→ PRE-S02 V555 excavation`
`→ PRE-S02.5 V555 maximal architecture`
`→ PRE-S03 V556 excavation`
`→ PRE-S03.5 V556 maximal architecture`
`→ PRE-S04/05 V557-V558 boundary/runtime-gate excavation + build-out as topology warrants`
`→ PRE-S06 V3 excavation + maximal architecture`
`→ PRE-S07 V2/app excavation + maximal architecture as needed`

V557/V558 may be treated as a coupled architecture unit if excavation proves their contracts are inseparable; do not force artificial stage isolation merely for numbering symmetry.

This serial advisory sequence does **not** unblock production implementation or binding seam progression.

## Reporting economy

Pass A should remain decision-bearing rather than encyclopedic.

Pass B may be substantially more detailed because its purpose is to terminate in an implementation-ready provisional blueprint. Detail is justified when it defines a component, schema grain, authority rule, lifecycle, artifact role, test, migration obligation or later binding decision. Repeated research notes and file-read narration are not.

# Downstream Advisory Reconnaissance Track

**Authority:** Vozhd Dva coordination only  
**Status:** advisory / pre-adjudication  

## Purpose

The binding implementation/adjudication track may be blocked by an upstream dependency while substantial downstream excavation remains useful.

This track allows Rawlsing to bank downstream understanding without pretending that an unfrozen upstream contract is already production law.

## Governing distinction

Two tracks may coexist:

1. **Binding track** — accepted seam rulings, production architecture, implementation packets, completion gates. This track obeys real upstream dependencies.
2. **Advisory reconnaissance track** — code excavation, cumulative-upstream analysis, downstream-demand analysis, boundary examination, architecture sketches, likely object grains, defect maps, hostile cases, and provisional test strategies. This track is read-only against production code and cannot change project law.

Advisory work may inspect downstream stages before their binding predecessor has completed. It must label every conclusion according to dependency status:
- `STABLE_FROM_ACCEPTED_UPSTREAM_LAW`
- `PROVISIONAL_ON_INTENDED_UPSTREAM_TARGET`
- `CURRENT_CODE_OBSERVATION`
- `REQUIRES_LATER_BINDING_ADJUDICATION`

## What advisory work may do

- inspect all current production/test surfaces of the stage under study;
- inherit the cumulative upstream map and identify earlier outputs the stage could lawfully reuse directly;
- use already-adjudicated upstream semantic law and accepted target architectures as constraints;
- inspect the next stage far enough to understand total downstream need;
- identify the current stage's likely residual semantic responsibility;
- sketch a bounded internal architecture and artifact/handoff strategy;
- identify current implementation strengths, losses, duplicate authority, placeholders and wrong-primary surfaces;
- propose implementation/test implications for later adjudication;
- identify exactly which conclusions could change when the blocked upstream implementation lands.

## What advisory work may not do

- write production code;
- modify accepted seam rulings;
- update the authoritative cumulative map as though proposals were accepted;
- declare a downstream stage `COMPLETE` or `READY`;
- freeze schemas/object contracts for later workers;
- make speculative upstream changes;
- promote generated/persona/runtime meaning into V5 structural stages.

## Reuse law

Advisory reports are intended to be reused.

When the relevant upstream stage becomes binding, Vozhd performs a **delta check**:

`advisory model + final upstream contract → contradiction/delta analysis`

If no material contradiction exists, the advisory excavation becomes evidence for the formal seam court and does not need to be repeated. Only binding choices are then adjudicated.

## Sequencing

Run advisory reconnaissance one stage at a time so each later excavation can use the accumulated provisional understanding while keeping its dependency labels explicit.

Initial sequence:

`PRE-S01 V554 → PRE-S02 V555 → PRE-S03 V556 → PRE-S04/05 V557-V558 → PRE-S06 V3 → PRE-S07 V2/app`

This serial advisory sequence does **not** unblock production implementation or binding seam progression.

## Reporting economy

Investigate deeply; return decision-bearing architecture.

A normal advisory report should emphasize:
- current implementation topology;
- cumulative available upstream material;
- next-stage total demand;
- likely residual responsibility of the stage;
- provisional target architecture/object families;
- concrete current defects/gaps;
- assumptions that depend on unfinished upstream work;
- later adjudication questions;
- tests/hostile cases that would prove the proposed boundary.

Do not create an encyclopedia merely because more code can be described.

## 2. What GF1 demonstrated, and what it did not

**Demonstrated (bounded, sourcefree, TEST_ONLY):**

- The accepted native C11/I03/I05/P01 machinery already produces a genuinely
  generic two-binary-item pair. Its query components are
  `m01-X` / `m01-Y`, not Q86A/Q86B.
- A separately named owner can consume those same native objects and emit a
  distinct relation object with genuine per-slot role binding, without touching a
  single accepted byte.
- Role binding can be made owner-gated: a swap refuses without a separate grant,
  and succeeds only with it.
- A named consumer can derive an evidence-bounded downstream value that is not a
  copy of the relation.

**Not demonstrated, and not claimed:**

- That a generic native relation is *semantically warranted* for any original
  survey family.
- That generic X/Y labels may ever be read as Field Forge semantics.
- Anything about persons, dyads, peers or causality.
- That the GF1 candidate should be adopted, renamed or promoted.

## 3. Exact minimum competent-owner signature required before adoption

The owner must issue, at minimum, each of the following. GF1 deliberately did
**not** invent any of them.

| # | Required signature element | Why it cannot be defaulted |
|---|---|---|
| S1 | **Generic relation family identity** | A generic family must be separately named and scoped; reusing the GT2 family would silently merge a specialized reading into a generic one. |
| S2 | **Authorized role binding**: which native component is CONDITIONER and which is TARGET, per operation | GF1 showed the native order genuinely varies by slot (`PAIR` = `[X,Y]`, `B` = `[Y,X]`). Without an owner rule, "conditioner" is ambiguous. |
| S3 | **Reverse-operation rule** and its **separate grant** | X given Y is a *different operation*, not a view of the same one. GF1 enforced the separation but cannot authorize it. |
| S4 | **Source-native response domain** and its missingness/nonresponse rules | Admitting a nonbinary or out-of-domain category would fabricate a category the source does not have. |
| S5 | **Risk-set and universe admissibility**, including same-person joint eligibility | Who is jointly eligible is a semantic decision; `observed 0` and `ZERO_SUPPORT` must stay distinct. |
| S6 | **Producer and relation permission ceilings** | GF1 kept `SOURCE_FREE_DEV` and refused widening; production rights were never sought. |
| S7 | **Instrument / release / form / administration / language / occurrence / respondent grain** | These bound what a generic relation may claim to be about. |
| S8 | **Consumer contract**: what a downstream reader may conclude | A support profile is not a person, a peer trait, or a mechanism. |
| S9 | **Comparison with the existing specialized GT2 owner** | A generic relation must not be allowed to shadow or overwrite Q86B/Q86A outputs. |

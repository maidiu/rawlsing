## Cost comparison without invented numbers

The source-native query scans/evaluates eligible respondent configurations and needs exact routing, authority and provenance. GF1's own aggregation **after** a materialized two-binary I03 joint is bounded by four cells; this makes the *derived profile cheap* relative to native measurement, but does not prove end-to-end acceleration. A separate relation adds hashing, serialization, replay audit, permission/currentness checks, version invalidation, storage and reader maintenance. A repeated consumer may gain by reusing a qualified cached relation, but a direct C1/I03 query may be equally cheap after current indexed/compact reuse. Neither path is benchmarked here.

Current protected engineering already includes compact C11 execution view, authenticated Parquet reuse, and I03 per-repository indexed access at their independently scoped sourcefree cuts (PRs #686 and #684). E41 current extension already exists and actual learned-world composition calls it; historical E41/J42 success is sourcefree, not original native N10W qualification. Additional W04/W05 grouped computation or compression should be selected **only** after native-sized first-reader profiling, not because GF1 exists. No second query engine, universal graph store or mandatory GF1 materialization is justified.

**Future performance protocol if an owner selects a reader:** pin source/release/form/as-of, eligible respondents, target pair and true 3+ joint competitor; compare direct I03/C1/E41 vs GF1-derived cached/un-cached paths on identical permission checks, denominator/zero/replay outputs; report wall time, CPU, peak RSS, total and marginal I/O, cold/warm cache hit/miss, invalidation/revocation cost, serialized bytes, write/read amplification and exact output parity. Treat run-to-run variance and sourcefree/original35 separately. A cheap four-cell postprocessor without measured source/read cost is not a terminal performance win.

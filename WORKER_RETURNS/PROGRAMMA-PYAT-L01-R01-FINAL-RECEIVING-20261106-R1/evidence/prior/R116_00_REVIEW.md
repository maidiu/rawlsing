### Blocking finding — mixed-prefix model identity

`_progressive_prefix_identity` compares universe, release, risk and repository,
but not `prefix.model_rule`/model authority. `configure_progressive_world_context`
computes each prefix extension with its own model rule and accepts two prefixes
with different rule hashes. The resulting `n10e_steps` have different
`model_rule_hash` values inside one selected N10W assertion.

Witness: use `_progressive_fixture_parts()`, replace the second prefix's
`model_rule` with a different actual model rule (same source universe), then
configure and view T0. The candidate returns
`PROGRESSIVE_WORLD_SELECTED_VIEW` with native state
`OPTIONS_AND_SOURCE_SUPPORT_PRODUCED`; step model hashes differ
(`c3f635e9…` vs `e004d8ca…`).

Minimal fix: require every prefix's exact model identity (at least
`model_rule.rule_hash`; also the model authority/source identity used by the
existing contract) to equal the first prefix's before registration/serving, and
refuse with a typed identity code. Preserve the actual native positives,
R115 rows/repository checks and the existing behavior for a single shared
model. No new architecture or engine.

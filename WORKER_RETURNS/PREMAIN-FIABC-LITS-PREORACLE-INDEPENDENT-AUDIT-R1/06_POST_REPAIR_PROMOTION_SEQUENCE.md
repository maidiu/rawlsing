# Post-Repair Promotion Sequence

## Governing correction

The rough sequence supplied in the commission places governed execution-branch advancement after fresh LiTS/WVS oracle work. Current repository launch law requires the opposite for the **branch transition only**:

`02_PRE_CANDIDATE_LOCAL_PREFLIGHT.sh` fails unless the checkout branch is exactly:

`agent/rabochii-prev3-ee-p2x-final-abc-equal-work-execution-r1`.

That same preflight script then:
1. standardizes the accepted WVS R1M oracle;
2. performs the fresh local candidate-neutral LiTS oracle pass;
3. freezes T3 from the two verified standard oracles;
4. produces and validates succession/preflight receipts;
5. stops before candidates.

Therefore the existing governed P2X branch must be cleanly fast-forwarded **after source-free qualification/adoption but before the fresh local pre-candidate pass**. This is not authorization to execute candidates.

## Important distinction

“Governed execution branch advanced” is not the same event as “candidate execution authorized.”

Repository law requires the branch to be advanced first so the governed pre-candidate script can run, but the script itself ends before candidates. The later measured-run command is separately gated by the frozen upstream receipt and succession preflight.

## Stop conditions

Any of these blocks promotion:
- wrong-catalog successor accepted;
- wrong-parent-operation successor accepted;
- LiTS parity based only on counts/hashes;
- any P0–P4 substantive mismatch;
- WVS terminal truth drift;
- stale WVS packaging regression still failing full qualification;
- branch ancestry not clean;
- post-qualification production-code drift;
- source SHA mismatch;
- candidate-owned state present before freeze;
- T3 or succession preflight invalid.

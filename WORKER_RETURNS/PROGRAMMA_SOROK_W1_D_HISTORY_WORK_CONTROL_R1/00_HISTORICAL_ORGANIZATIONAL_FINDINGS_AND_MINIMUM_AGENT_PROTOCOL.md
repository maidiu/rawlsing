## 1. Decisive finding

**The essential unit is not a task, document, branch, graph node, or approval. It is a consequential, source-qualified change in understanding or function that survives into its actual downstream consumer, with its contrary evidence, responsible owner, and next lawful action.** Sorok has accumulated first-rate historical conceptual work and genuine sourcefree engineering, but its historical registers, recent returns, HQ motion stream, Programma experiments and PRE-MAIN progress do not share a single *interpreted, authority-qualified account* of what is already settled and what changed. PROGRAMMA should represent those relationships, not reproduce each record system as another work queue.

This is an organizational problem with scientific consequences: a status-only query can reopen closed alpha questions, a title-only source index can misclassify historic proposals as current authority, and a Git branch can be mistaken for a running worker. Conversely, strict process formalism can suppress the very already-qualified implementation work it was meant to safeguard. Programma must cut both errors.

**Four essential distinctions:** historical assertion vs current adopted judgment; executable sourcefree fact vs original native science; returned candidate vs reviewed/adopted/merged work; queued or published work vs an observed live session. These distinctions are orthogonal. Neither a newest timestamp nor a larger test count replaces them.

## 6. Minimum future agent transaction

`RECEIVE EXACT CONTEXT → BOUNDED WORK → RETURN EVIDENCE + CHANGED EDGES → COMPETENT RECONCILIATION → NEXT PRODUCTIVE ACTION`.

At launch (one sealed record): **work_id**, original question/function and intended **first consumer**, source branch + full SHA + relevant blobs, current accepted vs RED/held baseline and tests, allowed/read-only paths, prohibited effects, competent owner/reviewer, exact selected editor/model/effort/host as *requested* with separate verification, user launch/transport authorization, active lease or unknown, one acceptance falsifier and how to rollback. No compulsory invented ontology survey, blanket recensus or duplicate accreditations.

At return (one receipt): input SHA and output SHA; changed files/functions and actual consumed edges including producer→first executing/importing consumer; test commands/execution host/observed outcomes, **positive and negative** plus severance/restore when material; changed owner/source/semantic assumptions; author vs independent distinction; explicit `NOT_RUN`; author proposed next action and unaffected parallel lanes. Absence of changed function is legitimate if the return is a conceptual falsification or exact owner NO decision.

At intake (one qualified owner decision): exact subject SHA, review only if consequential disputed/failing claim, `ACCEPT_SCOPED / REVISE_EXACT_DEFECT / HOLD_NAMED_OWNER / REJECT_WITH_NEGATIVE / SUPERSEDED / HISTORICAL_ONLY`, affected dependencies (forward and reverse), consumer impact, first actual user/scientific/product gate and one next productive action. **Returned ≠ accepted ≠ adopted ≠ merged.** Each change is journaled; previous statuses and WHY_NOT survive. No permanent “approval request” for routine already-qualified repair or metadata.

### Status and evidence axes, not a single tempting traffic light

- Source: `ORIGINAL_AUTHENTIC / SOURCE_READ / CANDIDATE / UNKNOWN / UNRECEIVABLE`; exact immutable origin.
- Engineering: `CODE_PRESENT / AUTHOR_TESTED_SOURCEFREE / INDEPENDENTLY_TESTED_SOURCEFREE / SCOPED_ACCEPTED / NATIVE_EXECUTED`; actual first consumer and negative.
- Science/authority: `PROPOSED / ISSUED_BY_COMPETENT_OWNER / WITHHELD / UNVERIFIED` for each separate rule/source right, never derived from engineering status.
- Product: `STRUCTURAL / DEMO / HUMAN_EVALUATED` with actual participant, exposure and evaluation warrant.
- Work: `DRAFT / PUBLISHED / USER_LAUNCHED / OBSERVED_RUNNING / RETURNED / REVIEWED / OWNER_ADOPTED / INTEGRATED / CANCELLED / UNKNOWN`, each supported by *different evidence*. A worker can be returned and not adopted; a published branch can have unknown running status.

Store only qualifying **relations**: `addresses, derives-from, corrects, supersedes, contradicts, realizes, imports, first-consumes, tests-positive, falsifies, authorizes, held-by, blocked-by, affects, reviewed-at, adopted-at, pending-on`; for every consequential edge: `source_ref + authority_grade + observed_at/source_cut + status`. Reverse traversal is derived, not manually duplicated. Link ambiguous IDs as aliases instead of silently merging differing source objects. A refused/rejected approach remains searchable with its reason and reopen condition.

**Mechanical automatic checks** where the available environment permits: exact SHA/ref existence and blob identity, typed schema and namespaced IDs, missing source refs, declared changed paths vs Git diff, approved path sandbox, author/reviewer separation, commissioned base/return ancestry, duplicate receipt idempotency, process lease/observed PID when present, source-only first-consumer proof labels vs real importer/test, failure witnesses/severance/restoration, running status TTL and stopped-user grants. Do not “autoprove” science, owner signatures, human authenticity, intent or causal explanation from these checks.

**Independent review threshold:** new original science or provenance/actor/source ownership; consequential security/custody/cold/fork/causal-source severance; disputed exact consumer; new A5 human claims; previously failing defect with material downstream consequence. Routine metadata, already scoped repeatable repairs and index refresh do not need a new opposing court every time. If a reviewer says `REVISE`, return to an existing implementer on exact defects; same independent reviewer can inspect repaired SHA rather than a growing reviewer tree.

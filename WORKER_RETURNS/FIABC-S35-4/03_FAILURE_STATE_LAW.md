# FIABC-S35-4 — Failure-State Law

Status: `ALL35_PORTABILITY_FAILURE_LAW_PROVED__EXECUTABILITY_NOT_CLAIMED`

## 1. Court object

This worker defines the admission law for a future CLOSED_35 source×candidate cell. It does not certify that the cell is currently executable.

For source `S` with canonical source-root SHA-256 `H`, the admissible physical relation is:

`candidate(S) -> exact physical/derivative lineage -> H`

The semantic relation is separately invariant:

`H -> accepted decoder/source-native incidence -> governed source-specific authority -> validated source-backed C11 -> unchanged I03 -> governed I05 terminal`

A/B/C may vary the first relation. They may not vary the second.

The governing distinction is therefore:

`PHYSICAL PORTABILITY != SEMANTIC JURISDICTION`

and:

`LAWFUL DERIVATIVE != ALTERNATE SOURCE`.

## 2. Failure precedence

A future source/candidate admission must evaluate failures in this order.

First, establish one canonical CLOSED_35 root `H`. If no unique root is proved, return:

`BLOCKED__CANONICAL_SOURCE_ROOT_UNPROVED`

Do not inspect candidate caches, accelerators, historical exports, labels, dimensions, or outputs as a substitute.

Second, reject any noncanonical file presented as the source unless an explicit governed equivalence/derivation chain terminates at `H`:

`BLOCKED__ALTERNATE_SOURCE_SUBSTITUTION`

Third, validate every preserved empirical derivative used by the candidate. Every physical edge must bind exact parent, producer/operation, derivative identity, scope, replay/currentness and candidate-policy permission. A missing edge returns:

`BLOCKED__DERIVATIVE_LINEAGE_TO_CANONICAL_ROOT_UNPROVED`

A proved derivative whose scope is narrower than the current workload returns:

`BLOCKED__DERIVATIVE_SCOPE_INSUFFICIENT`

unless the candidate lawfully supplies the uncovered remainder from `H`.

Fourth, close the workload-required source-specific semantic authority. Missing documentation does not become candidate discretion. If the exact required claim cannot lawfully remain typed `UNKNOWN`, return for A, B and C alike:

`BLOCKED__REQUIRED_SOURCE_SEMANTIC_AUTHORITY_MISSING`

Fifth, prove the candidate has a current physical binding to the common semantic surface. If common authority exists but only one candidate lacks implementation, return for that candidate:

`BLOCKED__CANDIDATE_RUNTIME_BINDING_MISSING`

Do not reclassify an implementation absence as source-semantic absence.

Finally, if candidates target different semantic owners or different workloads, return:

`BLOCKED__SEMANTIC_OWNER_DIVERGENCE`

No parity or performance court may run through that state.

## 3. When a preserved derivative is lawful

A preserved derivative may be consumed instead of reopening raw bytes only when all of the following are positively proved:

1. the exact canonical root `H` is named;
2. the derivative has an exact content identity;
3. an immutable parent receipt binds that identity to `H`;
4. the derivation operation and producer implementation are pinned;
5. the derivative determinant/scope covers the exact work it is being asked to serve;
6. replay or reopen validation binds it to the governed common semantic owner;
7. it claims no semantic authority of its own;
8. the candidate's physical policy permits that derivative class;
9. source-release and semantic-authority invalidation have not made it stale;
10. candidate ownership and permitted reuse boundaries are satisfied.

A derivative is therefore a reusable physical consequence of `H`, not a competing origin.

Successful downstream output equality is insufficient. Matching filenames, shapes, variable names, row counts, labels, or self-declared parent SHA values are insufficient.

Candidate A is permitted a durable transformed carrier under this law.

Candidate B is not permitted to replace its `SOURCE_BACKED_VIRTUAL_C11` empirical realization with a persisted transformed payload. It may reuse nonempirical authority/runtime assets, but fresh empirical realization remains source-backed.

Candidate C may preserve only an accelerator or derivative explicitly allowed by its policy and exact source/workload determinant scope. No derivative acquires an authority role because Candidate C uses it.

## 4. When raw-source reopening is required

Reopening the exact canonical raw root `H` is mandatory when any of these conditions holds:

- no lawful derivative exists for the required scope;
- the parent lineage of a derivative is missing;
- derivative scope is incomplete;
- derivative content/member identity fails;
- persisted state is stale or corrupt;
- source release invalidation requires regeneration;
- semantic-authority invalidation invalidates the derivative;
- the candidate's policy itself requires fresh source-backed reconstruction;
- Candidate C has no applicable accelerator, or its accelerator covers only part of the workload and no other lawful derivative supplies the remainder;
- fresh-process replay requires reconstruction and no admitted preserved state can satisfy it.

Raw reopening means reopening `H`. It never means selecting a same-wave file, producer-versioned file, historical DTA/SAV, compiled trend file, source-family glob result, or other apparent substitute.

If `H` is required and cannot be opened, return:

`BLOCKED__CANONICAL_RAW_ROOT_REQUIRED_BUT_UNAVAILABLE`

An unavailable accelerator is not grounds to weaken that rule.

## 5. Compatibility decoding is physical-only

The accepted compatibility cases are:

- EVS 1999;
- EVS 2008;
- LiTS I;
- LiTS II;
- LiTS III;
- LiTS IV.

For these sources the compatibility mode changes how the exact canonical bytes are physically decoded. It does not change which bytes are the root.

Compatibility decoding does not prove:

- intended source text encoding;
- text repair;
- response-state meaning;
- routing/applicability;
- topology meaning;
- weight/design/estimand meaning;
- cross-release equivalence;
- semantic certification.

If compatibility-decoded output is persisted, that persisted object is merely another derivative. It must satisfy the full derivative-lineage law.

If a candidate promotes the compatibility decoder or its decoded text to semantic authority, return:

`BLOCKED__COMPATIBILITY_DECODE_PROMOTED_TO_SEMANTIC_AUTHORITY`

EVS 1999/2008 documentary blockers remain blockers after successful physical decoding.

## 6. Candidate C zero-accelerator law

Candidate C's accepted policy is:

`SOURCE_BACKED_HYBRID_WITH_REGENERABLE_ACCELERATORS`

Its mandatory core is source-backed. Accelerators are optional and nonauthoritative.

The original Candidate-C lifecycle positively includes deleting all accelerators, starting fresh, executing cacheless/source-backed, regenerating, and reproducing the same governed truth/replay identity. Wave-2 L04 and Wave-3 I03 therefore prove that zero applicable accelerators is a lawful Candidate-C state.

S35-4 extends that proposition at the **policy** grain:

> For any future source already lawfully admitted to the common source-backed semantic spine, Candidate C is lawful in principle with zero applicable accelerators.

This is not an all-35 executability finding.

The statement does **not** prove that every CLOSED_35 source currently has:

- a source-specific governed projection;
- complete documentary authority;
- a Candidate-C runtime binding;
- a qualified C execution receipt.

It means only that lack of an accelerator is not itself a portability failure.

Candidate C remains C even when its physical work degenerates to the same source-backed realization B performs.

## 7. Why accelerator absence cannot authorize an alternate source

An accelerator is downstream of the source root. Its absence cannot alter the root upstream.

The lawful relation is:

`H -> optional governed derivative/accelerator -> candidate realization`

not:

`missing accelerator -> choose different source bytes`.

If CACC or any future accelerator is absent, invalid, stale, scope-incomplete or forbidden, Candidate C must use its lawful source-backed state from `H` if the common source authority and runtime binding exist.

If `H` is unavailable, C blocks.

If common semantic authority is missing, C blocks with A and B.

No missing accelerator can authorize:

- a historical alternate export;
- a different producer release;
- a harmonized/trend file;
- a compatibility-decoded saved copy as new source;
- a detached structural preimage with no parent receipt;
- a source-family filesystem discovery result.

Trying to use an accelerator as source or authority returns:

`BLOCKED__ACCELERATOR_USED_AS_AUTHORITY_OR_SOURCE`

## 8. Missing source-specific semantic authority

The source root proves physical identity. It does not automatically prove what every physical state means.

Source-specific semantic authority remains candidate-neutral.

Where accepted authority says the unresolved item may remain typed `UNKNOWN`, A/B/C must preserve the same typed `UNKNOWN`.

Where the current workload requires an assertion that cannot be made without missing documentary authority, all candidates receive the same common block:

`BLOCKED__REQUIRED_SOURCE_SEMANTIC_AUTHORITY_MISSING`

The seven Authority72 L2 sources remain exact examples:

- Afro Barometer Round 5;
- Afro Barometer Round 9;
- EVS 1999;
- EVS 2008;
- GSS 1972;
- GSS 1973;
- Latinobarometro 1995.

L2 is not a license for candidate-local interpretation. It is the opposite: the affected semantic grain lacks authority.

Therefore A may not encode one interpretation in a persistent carrier, B may not infer one from physical incidence, and C may not bake one into an accelerator.

If one candidate guesses while another preserves `UNKNOWN`, the court has changed the independent variable from physical realization to semantics and is invalid.

## 9. Common versus candidate-specific failure

The distinction must remain mechanical.

### Common source failures

These apply symmetrically to A/B/C:

- canonical root unproved;
- required source semantic authority missing;
- common semantic-owner surface unproved;
- workload identity unproved;
- canonical raw root unavailable when all lawful paths require it.

A common source failure must not be presented as a Candidate-C portability failure merely because C reaches it through fallback.

### Candidate-specific physical failures

These may affect one candidate without changing the common source semantics:

- A preserved carrier lineage missing;
- B runtime source-backed binding absent;
- C accelerator lineage/scope invalid;
- C zero-accelerator binding absent;
- candidate policy identity or persistence rules violated.

The correct result is a candidate-specific implementation/lineage block, while the common semantic authority remains unchanged.

This preserves the historical lesson from LiTS-C/WVS-C: a missing C execution binding was real, but it did not prove Candidate C lacked a lawful semantic scope.

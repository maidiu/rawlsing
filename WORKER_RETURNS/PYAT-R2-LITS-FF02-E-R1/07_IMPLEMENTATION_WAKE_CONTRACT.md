# Implementation wake contract

## Purpose

This contract prevents a future implementation commission from collapsing relation truth into PRE-V3 use merely because the current GT2 code combines them in one canary path.

## Wake A — Field Forge relation instantiation / publication / current selection

Production work may wake at this grain only when all are true:

1. **FF02-D exact preimage closure is green.**
   Required export includes exact candidate->DiscoveryResultReceipt refs, all required authority snapshots/per-object authority bindings, exact P2 bindings and checkpoint-only verification.

2. **HQ adopts the FF02-E constitution.**
   HQ must explicitly adopt the four family-specific neutral semantic clauses/rule identities and the relation/current-selection/permission separation.

3. **HQ authorizes bounded LiTS relation instantiation/current selection.**
   The implementation commission must be limited to exact retained LiTS objects and the adopted families.

Wake-A output may include:
- positive relation object;
- exact relation replay object/ref;
- explicit relation current-selection receipt.

Wake-A output must include **no PRE-V3 target-use admission by default**.

## Wake B — PRE-V3 relation-admission implementation

This remains asleep after Wake A unless:

4. a concrete downstream PRE-V3 consumer/contract is named;
5. an exact target-use semantic definition is adopted;
6. competent target-use permission authority positively grants that exact use for the exact relation family;
7. all use-specific prerequisites are exact-bound and positive;
8. family-specific admission rule identity exists.

Only then may a positive `PREV3_FIELD_FORGE_RELATION_ADMISSION@1.0.0`-shaped receipt be minted.

`STRUCTURAL_MEDIATION_INPUT` is unavailable unless mediation is separately earned.

## Wake C — downstream objective PRE-V3 producer

This remains asleep until Wake B has produced a positive exact admission receipt for the named consumer.

Relation currentness alone cannot wake it.

## One-module implementation caveat

HQ may later choose one bounded code module for engineering convenience, but that module must preserve three distinct states:

1. relation not instantiated/current;
2. relation current, no PRE-V3 admission;
3. relation current + separately admitted for one exact target use.

A module that requires a target-use token merely to instantiate/select a relation would violate this constitution.

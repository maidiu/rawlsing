## Precise nonadoption dispositions

### C3 G01 — nonadopt now

Reason: behavior already present; authority wrapper has no current production caller. Current decoder returns float64 for SAV numeric lanes; the six unique G01 float binding keys are reproduced directly by the current C11 facade. The exact nine-surface authority object is absent. Reinstating it would not change any current execution and would not close a current defect. It is a safe future authority-candidate, not a current source-access repair.

Owner if later pursued: C11 physical-binding owner; the accepted G01 authority material itself must remain byte-exact (`31a9afd7`).

### C3 D01 — nonadopt / HOLD

Reason: current `_compatibility_config` admits only the six exact-SHA latin1 compatibility lanes. The three accepted declared pairs (`ac0b8bc1 -> BIG5`, `5b703173 -> WINDOWS-1252`, `66252a92 -> WINDOWS-1252`) are absent. Restoring them requires a production decoder change (new declared allowlist and authority status) while preserving PR526 `_SourceSnapshot`. No current consumer uses those sources; raw source SHAs are source-authority-held here. Do not monkeypatch `_compatibility_config`, do not pass a raw path, do not bypass the snapshot.

Owner: PRE-MAIN physical-decoder owner plus native source authority.

### C3 D02 — nonadopt / HOLD

Reason: current decoder `_jsonable` stringifies built-in date/time; current R5 codec `encode` rejects date/time and has no `opaque_decoder_value`/`normalize_decoder_physical_value`. Restoring D02 requires both decoder `_physical_value` and codec opaque constructor/normalizer changes in production. A WR-only adapter cannot reach the pre-`_jsonable` value without duplicating decoder source access. No current consumer for the observed affected source 14; source authority absent.

Owner: PRE-MAIN decoder and R5 codec owners plus native source authority.

### Accepted C3 R5 codec 6000a170 — nonadopt wholesale

Reason: current codec `72f8f3c` is a later revision used by all current tests and the current decoder. The historical codec differs only by the D02 opaque constructor/normalizer. Replacing the current codec with the historical blob would not add a current consumer and would create a second codec authority. If D02 is later authorized, the minimal move is the two D02 functions on top of current `72f8f3c`, not a wholesale codec transplant.

### R9 broker/session/execution-binding — nonadopt / HOLD

Reason: the modules are absent and have no current importer. The historical broker opens the raw source path with its own `GovernedSourceOpen`, while current PR526 creates a private content-bound snapshot, hashes it while copying, reads through `/dev/fd`, checks stability, unlinks, and closes idempotently. Running both would create two competing source-access authorities. The historical R9 decoder (`b406d45f`) also differs from current PR526 (`8732e34d`) and requires `decode_in_session`; transplanting it would revert PR526 and is forbidden. Direct measurement in the reconstructed R9 tree showed the historical decoder breaks 6 current SAV representation tests (in addition to the two SR06 seam tests HQ204 recorded and HQ207 resolved in the accepted lineage).

No current production caller exists for `SourceAccessBroker`, `GovernedSourceSession`, `BoundSourceExecution`, or `decode_in_session`. No real issuer/role owner exists; `TestOnlyDecisionResolver` is a test double and cannot be promoted. The current `IssuedWorkloadRecord` has no role field.

A future nonduplicated R9-successor would have to be built on top of the current `PhysicalSourceIncidence` custody (not a second raw-path broker), consume an externally authenticated issuer/role record, and be called by a real current consumer. That owner is not present in this scope.

## Why no `MINIMAL_CANDIDATE_AND_TESTS/` was produced

The only candidate that could be written without production writes is a test-only wrapper. That is exactly the forbidden "test-only mock represented as production". The alternatives are:

1. write production decoder/codec changes — not permitted here; PRE-MAIN write is forbidden;
2. create a second source broker/path-open layer — conflicts with PR526 custody and has no consumer;
3. self-assert issuer/role — forbidden fake caller/issuer;
4. reinstate G01 authority only — safe but no current receiver and no behavior change; not a warranted source-access compatibility fix.

Therefore nonadoption is precise and complete at this scope.

## Conditions that would reverse nonadoption

- A current C11/receiving owner explicitly calls a G01 authority object, making it non-test-only.
- PRE-MAIN authorizes D01/D02 production edits with exact source authority and a current consumer for the affected sources.
- A real current issuer/role owner and a current session/broker consumer exist, and the successor can be implemented on PR526 `_SourceSnapshot` without a second source-open authority.

Until then the correct engineering verdict is HOLD, not adoption.

Module surfaces for parallel work
- engine.py defines BatchEngine(owner, journal_path), run_batch(batch_id, proposals), history(batch_id), and verify(). The owner is exposed as engine.owner for coordinator identity checks. Batch IDs and event IDs are nonempty and uniquely bound to immutable proposal material. Completed same-input replay returns the same stored result; conflicting reuse refuses. run_batch returns {batch_id, history_hash, records}; records are RealizedEvent.document() rows augmented with event_id. history_hash is digest(records). history(batch_id) validates stored chain and current source-bound owner identity as applicable, then returns the same shape. verify checks the journal and owner linkage. Journal writes are atomic and serialized. Interrupted steps retain durable reservations and resume only via owner's idempotent operation protocol.
- model_cycle.py defines RecursionCycle(engine, provider, store_path), bootstrap(context=None), advance(context=None), finish(context=None). A separate durable cycle store binds pending/retrospected batch, expected owner state, model-call reservation and next batch sequence. A provider/engine failure never marks a preceding batch retrospectively complete or duplicates effects. An ambiguous prior provider call is held without blind reissue. Each method returns the persisted realized batch (bootstrap/advance) or final retrospective record (finish).
- A model request is {mode, context, previous}. previous is null for bootstrap, otherwise {batch_id, history_hash, events}, where events is [{event_id, accessible}] in realized order. Context must not carry a state writer; input is detached JSON. Retrospective output is {batch_id, history_hash, event_ids, impressions}. A prospective output is a list of EventProposal documents. Only the keys retrospective/prospective are accepted. Impressions stay proposals. Bootstrap requires retrospective=null; terminal requires prospective=null. Ordinary requires both. Provider-caused owner-state change refuses and preserves ambiguous custody. Tests must bind reconstruction to source result history, not prospective prose.
- Core statuses are REALIZED, IMMEDIATE_ONLY, NO_CHANGE, HELD, REFUSED, OMITTED. Consequences retain their native owner's status, including MISSING_RULE. HELD/REFUSED/OMITTED do not become evaluated NO_CHANGE. Only authorized owner APIs can mutate state.

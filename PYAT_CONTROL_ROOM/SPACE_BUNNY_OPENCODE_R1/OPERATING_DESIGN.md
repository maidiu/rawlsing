# Pyat: OpenCode operating design and route to completion

Prepared 2 October 2026. Status: **PROPOSED OPERATING DESIGN — NOT AN ISSUED COMMISSION OR EXECUTION WARRANT**.

Run Space Bunny as the actual executive HQ in OpenCode, with bounded worker sessions, independent review and a small deterministic dispatcher. Keep accepted project state in Git; use local processes for execution and fast communication. Use Sol/Astra for selected consequential decisions rather than every handoff.

The objective is accepted functional progress per unit of elapsed time and human attention. More agents, more reports and more tests are not themselves progress.

## 2. What completion means

The destination is the composed empirical-social possibility service: distributions and bidirectional conditioning; minority/counterpattern and recursive branches; empirical co-travel and governed joint configurations; lawful structural content; multiple distinct source fields; authorized temporal comparison/pressure; and progressively conditioned positioned-subject possibility with current/historical serving, permissions and replay.

C9 must establish F1–F8 at the declared estate scope, retaining all 35 identities and every mandatory unresolved obligation. C10 then makes the explicit PRE-V3→V3 wake or continued-deferral decision. Actor implementation is a separate later commission. A correct refusal does not satisfy a required positive result, and an empty world is not mature simply because its negative cases pass.

Use the adopted [functional acceptance law][law] and the [forward program][program] as the destination. The atlas's draft commissions identify work; they are not blanket implementation or source authority.

## 3. Division of labor

| Role | Owns | Does not own |
|---|---|---|
| Space Bunny HQ | Priorities, exact commissions, dependency decisions, adjudication, integration requests, accepted state and next dispatch | Inventing semantic authority, bypassing raw-source gates, silently expanding a commission |
| Worker A | The highest-priority ready implementation or exact repair | Accepting its own work or changing shared control state |
| Worker B | An independent implementation, evidence-binding or downstream-preparation task | Concurrent edits to Worker A's files without an explicit integration arrangement |
| Fresh hostile reviewer | Contract satisfaction, genuine counterexamples, evidence sufficiency, and consequential claims added by HQ | Requiring unrelated improvements or producing a defect quota |
| Governed source runner, activated only when warranted | One exact source workload on its qualified host/runtime, including failure preservation | General exploration, automatic retries or changing expected truth |
| Sol/Astra, on demand | Novel authority questions, unresolved consequential disagreement, major maturity transitions and sampled decisions | Routine polling, every worker handoff or acting as a second simultaneous HQ |
| Deterministic dispatcher/integrator | Worktree/session mapping, locks, event delivery, manifest checks, publication and transition mechanics | Deciding whether evidence proves a sociological or semantic claim |

Start with **two worker slots and one review slot**, plus HQ. The source runner replaces a worker slot during measured execution. Increase concurrency only when ready independent work and host resources support it. A waiting review takes priority over starting another low-priority implementation. Serializing adoption does not require serializing investigation or implementation.

HQ remains an executive: it chooses what to build next and resolves routine decisions within its commissioned authority. The dispatcher handles repetitive mechanics so HQ does not spend reasoning turns polling branches, copying text or assembling manifests.

## 4. GitHub, local Git and the source estate

Use an explicitly named operations checkout and one worktree per active commission. Do not convert, reset, clean or overwrite the Desktop Rawlsing artifact estate. Source carriers and large retained custody remain in their established stores, outside the operations checkout and outside routine worker access.

Local Git is the working surface. GitHub is the durable publication and cross-machine retrieval surface. Accepted state is the exact Git object and HQ decision, not a chat message, a green CI badge or a branch name alone.

Each commission binds its correct implementation base. Do not start every worker from the control branch merely because it has the latest documentary commits. Freeze exact evidence refs, including non-ancestor inputs; fetch them before dispatch. This directly removes the missing-reference setup problem seen in the model comparison.

Workers commit only their permitted terrain on their own branches. An integration service publishes exact branches and verifies remote heads. Only HQ-authorized integration can advance accepted implementation branches or control state.

**Mandatory commission I/O law:** every issued worker/reviewer commission must tell the agent to fetch `origin`, verify the exact remote worker branch and commissioned startup SHA, work from an isolated worktree at that exact tip, and stop if the remote tip differs. Every return must be committed, pushed to the same worker/reviewer branch on GitHub, re-fetched, and verified so local HEAD equals the exact remote return SHA. A local-only commit or chat completion is not a return. Blind `git pull`, implicit merge/rebase, self-publication into control, and force-pushed returned history are prohibited unless a later explicit HQ commission narrowly authorizes the required operation. A commission missing startup or remote-return binding is malformed and must not launch. Preserve the existing commission-specific merge/import law: ancestry-preserving merge where required; exact path/blob import for documentary evidence where required. Do not globally substitute cherry-picking or rebasing for those rules.

**Worktree retention law:** one worktree per active commission is an execution-isolation mechanism, not a retention strategy. Once a worker/reviewer return is pushed, remotely verified, HQ-routed, and no active process/successor still needs that checkout, the worktree should be audited for unique local residue and removed through `git worktree remove`. Unique local substantive deltas must first be committed/pushed or explicitly salvaged outside the repository; disposable caches do not justify preserving a full checkout. Historical returned worktrees should not accumulate inside the canonical checkout. Use a dedicated disposable worktree root where practical. Never treat this law as authority to delete LOCAL_COURTS, source estates, shared toolchains or user documents.

Review a frozen candidate SHA. Any subsequent candidate change makes the existing review inapplicable to that change. If the integration base moved, assess the actual touched dependencies and conflicts; documentary-only movement does not justify repeating an unrelated court. Conflict resolutions that alter reviewed behavior need a new candidate and bounded re-review.

For every authoritative transition:

1. Acquire the single HQ/integration lease and verify the expected control head.
2. Validate the candidate, review and accepted prerequisite identities.
3. Integrate by the commissioned law and run the necessary integration checks.
4. Record the decision and new immutable checkpoint, including active workers and dependency edges.
5. Bind manifest blobs, then advance `LATEST` to the packet commit under the existing protocol.
6. Publish and re-fetch the remote pointer/objects. Only then mark the transition sealed and wake dependent work.

A failed or ambiguous push is a publication uncertainty, not permission to repeat integration blindly. Inspect remote state first. Retain local results during an outage, but do not announce remotely sealed authority.

Pull requests may provide a useful review interface for substantial code batches. Do not add a compulsory PR, issue and comment workflow on top of every already-governed return. GitHub comments are notifications; accepted manifests and decisions carry the authority.

## 5. Agent communication without the user as courier

Use a hub-and-spoke topology. Workers report to HQ through structured events. Direct worker questions may clarify a shared contract, but any change to scope, interface, base or authority must be recorded by HQ before dependent work uses it.

OpenCode supports custom primary/subagent roles and per-agent permissions. Its documented server exposes session creation, asynchronous prompts, status and event streams. Locally, OpenCode **1.14.33** was verified; `run --help` supports `--agent`, `--dir`, `--session`, `--format json`, `--attach` and `--variant`. These are the integration primitives, not a claim that the proposed Pyat dispatcher already exists. [Agents][oc-agents], [server][oc-server], [CLI][oc-cli].

For substantial work, dispatch separate OpenCode sessions explicitly bound to their own worktrees. Do not assume invoking a subagent creates an isolated checkout. Use built-in subagents for small read-only questions where separate Git state is unnecessary. Verify actual directory, effective role, model and variant at launch. The model-catalog command failed in this assessment, so the provider/model ID remains an activation-time check; do not invent it from the display label.

The first dispatcher can be a small local wrapper around the installed CLI, capturing JSON events. Add a persistent authenticated loopback server when it reduces startup overhead. Inspect the installed server's API schema before coding its directory/session routing; online documentation is not proof of exact installed behavior. Never use a bare `--continue` to choose a worker in concurrent operation: store the explicit session ID.

Implement only a few bounded operations: prepare assignment, start worker, obtain status, deliver clarification, submit return, start review, publish artifacts, seal an HQ decision. Do not build a second general agent framework.

A task record should contain:

```text
task_id, commission_revision, attempt_id
role, session_id, host, worktree, branch, base_sha, commission_sha
input_manifest, allowed_write_paths, source_permission, runtime_identity
acceptance_cases, expected_oracle_refs, reviewer_assignment
dependency_ids, pass_wake, blocker_effect, state
result_sha, review_sha, decision_ref, last_event_id
```

Events are small: `STARTED`, `NEEDS_INPUT`, `BLOCKED`, `RETURNED`, `REVIEW_RETURNED`, `ERROR`, `CANCELLED`. Include task/attempt identity, sequence or event ID, timestamp and exact result reference. A completion message points to an artifact; it does not paste the entire transcript into HQ's context. Store full logs for investigation outside ordinary HQ context, with restricted access for source-execution logs.

Use a transactional local queue with one dispatcher writer and deduplicated event delivery. Git carries accepted task transitions; the queue is a recoverable operational projection. Resume from durable task/session/commit identities after interruption. An idle session or closed process is not automatically a completed task.

## 6. State, context and scheduling

Preserve the existing authoritative chain: decision ledger → sealed checkpoint → `LATEST`. Maintain one reconciled operational frontier derived from it and pending authorized returns. An event cannot declare itself adopted.

Suggested task states:

```text
PROPOSED → READY → COMMISSIONED → RUNNING → RETURNED
→ REVIEWED → ADJUDICATED → INTEGRATED → SEALED
```

Maintain separate `BLOCKED`, `CANCELLED` and `SUPERSEDED` states. READY means prerequisites are present; COMMISSIONED means the actual bounded work is authorized. Keep observed returns separate from accepted dependencies.

A fresh HQ receives the checkpoint, operative frontier, unresolved decisions and named pending returns. A worker receives its exact commission, input manifest and relevant acceptance cases. A reviewer gets the contract and source evidence before the author's preferred conclusion. Avoid full-history forks for independent review.

Allocate work by: critical-path unblocker first; review of a completed critical return second; ready downstream work third; useful independent evidence preparation fourth. Do not fill slots with speculative architecture work. Limit shared-file ownership and permit only one measured source job on the anchor at a time until resource evidence justifies more.

Coalesce simultaneous completion notices into one HQ turn. Trigger HQ on meaningful events instead of asking it to poll constantly. A lightweight process may check liveness without spending model turns. A quiet model is not presumed hung; inspect process/session/tool state before interruption.

## 7. Quality controls aimed at the observed failures

Every substantial implementation receives independent review. Routine acceptance does not require a second full review of the reviewer. A short additional check applies when HQ adds a new load-bearing claim, reclassifies a blocker, changes authority, or widens a proof grade.

Keep a compact decision table:

| Claim | Exact source | Observed / inherited / inferred | Proposed consequence | Check |
|---|---|---|---|---|
| The fact that changes this decision | Commit, path and field or lines | Explicit classification | What becomes allowed, blocked or accepted | Counterexample or independent corroboration |

This targets the Space Bunny HQ errors already observed: changing a quotation while labelling it verbatim, treating complete Git identifiers as truncated content hashes, and treating implementation uniqueness as sufficient evidence of adoption.

Automate mechanical checks where possible: quote matches; schema-specific SHA-1 versus SHA-256 typing; committed-file allowlists; parent/base identity; manifest verification; full commands and exit codes; test denominator and skips; input freshness; candidate/review binding. These checks cannot establish semantic authority or prove that no unlogged file access occurred.

Require the reviewer to state the violated acceptance clause, exact evidence, scope and minimum repair. Accept no demand for unrelated polish. After one normal repair/re-review cycle, another substantive disagreement should trigger a narrow HQ diagnosis of the contract or premise; do not launch endless slightly rewritten reviews. Necessary repairs can still continue under an explicit revised commission.

An outside model examines major authority transitions, architecture exceptions, unresolved consequential disagreements and a rotating sample of normal acceptances. Sample some apparently easy passes; Space Bunny cannot be the sole detector of its own unnoticed errors. Different models provide another perspective, not an automatic truth oracle.

## 8. Safety with minimal recurring permission friction

Authorize routine reads, scoped edits, source-free tests and branch publication once through a concrete commission and capability profile. Reserve human intervention for genuinely new scope or authority, exact source warrants, destructive operations and final seam decisions. Do not repeatedly ask for already authorized steps.

OpenCode permission rules can restrict tool use by role, but worktrees and prompt instructions are not security boundaries. A worker with an unrestricted shell and the user's credentials can escape a conversational write restriction. For actual enforcement, isolate source-free processes from raw carriers and integration credentials using host permissions or a suitably isolated execution account. Give the publisher/integrator the credentials and only bounded operations. Scope OpenCode permissions as an additional layer. [Permissions][oc-permissions].

The source runner gets only the exact warranted paths and qualified environment. Local filesystem availability never implies permission to stat, hash, enumerate or decode carriers. HQ can remain aware of source custody through approved manifests without inspecting raw storage.

Do not move a qualified Darwin workload into a different container/runtime and assume its qualification survives. Any host or interpreter isolation change must preserve the declared surface or undergo the required bounded qualification.

On source failure, preserve the failed root and its logs. No automatic task restart, infrastructure retry or model fallback may silently replay a governed source operation. First determine whether any source work happened; follow the issued failure law and obtain new authority when required. Source-free resumptions also inspect existing commits and task attempts before restarting to prevent duplicate work.

Same-account role separation is procedural unless technically enforced. The activation exercise must demonstrate the chosen enforcement rather than merely asserting it in prompts.

## 10. First activation batch and acceptance test

Suggested bounded implementation order:

1. Reconcile the live frontier and record the change from browser-led to OpenCode-led operation. Preserve prior decisions and unresolved authority boundaries.
2. Establish role profiles, task/session/worktree mapping, one integration lease, a structured return contract and deterministic validation/publication helpers.
3. Exercise the dispatcher with a small source-free task: dispatch two disjoint branches, review one frozen return, reject an out-of-terrain result, resume after interruption without redispatch, and verify the sealed remote state. Use disposable fixtures, never real raw carriers, to test permission denial.
4. Have HQ prepare one bounded C4 reconciliation: preserve both reviewers' useful findings, correct the HQ quotation/hash-type errors, resolve issuance binding and runtime-preservation requirements, and distinguish those from freeze acceptance.
5. Once authorized, complete that adoption/warrant path while commissioning only demonstrably ready downstream source-free tasks.

Do not launch the entire C5–C8 graph at once. Start two workers, keep review capacity available, and expand only when accepted throughput improves.

Operational readiness requires evidence that: the wrong directory/base is rejected; source-free jobs lack raw access; candidate changes invalidate review; two HQs cannot publish competing state; duplicate events do not duplicate execution; unexpected branch movement blocks only the affected transition; and a successor HQ can resume from the checkpoint without reconstructing a transcript.

## 11. What the user sees and how success is measured

The ordinary HQ report should fit on one screen: newly accepted capability; current critical path; workers/reviews in progress; precise blocked premise; the next already-authorized action; and any decision genuinely needed from the user. No unchanged polling reports.

Record assignment-ready, dispatch, first activity, return, review return, adoption and remote-seal timestamps. Separate model/tool activity, provider delay, human wait and repair time. Keep unknown idle causes unknown. Measure accepted critical-path progress, human interventions, review escape defects, unnecessary blockers and reopen rate.

Begin with several real commissions plus targeted hostile fixtures. This is a practical calibration period, not proof that rare executive errors are impossible. Continue sampling accepted decisions after the initial period.

Record the actual provider/model ID and reasoning variant per attempt. While Space Bunny is free, use that capacity to reduce queues and improve review coverage. Do not let the workflow depend on its continued availability: portable Git contracts and returns should let another capable OpenCode model resume the role. On a model change, run the small executive-error regression set before restoring the same autonomy. Never silently switch models mid-governed source run.

## 12. Delivery and limits

This file is the design deliverable. No OpenCode configuration was changed, no dispatcher installed, no agents launched, no GitHub records mutated and no source execution authorized by this assessment. The source tree and local CLI were inspected read-only, apart from creating this document and ordinary CLI internal logging. The installed model listing failed with an OpenCode database checkpoint error; it was not retried or repaired.

The design can preserve the present acceptance standard while removing handoff friction, but cannot guarantee identical error rates before it is exercised. Its central protection is to make consequential executive claims checkable and to make permitted work automatic once its prerequisites are genuinely satisfied.

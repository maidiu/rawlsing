# 12 — How the ANVIL workshop will reach ONE defensible whole-machine architecture

**Purpose:** Provide a repeatable, rigorous procedure for future reasoning that neither lets considerations disappear nor traps the user in endless status reports/architecture bakeoffs. The user's immediate mandate is **save and interrogate**, not launch workers, mutate production, or declare final selection.

## 1. Begin from the most demanding terminal consumer

Use [06 downstream requirements](06_DOWNSTREAM_REVERSE_REQUIREMENTS.md), the 27-row original PYAT product obligations, and actual owner code/callers. For every stage from source to SOROK two-event continuing-person read, answer:
- What must be materially **produced**, not just represented or logged?
- What exact source, sample, question/role, uncertainty, population/time and power information does it require?
- What are the scientific categories/claim ceiling and typed negative states?
- Which earlier product does it actually **read**; which declared interface has no real consumer?
- What intermediate data can be shared across distinct scientific investigations?
- What can be economically regenerated, what must persist across crash/as-of/cold reopens, and what can never be invented after early projection lost it?

Record the answer with exact source file@SHA and consumer. If an important source/consumer is inaccessible or science unresolved, mark `UNKNOWN/OWNER_REQUIRED`, not `ABSENT`.

## 2. Simultaneously reverse-derive the pre-FORGE functions

Consult [05](05_PRE_FORGE_FUNCTION_INHERITANCE.md) and [09](09_1097_VERBATIM_HISTORICAL_LEDGERS.md). For each **meaningful operation**, map:
`source + population + authority + valid estimator → computation and reused intermediates → output+negative → downstream first consumer → modern current equivalent / necessary repair`.

Do not copy old bad formulae. If no downstream operation needs a historical output, explicitly propose scientific retirement/keep as diagnostic with owner rather than silently erase it. Stop searching when the functional obligation is decided from sufficient exact evidence, not after arbitrary exhaustive repository excavation.

## 3. Build the factor and contradiction map

Work through every row in [08](08_FACTOR_COURT_AND_OPEN_DECISIONS.md). Cluster factors that constrain one another:
- complete but compact C11 versus future unanticipated source role data;
- shared prep versus exact per-query provenance/output;
- immutable release integrity versus live source CURRENT revocation;
- one respondent universe index versus cross-source nonpooling and temporal comparison;
- sourcefree optimized throughput versus lawful real-wave/actor evidence;
- statistical inference versus structural/material-power claims;
- same-person joints versus combinatorial full-domain explosion;
- immediate product utility versus long-term science/extension.

When two objectives genuinely conflict, state who pays the cost and which invariant cannot be relaxed. **No rhetorical “all optimized” outcome.**

## 4. Reason quantitatively *before* making competing implementations

For candidate architecture A, estimate orders of growth for:
- writer source/proof passes, per-object encode/canonicalization and scratch;
- cold source/member verification and derived-index rebuild;
- distinct question variables, respondent access, eligible/observed masks, multi-target joins, recursive branches, per-result read amplification;
- output/ref/replay materialization, aggregate whole-process RSS and disk;
- retained/derived storage and restart/invalidations;
- integration/owner/science change risk.

Use actual measurements from [02](02_SYSTEM_AND_MEASURED_STATE.md) **only when they measure the same path**. Predict relative outcomes from dataflow and complexity; no fabricated 2×/10× promises. If a specific uncertainty could reverse the decision, identify **one tiny differentiating probe**—not two full systems in a bakeoff.

## 5. Strongest-alternative adversarial analysis

For each plausible serious alternative, write:
1. Most persuasive reason to choose it.
2. Strongest *realistic* downstream scenario where it beats the favored design.
3. Worst risk to scientific trust, performance, recovery and compatibility.
4. What old tested code it reuses or strands.
5. Exactly which existing invariant it would threaten.
6. Why the chosen design should still win, or why the decision remains genuinely unresolved.

Eliminate untenable alternatives by logic when possible; do not cherry-pick favorable benchmarks. If an accepted schema is fundamentally preventing required function, **allow reconsideration**, but show the exact unrepairable condition before abandoning it.

## 6. Settle semantic object boundaries before physical indexing

The computational substrate needs explicit identities for:
- immutable source and C11 reference truth;
- respondent-local physical addresses and reversible refs;
- eligible/asked/observed/condition/branch membership and typed negatives;
- same-person response patterns, domain/denominator and estimator;
- provenance/replay/authority closure of each intermediate;
- cross-universe source/science relation and time/as-of;
- actual owned FF/N9/N10E/N10W/PRE-V3/SOROK claim-grade gates;
- planned v1 output compatibility and any separately versioned prospective witness.

These can collapse into fewer implementation types, but must not collapse their **meanings**.

## 7. Make one architecture decision; then implement and falsify

The final ANVIL decision record (not yet written) must include:
- one coherent architecture diagram from source decode through the true first consumer;
- data model, persisted/ephemeral boundaries, proof and release/CURRENT points;
- endorsed query/analysis execution strategy and incremental reuse;
- complete known downstream need/legacy function coverage and explicit unknowns/rights holds;
- why it wins the analytic alternatives court;
- exact code owners, reuse-first repair plan and consumer changes;
- realistic memory, disk, CPU, output and disaster recovery expectations;
- **finite tests targeted to falsify the selected design**, with negative typed fates and actual first readers;
- clear user/owner decision and whether the solution is provisional or adopted.

Do not turn the analytic process into a new HQ or parallel PROGRAMMA. Qualified code/science/authority/integration/protected receiving still lives in original jurisdiction. Existing workers may finish scoped useful repairs independently, but ANVIL must not preempt their files without verified lease.

## 8. Conversation discipline for the next ANVIL sessions

The user needs an intelligible **concept** of each proposed stage and consequence, not merely a list of module names. Explain each critical entity in plain language with a real-world survey example; then connect it to exact code and ask the uncomfortable question. The user must be able to challenge assumptions and suggest alternatives. Keep one stable idea/objection/decision ID and update its argument history rather than rewriting it away.

Suggested sequence: (i) reverse-consumer full requirements, including material world and SOROK; (ii) recovered DDM operations and scientific corrections; (iii) exact source→C11 information sufficiency; (iv) reusable analytic objects/semantics; (v) performance and trust boundary; (vi) design alternative court; (vii) one chosen design + limited falsification.

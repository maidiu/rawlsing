## What ANVIL is for

The user's essential question: **Given every existing/stranded scientific function, downstream consumer, correctness obligation, authorization boundary, and physical resource constraint, what is the most intelligent possible arrangement of C11 and the computational/analytical machinery around it?** Existing design decisions are open to criticism; **no systematic deficiency can be hidden by optimizing the implementation of today's narrow I03 interface**.

This workshop serves four duties:

1. **Conservation of argument:** record every consequential suggestion, why it seemed plausible, what falsified or qualified it, and what remains useful—even if the candidate was rejected.
2. **Conservation of function:** do not confuse preservation of survey data with preservation of the old DDM's extraction-sharing, respondent-level analytics, branches, co-associations, signed/contextual constructs, temporal transformations, provenance and actual downstream utility.
3. **Epistemic grading:** visibly separate examined code; observed independent execution; author-reported measurements; historical reconstruction; scientific desiderata; architectural deduction; and untested hypotheses.
4. **Conclusive reasoning before building:** analytically eliminate weak structures and choose the strongest defensible design, then run **minimal falsifying implementation tests**, not days of competing bake-offs.

## The workshop's decisive distinctions

- **Evidence ≠ output ≠ scientific claim ≠ authorization.** An immutable source can be faithfully preserved yet scientifically misinterpreted. A correct condition can be measured yet wrongly promoted to causal or structural law.
- **Canonical C11 ≠ execution index ≠ prepared cohort ≠ issued scientific fact.** Derived structures do not acquire independent authority.
- **Functional conservation ≠ algorithm resurrection.** Old DDM functions must be recovered where valuable, but false denominators, mislabeled mutual information, degenerate branch masks, and other defects must not be copied.
- **Current interface ≠ full ultimate requirement.** I03/I05/F1–F4 as currently implemented are not a sufficient specification of all future analytic consumers, nor of N6/N9/FF/actor-world semantics.
- **Historical observation ≠ current code fate.** An old PR's failure to have an operation is not proof that today's exact code lacks it.
- **Candidate ≠ accepted ≠ protected.** New local/pushed prepared-index code is not accepted by itself; user intent is not a scientific issuance.

## Non-negotiable workflow

**Nothing in ANVIL is an adopted architecture.** Entries can be marked `OBSERVED_CODE`, `AUTHOR_REPORT`, `HISTORICAL_SOURCE`, `DOCUMENTARY_RECONSTRUCTION`, `ANALYTICAL_INFERENCE`, `DESIGN_CANDIDATE`, `REJECTED_AS_PROPOSED`, `OWNER_DECISION_REQUIRED`, or `UNKNOWN`; do not silently upgrade.

Every proposed structural change must answer: (a) what end consumer needs it; (b) which actual code/path owns it; (c) what redundancy or scientific loss it removes; (d) what new trust/identity/recovery risks it creates; (e) why it beats the strongest realistic alternative **on reasoning before coding**; (f) the smallest executable failure test. Record counterarguments and reversals in place. Do not create another living PROGRAMMA or overwrite paired CURRENT_PROGRESS. Qualified owner receiving remains required for any actual controlling change.

**Snapshot provenance:** This R1 banks the user's continuous current-chat design discussion and separately linked GitHub source material through 2026-11-16. It is not a verbatim export of every prior historical chat, not an independently executed integration, and not a guarantee that unknown future downstream scientific obligations have been enumerated. The explicit objective of the next workshop is to discover and decide those remaining requirements, not to pretend they are already known.

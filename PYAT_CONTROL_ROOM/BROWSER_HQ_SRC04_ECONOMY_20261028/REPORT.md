# Browser HQ handoff: SRC04 PRE553 scope, storage expansion and execution economics

**Date:** 28 October 2026, America/New_York. **Purpose:** support the user's architectural/engineering discussion; no new architecture or scope is adopted by this packet.

## 1. Decision needed, in plain language

Rawlsing needs to turn survey answers into usable, traceable evidence about human circumstances, dispositions, combinations and variation, then use that evidence in its world/possibility/persona pipeline. PRE553 is responsible for substantial empirical and analytical work. It is not merely an importer or a cleaned survey file.

The present SRC04 implementation has successfully produced and independently source-checked its native input release. It has also computed all 177 individual-question summaries and 31 two-question joint tables. It has **not** finished the declared pairwise catalogue, the broader PRE553 analytical programme, or an actual original-data consumer effect.

A 1.53 MB survey has become a **7,911,048,750-byte local native bundle**. The empirical execution then processes each pair through an expensive general-purpose query/fact/replay path. The author stopped a real run after measuring an estimated 20–43 hours remaining for its current joint-table queue. These are implementation costs, not demonstrated intrinsic requirements of the scientific task.

The requested discussion is: **what is the smallest rational, economical implementation that preserves the inherited analytical capabilities, evidence meaning, exact replay and source/privacy limits?** Examine the existing owners and predecessor shared-data machinery before inventing a replacement. Do not silently redefine PRE553 as pair counting, or solve performance by dropping the project’s analytical obligations.

## 6. Why empirical execution is slow

See `04_CURRENT_EXECUTION/.../native_streaming.py`, `native_workload.py`, `pre553_empirical_query.py`, `_pre553_query_eval.py`, and `actual_carrier.py`.

1. The execution loader hashes/checks the accepted carrier, unpickles native objects and validates their identity. The new bounded view discards routing/coordinate payloads it cannot use for this observed-response workload, retaining answer events, respondents and required identity/authority material. It is a transient view, not a new scientific release.
2. The runner enumerates 177 unary operations and every unordered pair of 177 response targets: **15,576 pair operations**. It submits each separately to `execute_empirical_query` (I03).
3. Each query still evaluates respondents and constructs native facts/replay/dependency material for its exact scope. `_make_execution_replay_ref` includes risk and denominator membership and complete cells; `_build_fact` collects provenance/dependencies and constructs an exact fact. This is much more work than incrementing a compact two-column frequency table.
4. Repeated work was partially repaired: cached release indexes, exact target-event indexing and contract projection reuse. The remaining per-operation work is still expensive. A streaming wrapper limits retained query/results memory; it does not turn the statistical kernel into shared batch computation.
5. `pre553_batch_runner.py` is a deterministic scheduling/resume framework for already-authorized jobs. It is **not evidence of an optimized multi-query counting kernel**. Using that runner alone would not establish that these repeated costs disappear.

The source has about **114.3 million respondent × pair positions** (7,337 × 15,576) before handling domains/provenance. That arithmetic alone is not an inherent multi-day calculation. It also is not a benchmark or proof that the full governed products can be produced in a particular number of minutes.

Some numeric fields have hundreds of distinct observed values. The code constructs domains and complete cell projections. Examine the cost of unobserved Cartesian combinations and explicit zeros as well as respondent iteration. The packet does not contain a full timing/memory profile proving which cost dominates; “provenance is the bottleneck” would be too categorical without that measurement.

## 8. An important semantic/scope issue in the latest runner

`native_streaming.py` executes all pairs, but only **one explicit conditional** for the consumer. It states that complete joint-cell projections represent both directional conditionals. That can be a useful computational reuse principle, but it is not a blanket equivalence proof:

- Conditioning on a particular answer requires the correct observed/common denominator and missing/state policy.
- Joint support can yield both directions under matching contracts; differing eligibility, routing, weights, topology or branch conditions require their own treatment.
- A mathematical possibility of deriving a conditional is not the same thing as a published, resolvable conditional product that the consuming API can actually use.
- Pairwise tables do not by themselves encode every higher-order combination, recursive branch, contextual claim or warranted structural role.

The latest changes have not yet independently established this complete conditional-service claim. Browser HQ should decide whether the intended product is a reusable joint-backed query service, precomputed native conditional products, or another existing lawful owner route. Avoid adding a new semantic promise merely to make the queue cheaper.

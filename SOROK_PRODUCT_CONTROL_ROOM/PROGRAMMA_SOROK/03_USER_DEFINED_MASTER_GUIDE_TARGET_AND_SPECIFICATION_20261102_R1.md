## 1. One-sentence end product

PROGRAMMA SOROK is a **lean, comprehensive, source-linked master guide to finishing the Sorok side of Rawlsing**. A fresh authorized agent should arrive at its control room, gain the whole- and middle-scale project picture promptly, follow exact references to prior research and real code, determine which versions exist and what they actually achieve, follow prerequisite and consumer relationships, see the health of material interfaces, identify concrete missing work, and intelligently start the next productive Sorok assignment **without reconstructing the entire repository or unknowingly reimplementing work already done**.

It is a *guide to building Sorok*, not a thing that generates a Sorok person. Descriptions of actors, world, memory, LLM rendering, historical development, S0–S16, C/A/M/N/O/E, etc., are the SUBJECT MATTER OF THE GUIDE. None is a PROGRAMMA delivery requirement in its own right. Likewise the guide need not be conversational, clickable, deployed as a service, or continuously active. The user's language of zoom, maps, clicking, navigating, edges and space means **organized references and causal/functional relationships**, not a mandate for a graphical user interface.

### Highest-priority practical questions

Given any substantial item X, find:
1. **What and why?** Plain meaning, original product/architecture context, containing section(s), exact current best description.
2. **What already exists?** The best presently relevant implementation, applicable architecture, historical variants, source documents, prior work, code/test artifacts, owner/review decisions, and exact locations. Do not silently prefer newest over best-qualified.
3. **What stage?** Idea; science/theory specified or contested; architecture specified or contested; code implemented; test/review evidence; actual producer→consumer integration; original science/permissions; human/product evaluation. Separate axes; scoped claims.
4. **What does X require?** Qualified upstream prerequisites, recursive prerequisite-of-prerequisite links, AND requirements vs genuine OR alternatives, concretely present or absent leaves, owners and precise blockers.
5. **What connects to X?** Actual upstream producers, downstream readers/consumers, artifact/schema/semantic contracts, the exact state of *each connection* and proof/counterevidence.
6. **What does X unlock?** Reverse dependencies, newly possible functions/sections, contribution to the whole Sorok program.
7. **What next?** Clearly described missing function/choice/integration/test, practical reuse opportunity, who can lawfully do it, relevant independent work, and reason for priority.

The same guide must answer whole-project and middle-scale versions of these questions without requiring the agent to read every historical page.

## 3. SOURCE INDEX FIRST, THEN COMPONENT ANCHORING — NO REINVENTED HISTORY

"Everything in one place" means **one reliable place to find and understand** the assets, not moving/copying every GitHub file, branch, document, Library source or local archive. Make references durable: repository, branch or immutable commit, path, source identity where useful, key symbol/section, relationship to current program, evidence/last inspection scope.

Keep all materially useful assets visible, including:
- Current authoritative or most-qualified implementation.
- Older implementations with reusable FUNCTIONS even if their old theory or interface is superseded.
- Alternatives, conceptual proposals and superseding decisions; why a path was abandoned.
- Returned work accepted at a narrow scope, unadopted tested candidates, negative reviews and exact failure witnesses.
- Existing code that has no current consumer (especially source-present/unwired material families), as well as already solved problems that must never accidentally be commissioned anew.
- Sources named in other sources but not currently available; distinguish SOURCE_REFERENCED_NOT_FOUND from NOT_SEARCHED and SOURCE_NOT_ACCESSIBLE.
- Source and authority conflicts rather than homogenizing them away.

Do not claim "zero orphaned assets" simply because every index row has a *named intended first consumer*. Actual contemporary importer/reader is a different fact. A candidate or historical consumer must not be relabeled an active one.

## 4. Minimal data model — choose simplest workable storage after reuse audit

This is a **logical relationship model**, not an engineering mandate for a graph platform. Existing O-INDEX/O-LIVE records may already implement much of it. A coherent set of linked Markdown sourcebooks plus small JSONL/JSON/TSV tables is adequate if agents can reliably retrieve/trace it. A short script for consistency/traversal is optional, not a prerequisite for usefulness.

**Required conceptual records:**

**ASSET/REFERENCE** — stable key; type (code, docs, theory, plan, review, return, test, historical artifact, Library/local source); canonical location and exact cut; owner/source; original claim or function; currentness/read depth; disposition: ACTIVE, HISTORICAL_REUSABLE, ALTERNATIVE, SUPERSEDED, REJECTED_WITH_REASON, CANDIDATE, DISCONNECTED, UNKNOWN/UNREAD; tied component IDs or explicitly UNMATCHED; evidence of decision. Any referenced external asset remains discoverable even if not locally copied.

**COMPONENT/REQUIREMENT** — stable original or qualified local ID; parent section and crosscutting domains; plain purpose and scope; originating vision/requirement; authoritative/current candidate plan; best current implementation(s) and historical variants; independent maturity/status axes for conceptual/science, architecture, code, test/review, real integration, source/owner/native permission and product/human validation; directly implicated assets; owner; open questions; next work; source-cut last checked.

**RELATION / DEPENDENCY / SEAM** — source and target component IDs or exact assets; relation type (CONTAINS, REQUIRES, ALTERNATIVE_TO, PRODUCES, CONSUMES, IMPLEMENTS, EVIDENCES, SUPERSEDES, CONFLICTS_WITH, UNLOCKS); prereq AND/OR conditions where material; exact producer/output/contract/consumer when claiming a runtime seam; whether intended, actually instantiated, tested, blocked, broken or unverified; scoped evidence and version cuts; owner and single next step to qualify.

**GAP / NEXT ACTION** can be derived from components + relations or stored as a linked compact record when it improves clarity. Every gap must point to a program requirement and the actual missing item; distinguish science/architecture/software/integration/test/permission/missing source and unknown work; no invented universal percentage or magic priority formula.

**CHRONOLOGY/DECISION** need not be a separate database: link existing Q/D/R and exact owner/reviewer materials from the relevant asset/component/edge; preserve valid negative results. Only the minimal change log that makes later updates traceable is needed.

## 5. Dependency and seam status semantics

For X requires A/B, recursion should reach exact available source/implementation or an explicitly marked unknown, without inventing science or source authority. "Requires" must reflect a real engineering/scientific/owner requirement, not merely a topical cross-reference. If two designs are alternatives, show a valid OR/choice, not force a false serial predecessor. Show reverse links so completing one item identifies downstream unlocked work. Avoid infinite loops; flag genuine cycles for resolution.

**Seam status applies to the *connection*, separate from each component's own stage.**
- GREEN_VERIFIED: exact producer/artifact/consumer behavior demonstrated at the explicitly stated scope (e.g. sourcefree author-tested, independently reviewed, native).
- PARTIAL_OR_FRAGILE: partly connected, conditional, known quality/contract limitation.
- BROKEN_RED: documented mismatch/failed interface/negative test.
- UNBUILT: required connection specified but not implemented.
- UNKNOWN_OR_UNTESTED: no sufficient current evidence; absence of witness is not proof of failure.
- OWNER_HELD: requires named legitimate science/source/actor/merge right; not automatically broken software.
- HISTORICAL_ONLY, SUPERSEDED, NOT_APPLICABLE: where supported by source.

Keep separate statuses for different evidence dimensions: e.g. a successful sourcefree C9→later E2 experimental seam can be GREEN at its tested cut and simultaneously NATIVE_HELD/UNKNOWN; neither statement overrides the other. Only a verified actual current first consumer is an ACTUAL_CONSUMER. A required/named consumer remains REQUIRED_CONSUMER unless verified.

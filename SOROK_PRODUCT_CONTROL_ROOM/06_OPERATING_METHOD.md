## 1. The problem

Sorok is intentionally green-field. Prematurely forcing certainty would be as damaging as unstructured brainstorming.

The method therefore preserves:
- imagination before closure;
- explicit uncertainty;
- traceable decisions;
- bounded investigations;
- prototypes where prose cannot settle behavior;
- architecture ownership;
- reversibility;
- connection to the governed codebase.

## 2. Canonical lifecycle

Every material product idea should move through:

`CAPTURE → FRAME → INVESTIGATE → PROTOTYPE / MODEL → ADJUDICATE → RECORD → CROSSWALK → HANDOFF → VERIFY`

### CAPTURE
Add a question or hypothesis to `registers/QUESTIONS.jsonl`.

### FRAME
State:
- exact question;
- why it matters;
- what would change depending on the answer;
- dependencies;
- what evidence could answer it;
- what is explicitly out of scope.

### INVESTIGATE
Use the lightest method sufficient:
- conceptual analysis;
- existing repo archaeology;
- literature / product research;
- user research;
- paper prototype;
- interactive prototype;
- simulation;
- cost experiment;
- adversarial / abuse test.

### PROTOTYPE / MODEL
Prototype only the uncertainty that prose cannot resolve.

### ADJUDICATE
Choose:
- `ACCEPT_PROVISIONAL`
- `ACCEPT_REQUIREMENT`
- `REJECT`
- `DEFER`
- `NEEDS_MORE_EVIDENCE`

### RECORD
Write one decision record. Do not bury decisions in a docket narrative.

### CROSSWALK
Identify exactly which existing Rawlsing owners, seams or runtime layers are affected.

### HANDOFF
Only `ACCEPTED_PRODUCT_REQUIREMENT` items can be packaged for governed engineering.

### VERIFY
After implementation, test whether the actual experience satisfies the product requirement.

## 4. Docket structure

When a question requires more than a short adjudication, create:

`dockets/D###_<slug>/`

Recommended contents:
- `00_DOCKET.md` — question, stakes, scope, dependencies;
- `01_CURRENT_KNOWLEDGE.md`;
- `02_OPTIONS.md`;
- `03_EVIDENCE.md`;
- `04_PROTOTYPE_OR_MODEL.md` where relevant;
- `05_ADVERSARIAL_FAILURES.md`;
- `06_RECOMMENDATION.md`;
- `07_DECISION_RETURN.md`.

A docket may omit files that do not help answer the question. Do not ritualize paperwork.

## 5. Decision record law

Every decision must state:
- decision ID;
- date;
- status;
- question(s) closed;
- exact decision;
- rationale;
- evidence;
- rejected alternatives;
- consequences;
- affected workstreams;
- architecture impact;
- reopen condition.

A decision is not immortal. Reopening must cite the exact new evidence or contradiction.

## 6. Evidence discipline

Distinguish:
- project vision;
- current repo fact;
- empirical research;
- design convention;
- user preference;
- prototype observation;
- inference;
- normative choice.

Do not smuggle a normative model of flourishing in as psychology.

Do not treat market convention as moral necessity.

Do not treat compelling UX copy as architecture evidence.

## 7. Prototype ladder

Prefer the cheapest falsifier:

1. state diagrams / scenario walkthroughs;
2. scripted conversation prototype;
3. LLM prompt prototype with fixed hidden state;
4. event-sourced dyad prototype;
5. persistent single-person alpha;
6. only then broader world / social / monetized experiments.

## 8. Weekly / session discipline

At the end of a substantive Sorok session:
1. update affected question records;
2. add decisions if any;
3. add risks if discovered;
4. update `state/CURRENT_STATE.md`;
5. identify the next 1–3 highest-leverage dockets;
6. do not rewrite stable charter/ontology files unless their governing content changed.

## 9. No-chat-canonicality law

Chat is an ideation surface, not the durable project state.

Anything we would regret forgetting must be serialized into Sorok before the session ends.

## 11. Architecture compression / kernel-sifting law

Sorok must not confuse an increasing number of correct propositions with an increasingly coherent architecture.

After any substantial ideation or hostile-review wave, perform a **compression pass**.

The compression pass asks:

1. What concrete part of the current organism changed?
   - state compartment;
   - owner;
   - causal flow;
   - membrane;
   - feedback loop;
   - clock;
   - fork/inheritance rule;
   - tunable balance;
   - user-facing circulation.

2. Which new decisions are genuinely independent?
3. Which are consequences of an already-visible deeper invariant?
4. Which older decisions can now be read as derived consequences rather than separate axioms?
5. What repeated structural necessity appears across otherwise different domains?
6. Does that repeated necessity strengthen, weaken or split a candidate kernel?
7. What hostile case would distinguish competing kernel candidates?

Canonical compression output belongs first in:
- `03_REAL_ALPHA_SPINE.md` for the current living organism;
- `registers/QUESTIONS.jsonl` when the central derivation remains unresolved;
- the decision/risk ledgers for exact local law;
- a bounded docket only when deeper investigation is required.

Do **not** create a new synthesis artifact merely because a new conceptual phrase sounds central.

### Rule-count anti-metric

`MORE RULES != MORE ARCHITECTURE`.

A mature Sorok pass should increasingly produce one of:

- **DERIVE** — local rules collapse into a deeper principle;
- **SEPARATE** — two apparently similar phenomena prove to require different owners;
- **CONNECT** — previously separate organs enter one causal circulation;
- **TUNE** — a design question becomes a balance inside an existing organism;
- **FALSIFY** — a candidate kernel/spine fails a hostile case;
- **PROMOTE** — a candidate kernel gains derivational power across independent domains.

### Kernel non-presumption

The final Rawlsing kernel is not currently known.

A candidate may not be promoted merely because:
- it matches project philosophy;
- it is rhetorically elegant;
- many artifacts can be redescribed using it;
- the user or Vozhd finds it intuitively satisfying.

Promotion requires **derivational compression**: the candidate must make substantial existing architecture follow non-arbitrarily and predict failure cases before they are separately legislated.

Until then:

`KERNEL = OPEN DISCOVERY`.

### Hostile review output law

Future hostile architecture reviews must return two layers:

**Layer A — local corrections**
- exact missing law/risk/question if any.

**Layer B — organism synthesis**
- machine component affected;
- causal relation changed;
- repeated pattern exposed;
- candidate-kernel implications;
- opportunities to demote rules into derived consequences.

A review that only adds propositions without attempting Layer B is incomplete.


## 12. Worker orchestration / prompt-dispensation law

The full controlling procedure is:

`00C_HQ_PROMPT_DISPENSATION_AGENT_ROUTING_AND_ORCHESTRATION_CONSTITUTION_R1.md`.

Sorok inherits Pyat's mature orchestration principles at process grain:

- capability, access, authority and evidence remain noncollapsed;
- reasoning intelligence, execution surface and authority role are separately selected;
- substantive Sorok work defaults to HIGH reasoning unless the job is mechanically bounded;
- maximum/Omega reasoning is reserved for named semantic/authority/readiness triggers, not difficulty or shell requirements;
- Browser/GitHub is preferred for documentary/authority/science/review work when its tools suffice;
- executable runtime work uses an actual verified runner, with bounded local/Codex/OpenCode fallback when needed;
- one coherent outcome has one accountable owner and one independent material acceptance review;
- live remote branch state is resolved before launch/relaunch/status claims;
- safe orthogonal work may run concurrently, while overlapping semantic/file owners serialize;
- every material launch uses the mandatory 00C prompt schema and return contract;
- after two substantively unchanged failed loops, HQ diagnoses the mechanism before issuing another equivalent prompt.

The orchestration objective is accepted evidence-producing progress, not maximum agent count or maximum model strength.

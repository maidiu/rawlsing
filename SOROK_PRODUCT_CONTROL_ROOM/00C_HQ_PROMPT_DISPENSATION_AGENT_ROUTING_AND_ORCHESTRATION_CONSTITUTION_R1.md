# 1. Hard noncollapse: intelligence != surface != authority

Every Sorok worker assignment MUST classify three independent axes.

## A. REASONING / INTELLIGENCE CLASS

How hard is the reasoning problem?

## B. EXECUTION SURFACE

What tools/runtime does the job actually require?

## C. AUTHORITY ROLE

What is this agent allowed to conclude, mutate, execute or adopt?

Never infer one from another.

Hard laws:

```text
BROWSER/GITHUB != LOW INTELLIGENCE
CODEX/LOCAL != HIGHER REASONING
ASTRA != SHELL EXECUTOR
HIGH REASONING != SEMANTIC AUTHORITY
EXECUTION CAPABILITY != EXECUTION PERMISSION
REVIEWER != ADOPTER
IMPLEMENTER != INDEPENDENT REVIEWER
```

A high-intelligence Browser/GitHub scientist may be the correct owner for an authority court.

A local/Codex executor may be the correct owner for a narrow deterministic test while having no authority to reinterpret the architecture.

# 3. Intelligence routing

Sorok HQ MUST specify the minimum sufficient reasoning level for each worker.

Current product/model labels may change over time; therefore record both:
1. **capability class**;
2. exact selected model/configuration when known.

## I0 — deterministic/tooling helper

Use for:
- hashes;
- counts;
- manifest checks;
- mechanically specified transforms;
- exact command execution.

No architecture/science adjudication.

## I1 — standard bounded reasoning

Use only for:
- routine clerical repo work;
- low-ambiguity transformations;
- exact already-decided implementation tasks.

Not sufficient for consequential Sorok architecture, psyche science, genealogy authority or cross-owner review.

## I2 — HIGH reasoning

**Default for substantive Sorok workers.**

Use for:
- architecture investigation;
- authority archaeology;
- scientific test design;
- hostile review;
- implementation with meaningful semantic constraints;
- independent acceptance review;
- causal/relational/personhood questions.

Where the product exposes a named High reasoning configuration, specify it.

## I3 — MAXIMAL / OMEGA reasoning

Reserve for material questions where an error propagates across the program, especially:
- unresolved contradiction between competent authorities;
- new semantic grain or owner jurisdiction;
- architecture that cannot represent a mandatory capability without loss;
- whole-program readiness;
- PRE-V3→V3 seam/wake/weld recommendation;
- persistent implementer/reviewer disagreement after exact evidence;
- cumulative contract drift;
- white-whale decision whose answer materially determines continuation versus redesign.

Use Astra/Omega-class review or the strongest currently available reasoning configuration appropriate to the question.

Difficulty alone does not trigger I3.

Revision count alone does not trigger I3.

A shell requirement never triggers I3 by itself.

## Intelligence escalation law

Start at the lowest class competent for the **reasoning**, not the cheapest model that can emit text and not the most expensive model available.

Escalate only when:
- the current worker identifies a concrete reasoning limit;
- independent review exposes unresolved substantive disagreement;
- an I3 trigger above becomes true.

Do not silently upgrade paid/finite resources.

# 4. Execution-surface routing

After intelligence is chosen, select the surface independently.

## S0 — Browser/GitHub/documentary

Preferred when the job requires:
- repository archaeology;
- authority comparison;
- design/science specification;
- code forensics;
- branch/file writes through GitHub;
- independent documentary review;

- exact remote verification.

Browser is valid for I2/I3 reasoning if the required tools are present.

## S1 — Browser + supported execution / authorized CI

Use when the browser worker can actually run the required bounded execution with reproducible logs.

Do not infer runtime from "browser."

## S2 — Local/Codex/OpenCode execution worker

Use when the task actually requires:
- checkout/worktree;
- shell/process control;
- Python/Node;
- pytest;
- generated artifacts;
- repeated local repair/test loop;
- model API/runtime not available to Browser.

Give S2 a bounded exact job when possible.

A runtime executor does not inherit HQ or semantic authority.

## S3 — external specialized source/model environment

Use only with explicit relevant access/permission.

Examples:
- original survey runtime;
- licensed source environment;
- named model-provider experimental surface.

No prompt may manufacture this access.

# 5. Default routing decision tree

Before issuing the prompt, HQ should answer:

1. **Can the outcome be established without process execution?**
   - YES → prefer S0 Browser/GitHub.
   - NO → continue.

2. **Does the current Browser/authorized CI actually provide the required runner?**
   - YES → S1.
   - NO → S2 bounded executor.

3. **Does the task involve new semantic authority, cross-owner meaning or program readiness?**
   - YES → candidate work may proceed on the appropriate surface, but require I2/I3 independent authority review.
   - NO → ordinary implementation/review law.

4. **Does it require original source/model/actor access?**
   - YES → verify explicit grant before execution.
   - NO → do not ask for or simulate such access.

5. **Is there already an active worker for the same outcome?**
   - YES → continue/reconcile that worker unless exact evidence warrants replacement.
   - NO → launch.

6. **Are outputs/owners orthogonal?**
   - YES → parallelize if host/user capacity permits.
   - NO → serialize or define one writer.

# 5A. BINDING EVIDENCE-GROUNDED ENVIRONMENT SUITABILITY VERDICT (USER DIRECTION 2026-10-14)

**A launch cannot replace HQ's environment judgment with an unranked menu.** User preference is Browser when it is technically and economically sensible. HQ MUST state, in plain language, which environment is genuinely the best execution host, not just which ones are theoretically able to run Python. Use exact earlier import/runner evidence, known source/dependency size and test-loop nature, distinct model-grant needs, and realistic session continuity.

Every material prompt MUST have the following standalone fields **BEFORE** the worker is launched. Each field must contain a substantive answer rather than "Browser or local whichever works":

1. `HQ_ENVIRONMENT_VERDICT` — choose EXACTLY ONE primary class:
   - `BROWSER_NATIVE`: Browser/GitHub plus currently available independent/small runner is the **preferred** way to perform the *entire stated proof*. No substantial private owner import graph; setup is light or documentary only. Browser-first; do not use local simply because sourcefree code exists.
   - `BROWSER_AMORTIZED`: Browser is the **preferred investment only under a specified continuation queue** (default at least two further same-domain operations sharing verified files/imports). Initial staging is material; declare the actual dependency burden and run the first decisive test before continuing. If no coherent follow-on queue or warm continuity, prefer an identified local executor.
   - `LOCAL_DOMINANT`: For the **stated acceptance grade**, an authorized persistent Codex/OpenCode/DeepSeek-Harness worktree is substantively better than Browser because of transitive imports, test/repair loops, source transport, model/provider controls or large output. Say "LOCAL RECOMMENDED" plainly. Browser may be a bounded fallback, never described as an equally good option merely because it has Python.
   - `SPECIALIZED_REQUIRED`: Authorized source/model/actor environment is intrinsic; choose only with explicit permission and cost policy, and identify sourcefree preparatory work separately.

2. `BROWSER_SUFFICIENCY` — `FULL` / `SCOPED_ONLY` / `NOT_QUALIFIED`, with *which* actual discriminating proofs Browser can and cannot reach. Qualify unknown imported dependencies by attempted earlier evidence: observed inability to materialize != general Browser impossibility.
3. `BROWSER_SETUP_COST` — `LIGHT` / `MATERIAL` / `HEAVY`, grounded in observed imports, file/module closure and test-loop requirements. Explicitly say whether it is likely to struggle, why, and whether initial source staging is worth doing.
4. `WARM_REUSE_PLAN` — name the exact observed/user-reported prior window and domain affinity, what live marker/import paths/permissions need probing, how many **related** follow-on jobs could amortize source staging, and how to respond if the runtime vanished. User-open != verified live. Neither a branch SHA nor a portable passport proves persistence.
5. `PRIMARY_MODEL_AND_HOST` — selected model and effort plus host/account if truly known, or explicitly state user-selectable preference among verified permissible options; explain why class suffices. Never infer cash price from model name.
6. `FALLBACK_TRIGGER` — one objective condition for changing host (e.g. exact missing transitive import after a bounded staged-closure attempt; no grant for model API; no same-domain continuation queue). State what is **not** an excuse to switch (missing full clone alone, general discomfort with Browser, or an open tab implying warm imports).
7. `WHY_NOT_ALTERNATIVE` — a short decisive comparative statement distinguishing preferred Browser, amortized Browser, or local.

**Hard law:** when the user prefers Browser, do not route Browser-native tasks to local by reflex. Do not route LOCAL_DOMINANT work to Browser for its full acceptance proof because it is "technically possible" unless a new evidence-based comparison actually overturns the classification. An individual worker can perform its first cheap capability probe and report a change, but must not silently replace an explicit HQ routing decision with an agnostic menu. Under `BROWSER_AMORTIZED`, HQ must say *whether the contemplated sequential work warrants the initial cost*, not delegate that decision to the user in vague wording.

**Acceptance-grade discipline:** static document review, isolated sourcefree fixture PASS, pinned imported-owner PASS, real model behavior, real-source science, actor use, and governed deployment are distinct. Routing is relative to the specific proof sought. When only a smaller isolated proof runs in Browser, classify `SCOPED_ONLY`; do not sell it as full fitness. Source materialization from the GitHub connector into a browser Python container is a separate actual operation; inspect real data path and earlier failures, not stereotypes of Browser capability.

**Invalidity:** a new consequential commission that gives `Browser / Codex / OpenCode, whichever is available` without ONE class, clear comparative judgment, setup burden, continuation economics and fallback is `SOROK_ENVIRONMENT_ROUTING_INVALID__REISSUE_REQUIRED`. This is an HQ-level nondelegable decision and supplements all sections below, including the mandatory prompt fields in §9. Only explicit new live evidence may override the documented HQ verdict, with reasons recorded.

# 13. Astra / Omega escalation triggers

Escalate to I3 / Astra/Omega when, at exact grain:

- two competent accepted authorities conflict and chronology does not resolve them;
- repair changes semantic grain, owner jurisdiction or required proof;
- mandatory capability cannot be represented without loss by current owners;
- source-free evidence is about to be promoted into production/readiness permission;
- full-system/world/actor-seam readiness is about to be claimed;
- candidate and independent reviewer remain materially divided after exact evidence and one diagnosis;
- integration loses provenance/negative/currentness/dependency meaning and repair requires new semantics;
- proposed fix waives accepted scope or invents comparability/model law;
- evidence integrity is materially disputed;
- cumulative small changes amount to a new interface/program.

Do NOT escalate to Astra because:
- shell is needed;
- the task is long;
- a test failed;
- the worker needed revisions;
- a Library item is missing;
- Codex would be convenient.

Astra receives a compact decision packet, not a transcript.

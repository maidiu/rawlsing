# Sorok Court 8D — Optional Personal Details / Portal Profile Design Space R1

Status: EXPLORATORY_PRODUCT_MECHANISM__HOMOLOGOUS_PEER

Date: 2026-09-29

## 0. Core proposal

Offer the user an optional pre-entry **Portal Profile** that lets them supply selected real-life facts before homologous-peer transposition.

This is not character creation.

It is user-authorized source material for deciding:
- what should remain literally true of the user;
- what should influence homologous mapping;
- what should become a local diegetic coordinate;
- what should remain off-stage/private;
- what the portal should know in order to avoid fabricating the user.

Core distinction:

`USER-SUPPLIED FACT != GENERATED PLAYER PSYCHE`.

---

## 1. Why personal details are useful

Optional real-user facts can improve:

1. **self-continuity** — preserve facts that are genuinely part of the user's life;
2. **homology quality** — map structural position more intelligently;
3. **portal translation** — establish stable coordinate bindings before contradictory speech occurs;
4. **capability realism** — know actual languages/skills/access needs the user wants carried;
5. **off-stage constraint realism** — preserve important obligations without simulating the user's full real life;
6. **player-reflection accuracy** — distinguish behavior caused by assigned constraints from patterns that persist across them;
7. **comparative/replay modes** — hold subjectivity fixed while varying structural position.

---

## 2. User should control disposition, not merely disclosure

For each supplied fact, the interface could allow a treatment choice such as:

- **CARRY** — keep this as part of me;
- **TRANSLATE** — preserve its structural/social function in homologous local form;
- **MEANING ONLY** — preserve the experiential/relational meaning but not literal identifying coordinate;
- **OFF-STAGE** — let this constrain me where needed but do not instantiate it locally;
- **PRIVATE** — do not use it in the simulation;
- **LET PORTAL DECIDE** — permit governed treatment under the portal constitution.

Not every class needs every option.

---

## 3. Potential input domains

Candidate optional domains include:
- name/pronouns;
- age;
- languages;
- education/knowledge;
- occupation / work pattern;
- skills;
- accessibility/physical constraints;
- religion/nonreligion or worldview if the user wants it carried;
- important family/relationship topology;
- caregiving obligations;
- formative places;
- socioeconomic background;
- current time burden;
- transport habits;
- important losses/events;
- migration history;
- hobbies/tastes;
- selected commitments the user wants treated as real.

Sensitive fields must be optional and never inferred merely because another field was supplied.

---

## 4. Structural facts can be used without importing power

Example:

A user may say they are a physician.

Possible decomposition:
- medical knowledge/skill → CARRY;
- prestige/status → HOMOLOGIZE;
- actual employer → BRACKET;
- actual salary → DO NOT IMPORT into main homologous-peer resource envelope;
- work-time burden → optionally map functionally.

Thus the profile can preserve the person without importing structural dominance.

---

## 5. Family and relationships can be represented at multiple grains

A user may want Rawlsing to know:
- I have a partner;
- I have children;
- I am close to my parents;
- I care for an elderly relative;
- I have a sibling I speak to weekly.

Main mode need not generate synthetic copies of these people.

Possible treatment:
- preserve the relationship's existence as an off-stage real-user constraint;
- preserve time/commitment implications;
- allow the user to speak truthfully about them;
- instantiate no local actor unless a separate mode explicitly calls for it.

This avoids total-life simulation.

---

## 6. Portal binding can happen before entry

Supplied facts can pre-resolve some stable mappings:

Example classes:
- educational credential → local status homologue;
- occupation → local functional/status homologue;
- hometown type → local spatial/urbanity analogue;
- purchasing-power reference → local equivalent scale for speech;
- work schedule → local time-demand envelope.

The user may inspect these mappings before entry or choose a discovery mode.

---

## 7. Personal facts can create intentional non-homologies

The Portal Profile can also mark facts that should **not** be translated.

Example:
- a specific formative loss;
- a religious conversion;
- an actual learned language;
- a meaningful artistic taste;
- a political/historical memory;
- a disability experience;
- an important real relationship.

These may remain genuine user history even if they make the impossible-subject premise visible.

This can be more honest than forcing local equivalence.

---

## 8. A useful privacy model: purpose-bound facts

Each fact should have an explicit use purpose.

Possible purpose tags:
- `PLAYER_SELF_CONTINUITY`;
- `PORTAL_HOMOLOGY_INPUT`;
- `WORLD_CONSTRAINT`;
- `CAPABILITY_INPUT`;
- `LANGUAGE_MEDIATION`;
- `OFFSTAGE_OBLIGATION`;
- `PRAXIS_CONTEXT`.

A fact supplied for one purpose should not silently authorize all others.

Example:
providing religion for social-legibility modeling should not automatically authorize psychological inference.

---

## 9. Progressive disclosure remains preferable to exhaustive onboarding

Upfront entry should be optional and lightweight.

Possible structure:

### Minimal entry
Only facts needed for playability.

### 'Make the portal more like me'
Optional deeper profile.

### Contextual additions
When a new class of fact becomes relevant, Rawlsing may ask whether the user wants to supply/transport it.

This avoids a 45-minute intake form.

---

## 10. Profile depth modes

Potential modes:

### VEIL LIGHT
Minimal personal input; portal assigns almost everything structural.

### VEIL PERSONAL
User supplies selected continuity facts, skills, obligations and background.

### VEIL DEEP
User supplies a richer autobiographical/structural profile for high-fidelity homology and longitudinal comparison.

All modes preserve the same core action/world laws.

---

## 11. Interesting product capability — structural replay

If the user supplies enough stable real-user context, Rawlsing could later replay the **same user** under different homologous positions.

Examples:
- more/less economic security;
- different household burden;
- different transport/access;
- different institutional status;
- different social-network reach.

Then the system can compare realized behavior without claiming any replay reveals the user's essence.

This could operationalize:

> what changes when the same present subject acts from a different position?

That is highly aligned with the veil experiment.

---

## 12. Interesting analytic capability — user / persona structural crosswalk

Rawlsing could privately maintain a non-evaluative structural comparison:

`USER REAL-WORLD INPUT (optional)`
vs
`PLAYER HOMOLOGOUS POSITION`
vs
`FOCAL PERSON POSITION`.

This can help ensure the player really is peer-comparable.

It should not become a visible social-rank score.

---

## 13. Possible later alternate-self mode

A rich user profile could also seed a separate **alternate-self experiment**:

- preserve selected user starting invariants;
- transpose structural position;
- let V3 generate a distinct locally formed person from childhood/life-course;
- compare that generated alternate to the actual user.

This should remain separate from main Sorok play because the generated alternate is not the actual player.

But the same Portal Profile could provide lawful input.

---

## 14. Praxis reflection benefit

Optional real-user details can improve later reflection by letting Rawlsing say:

- this behavior persisted despite a major structural change;
- this behavior appeared only under extreme scarcity;
- this choice was unavailable under the assigned material envelope;
- your local credential/power was lower here than in your supplied real-world context.

Still forbidden:
- diagnosis;
- essence claims;
- hidden motive inference.

---

## 15. Critical anti-dossier law

The Portal Profile must not become:
- a personality test;
- a psychometric intake;
- a hidden marketing profile;
- a pretext for inferring sensitive characteristics;
- a requirement to disclose one's life to play.

Principle:

> **Ask only for facts that change a known portal function, tell the user what function they serve, and allow omission.**

Unknown / withheld must remain legitimate states.

---

## 16. Deletion / edit semantics

Need explicit controls for:
- review supplied facts;
- change future portal use;
- delete profile facts;
- distinguish deletion from already-occurred in-world history;
- reset/rebuild a portal world if translated bindings depend on a removed fact.

Never silently rewrite already-admitted relationship history after a profile edit.

---

## 17. Current strongest product form

Rather than:

> Build your character.

present:

> **What, if anything, should cross the veil with you?**

Then explain each optional domain by function.

This frames disclosure as preserving the actual user rather than constructing an avatar.

---

## 18. Hard tests

1. User supplies profession but not salary.
2. User supplies an important disability but does not want it disclosed socially.
3. User supplies spouse/children but does not want them simulated.
4. User supplies religion privately but never tells the focal person.
5. User omits class background entirely.
6. User supplies an actual traumatic/loss event but wants its location bracketed.
7. User deletes a fact after ten simulated years.
8. User chooses minimal profile and later answers an autobiographical question in conversation.

Any design that requires full disclosure or turns supplied facts into psyche fails.
